# M0 风险清零 —— 实测结论

日期：2026-09-14
构建：Release，`net10.0-windows`，win-x64
原始数据：[`artifacts/m0/`](../artifacts/m0/)

M0 的目的是把方案里三个「只能靠实测确定」的未知项变成数据。结论如下，其中**一项未达标**、**一项推翻了我自己提出的方法**。

## 1. 环境事实

| 项 | 值 |
|---|---|
| OS | Windows 11 家庭版中文版，Build **26200**（25H2） |
| 会话 | Console（非 RDP），真实硬件 |
| 机器 | LENOVO 21VR，AMD Radeon 780M 核显 |
| 内存 | 31.3 GB |
| 显示器 | **单屏 3072×1920 @ 168 DPI（175% 缩放）** —— 见下方纠正 |
| 渲染层级 | **Tier 2 完整硬件加速**，PS 2.0/3.0 可用 |
| 小组件 | 已安装，但 `HKLM\...\Dsh\AllowNewsAndInterests = 0`（已被策略关闭） |
| `ForegroundLockTimeout` | 200000（默认值，符合预期） |

**一个必须记住的陷阱**：最初用 Windows PowerShell 5.1 测显示器，得到「1755×1097 @ 96 DPI @ 100% 缩放」。那是**DPI-unaware 进程被系统虚拟化后的假值**。

真实值是 **3072×1920 @ 168 DPI（175% 缩放）** —— 3072/1755 = 1.75，完全吻合，是同一个物理屏幕的两种读法。

这不只是数字纠正，它改变了几个判断：
- **本机本身就是高 DPI 环境**，不是我原先以为的 100% 缩放。DPI 换算从「以后要考虑」变成「现在就必须对」。
- 真实像素量 **5.9M**，是 4K（8.3M）的 71%，而不是我先前以为的 1.9M。全屏合成的性能担忧比我估的更接近现实。
- `--env` 与 `--overlay-probe` 必须由声明 PerMonitorV2 的进程运行，这条不能省。

同理，`.ps1` 脚本必须以 **UTF-8 with BOM** 保存，否则 PowerShell 5.1 按 GBK 解码中文注释会破坏 here-string 解析；而且 PowerShell 通过管道输出中文用的是 GBK，拿 `grep` 匹配中文前要先 `iconv -f GBK -t UTF-8`。

**本机无法验证的两件事**（写进已知限制）：多显示器、混合 DPI 缩放。单屏 100% 缩放下，「一个 HWND 只能有一个 DPI」和跨屏 DPI 换算这两个坑都复现不了。

## 2. M0.4 热键实测 —— Win+W 的结论

网上证据互相矛盾（whkd #6 称 Win+W 无法拦截，AHK 社区称可以），所以必须实测。分两步取证据。

### 第一步：`RegisterHotKey` 试注册

| 组合 | 结果 |
|---|---|
| **Win+W** | **不可用，err=1409（已被占用）** |
| **Ctrl+Win+W** | **可用**（本方案默认值，已验证） |
| Alt+Win+W | 不可用 1409 |
| Shift+Win+W | 不可用 1409 |
| Win+A | 不可用 1409（符合预期：Win11 快速设置） |
| Win+F1 | 不可用 1409 |
| **Win+F13** | **可用** |
| Ctrl+Alt+Win+W | 可用 |
| Ctrl+Shift+W | 可用 |

**结论：`MOD_WIN` 没有被系统性拦截**（Win+F13 能注册成功），而是**真实的逐个按键被 shell 预留**。Win+W 即使小组件已被策略关闭，仍然注册不到 —— 说明占用来自 shell 而非小组件本身。

**可用规律：给 Win+组合再加一个修饰键（Ctrl）就能绕开 shell 的预留。** 这条规律要用在设置的热键选择器里：用户选了一个 1409 的组合时，直接建议「加上 Ctrl 试试」。

### 第二步：`WH_KEYBOARD_LL` 钩子能否截获 Win+W

注入 Win down / W down / W up / Win up 后，钩子观察到：

```
VK    方向   Win  Ctrl  Alt  Shift  注入
0x5B  down  Y    .     .    .      Y     ← Win 按下
0xFF  up    Y    .     .    .      Y     ← 本钩子注入的幽灵键（清残留状态）
0x57  down  Y    .     .    .      Y     ← W 按下，且 Win 处于按下状态
0x57  up    Y    .     .    .      Y     ← W 抬起
0x5B  up    .    .     .    .      Y     ← Win 抬起（被吞掉，不会弹开始菜单）
```

热键回调触发 1 次，吞键生效。

> **结论：Win+W 能被低级键盘钩子截获，吞键方案成立。** 用户若坚持用 Win+W，走钩子路径可以实现。

**✅ 已用物理按键复核**（`--hook-probe --interactive=15`，手动按 9 次 Win+W）：

```
0x5B  down  Y    ← Win 按下（物理，非注入）
0xFF  up    Y  Y ← 幽灵键清残留状态
0x57  down  Y    ← W 按下，Win 处于按下状态 → 匹配、吞键、触发回调
0x5B  up         ← Win 抬起（被吞，不弹开始菜单）
0x57  up         ← W 抬起（被吞）
```

9 次全部命中，热键回调触发 9 次。注入测试留下的不确定性消除。
小组件也不会弹出 —— 钩子返回 1 吞掉了按键，shell 根本没机会看到它。

**日志还暴露了一个此前不知道的行为**：幽灵键（`0xFF up`）出现在 `0x57 down` **之前**，但幽灵键是处理 W-down 时才发出的。原因是 **`SendInput` 在钩子回调内部会同步重入同一个钩子** —— 注入事件立刻又被回调处理一遍并入队，所以排在了当前事件前面。这里无害（不同 VK、回调足够短），但它意味着回调会嵌套执行、栈深度翻倍，**"回调里只做匹配和吞键"这条纪律比原先估计的更重要**。

## 3. M0.3 内存实测 —— **未达标**

### 最终数字（Release，稳态：托盘 + 预热窗口 + 隐藏遮罩）

| 口径 | 数值 |
|---|---|
| **任务管理器「活动的专用工作集」** | **71.8 MB** |
| 完整工作集（`WorkingSet64`） | 148.9 MB |
| 私有提交字节（`PrivateMemorySize64`） | 86.7 MB |
| GC 堆 | 2.1 MB（可忽略） |
| 线程 / 句柄 | 21 / 1485 |

**对照 60MB 目标：未达标。** 我在方案里写过不达标会如实汇报，这里是原始数据。

### 分阶段定位

| 阶段 | 任务管理器口径增量 |
|---|---|
| 应用刚启动（无窗口、无托盘） | 基线 ≈ 47 MB |
| + 托盘图标 | +6 MB |
| **+ 原生 Win32 遮罩窗口** | **+0.1 MB（几乎免费）** |
| **+ WPF 轮盘窗口（AllowsTransparency）** | **+50～90 MB** |

### 关键发现一：遮罩层必须用原生窗口，但省下的是 12-15MB 而非 61MB

最初的对照实验显示「WPF 版遮罩窗口消耗 61MB、原生版只消耗 0.1MB」，我一度以为找到了 61MB 的省法。**这个结论是错的** —— 换成原生遮罩后总内存只降了约 12-15MB。

原因：**WPF 的渲染栈是一次性公共开销**。在同时创建两个 WPF 窗口的测试里，这笔开销记在了先创建的遮罩窗口头上；去掉它之后，同样的开销转移到了轮盘窗口（+50MB → +91MB）。

正确的结论是：遮罩层用原生窗口仍然要做（省 12-15MB，而且把昂贵的 WPF 合成面限制在小尺寸窗口内、避免全屏 `WS_EX_LAYERED` 表面），但**不能指望它把内存降到 60MB**。

### 关键发现二：内存 ≈ 47MB 固定底 + 24 字节每 DIP²

> **单位澄清**：下表所有「窗口边长」都是 **DIP**（WPF 的 `Width`/`Height`），不是物理像素。
> 本机 175% 缩放下，740 DIP 对应的物理窗口是 **1295×1295**。
> 内存模型和 740 这个上限都在 DIP 单位下成立 —— 混用单位会得出错误的窗口尺寸。

轮盘窗口尺寸与内存的关系（任务管理器口径）：

| 窗口边长 | 600² | 700² | 800² | 900² | 1000² |
|---|---|---|---|---|---|
| 内存 | 56.0 | 59.6 | 61.1 | 67.4 | 71.6 MB |

另有一组对照：

| 配置 | 内存 |
|---|---|
| 1000² 逐像素透明 | 71.6 MB |
| 1000² **不透明**（对照） | 58.8 MB |
| 700² 逐像素透明 | 59.6 MB |

**逐像素透明只多花约 13MB，尺寸是主要杠杆。** 47MB 固定底是 .NET + WPF 运行时与渲染栈，无法通过改窗口属性绕开。

### 由此得出的设计约束

要落进 60MB，**轮盘窗口必须 ≤ 约 740×740**。这不是审美选择，是内存预算反推出来的硬约束：

```
窗口 740×740  →  内存 ≈ 59.8 MB
  ├─ 中心死区      r = 56   （占外径 16%，符合 15-25% 规范）
  ├─ 第一层环      r = [52, 200]
  └─ 第二层环      r = [206, 350]   （留 20px 余量给标签外溢与投影）
```

在 1755×1097 的屏幕上，这个轮盘直径 700px，占屏高 64%，足够大。

**⚠️ 但这 59.8MB 是在占位内容下测的**（一个椭圆 + 一行文字）。M2 加入真实扇区绘制、图标缓存、文字排版后内存会上涨，我的预估是**最终落在 65-75MB**。要压在 60MB 以内，需要在 M2 用这套 `--mem-probe` 反复回归，并在必要时取舍（图标按需加载、不缓存整盘位图）。

## 4. M0.5 视觉流水线 —— 方法被推翻，替代方案已验证

### 我在方案里说错了一件事

方案的第二节把「设计期浏览器原型 → `RenderTargetBitmap` 渲染成 PNG → 我读图 → 改 → 再渲染」作为保证视觉质量的核心机制。我提出它的理由是「模型看不见结果就无法做出好看的界面」。

**实际执行时发现：这个会话的模型不支持图像输入，图会被直接丢弃。我看不见自己渲染出的 PNG。** 那条回环对我不成立，方案里的承诺是我说错了。

### 替代方案：把图像问题变成数字，已验证有效

`tools/analyze-render.ps1` 对渲染结果做极坐标采样，输出纯文本：扇区中心/边界的颜色、半径剖面、外缘抗锯齿比例。它能抓住**几何与配色错误**（角度错、半径错、透明失效、颜色偏），抓不住**审美**。

这个替代方案立刻抓到了一个真实的设计缺陷：

**12 点方向原本落在扇区缝隙上，而不是扇区中心。** 沿 0° 做半径剖面，从 r=76 到 r=262 全是背景色 `#26000000`，而同半径下 22.5°/67.5° 等位置都是扇区填充色。根因是 `Distribute` 把 0° 当作第一个扇区的**起始边界**。

修复后复测（1° 精细扫描，r=150）：

```
   0°  #1F1F1F   ← 扇区填充 ✓
  22°  #000000   ← 缝隙
  67°  #000000   ← 缝隙
  90°  #1F1F1F   ← 扇区填充 ✓（正右方）
 112°  #000000   ← 缝隙
 157°  #000000   ← 缝隙
```

缝隙现在落在 22.5°、67.5°… 即相邻扇区中心的中点；**0° 与 90° 都是扇区中心**。契约已用 36 个单测锁住（`tests/WinQuick.Core.Tests/RadialLayoutTests.cs`）。

同时验证通过的部分：
- 中心死区填充 `#FF121212` 正确，不随扇区变化
- 外缘 600/600 采样点存在半透明过渡 → **逐像素 alpha 与抗锯齿确实生效**（不是硬切边）
- 圆盘之外全透明 `#00000000`

### 一个必须知道的细节

渲染出的颜色与指定值有细微偏差：指定 `#EB202020`，实际渲染成 `#EE1F1F1F`。这是合成器色彩/alpha 舍入造成的。**做 HTML ↔ WPF 保真度比对时不能用精确相等，必须带容差。**

### 分工调整

- **几何/配色/透明是否正确** → 我用 `analyze-render.ps1` 自检，不需要人
- **好不好看** → 需要你的眼睛。我会渲染候选方案成 PNG，由你挑选和提意见

## 5. 由此产生的方案修订

| 项 | 原方案 | 修订后 | 依据 |
|---|---|---|---|
| 遮罩层实现 | WPF Window + `WS_EX_LAYERED` + `LWA_ALPHA` | **原生 Win32 窗口**（已实现 `RawDimWindow`） | 省 12-15MB，且避免全屏 WPF 合成面 |

| 环半径 | R1=[72,260], R2=[268,430] | **R1=[52,200], R2=[206,350]** | 由窗口尺寸反推 |
| 默认热键 | Ctrl+Win+W | **不变，已验证可注册** | M0.4 实测 |
| Win+W 支持 | 待实测 | **可行，走 LL 钩子**（物理按键已复核确认） | M0.4 实测 |
| 视觉质量机制 | PNG 回环给我看 | **数值自检 + 你的眼睛** | 模型无图像输入能力 |
| 内存目标 | 60MB | **60MB 在占位内容下达标；真实内容预估 65-75MB** | M0.3 实测 |

### 新增的可用资产

- `WinQuick.exe --env` —— DPI-aware 环境报告
