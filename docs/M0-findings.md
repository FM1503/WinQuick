# M0 风险清零 —— 实测结论

日期：2026-09-14
构建：Release，`net10.0-windows`，win-x64
原始数据：[`artifacts/m0/`](../artifacts/m0/)

M0 的目的是把方案里三个「只能靠实测确定」的未知项变成数据。结论如下，其中**一项未达标**、**一项推翻了我自己提出的方法**。

## 1. 环境事实

| 项 | 值 |
|---|---|
| OS | Windows 11 家庭版中文版，Build **26200**（25H2） |
| 会话 | Console（非 RDP），真实硬件 |
| 机器 | LENOVO 21VR，AMD Radeon 780M 核显 |
| 内存 | 31.3 GB |
| 显示器 | **单屏 3072×1920 @ 168 DPI（175% 缩放）** —— 见下方纠正 |
| 渲染层级 | **Tier 2 完整硬件加速**，PS 2.0/3.0 可用 |
| 小组件 | 已安装，但 `HKLM\...\Dsh\AllowNewsAndInterests = 0`（已被策略关闭） |
| `ForegroundLockTimeout` | 200000（默认值，符合预期） |

**一个必须记住的陷阱**：最初用 Windows PowerShell 5.1 测显示器，得到「1755×1097 @ 96 DPI @ 100% 缩放」。那是**DPI-unaware 进程被系统虚拟化后的假值**。

真实值是 **3072×1920 @ 168 DPI（175% 缩放）** —— 3072/1755 = 1.75，完全吻合，是同一个物理屏幕的两种读法。

这不只是数字纠正，它改变了几个判断：
- **本机本身就是高 DPI 环境**，不是我原先以为的 100% 缩放。DPI 换算从「以后要考虑」变成「现在就必须对」。
- 真实像素量 **5.9M**，是 4K（8.3M）的 71%，而不是我先前以为的 1.9M。全屏合成的性能担忧比我估的更接近现实。
- `--env` 与 `--overlay-probe` 必须由声明 PerMonitorV2 的进程运行，这条不能省。

同理，`.ps1` 脚本必须以 **UTF-8 with BOM** 保存，否则 PowerShell 5.1 按 GBK 解码中文注释会破坏 here-string 解析；而且 PowerShell 通过管道输出中文用的是 GBK，拿 `grep` 匹配中文前要先 `iconv -f GBK -t UTF-8`。

**本机无法验证的两件事**（写进已知限制）：多显示器、混合 DPI 缩放。单屏 100% 缩放下，「一个 HWND 只能有一个 DPI」和跨屏 DPI 换算这两个坑都复现不了。

## 2. M0.4 热键实测 —— Win+W 的结论

网上证据互相矛盾（whkd #6 称 Win+W 无法拦截，AHK 社区称可以），所以必须实测。分两步取证据。

### 第一步：`RegisterHotKey` 试注册

| 组合 | 结果 |
|---|---|
| **Win+W** | **不可用，err=1409（已被占用）** |
| **Ctrl+Win+W** | **可用**（本方案默认值，已验证） |
| Alt+Win+W | 不可用 1409 |
| Shift+Win+W | 不可用 1409 |
| Win+A | 不可用 1409（符合预期：Win11 快速设置） |
| Win+F1 | 不可用 1409 |
| **Win+F13** | **可用** |
| Ctrl+Alt+Win+W | 可用 |
| Ctrl+Shift+W | 可用 |

**结论：`MOD_WIN` 没有被系统性拦截**（Win+F13 能注册成功），而是**真实的逐个按键被 shell 预留**。Win+W 即使小组件已被策略关闭，仍然注册不到 —— 说明占用来自 shell 而非小组件本身。

**可用规律：给 Win+组合再加一个修饰键（Ctrl）就能绕开 shell 的预留。** 这条规律要用在设置的热键选择器里：用户选了一个 1409 的组合时，直接建议「加上 Ctrl 试试」。

### 第二步：`WH_KEYBOARD_LL` 钩子能否截获 Win+W

注入 Win down / W down / W up / Win up 后，钩子观察到：

```
VK    方向   Win  Ctrl  Alt  Shift  注入
0x5B  down  Y    .     .    .      Y     ← Win 按下
0xFF  up    Y    .     .    .      Y     ← 本钩子注入的幽灵键（清残留状态）
0x57  down  Y    .     .    .      Y     ← W 按下，且 Win 处于按下状态
0x57  up    Y    .     .    .      Y     ← W 抬起
0x5B  up    .    .     .    .      Y     ← Win 抬起（被吞掉，不会弹开始菜单）
```

热键回调触发 1 次，吞键生效。

> **结论：Win+W 能被低级键盘钩子截获，吞键方案成立。** 用户若坚持用 Win+W，走钩子路径可以实现。

**✅ 已用物理按键复核**（`--hook-probe --interactive=15`，手动按 9 次 Win+W）：

```
0x5B  down  Y    ← Win 按下（物理，非注入）
0xFF  up    Y  Y ← 幽灵键清残留状态
0x57  down  Y    ← W 按下，Win 处于按下状态 → 匹配、吞键、触发回调
0x5B  up         ← Win 抬起（被吞，不弹开始菜单）
0x57  up         ← W 抬起（被吞）
```

9 次全部命中，热键回调触发 9 次。注入测试留下的不确定性消除。
小组件也不会弹出 —— 钩子返回 1 吞掉了按键，shell 根本没机会看到它。

**日志还暴露了一个此前不知道的行为**：幽灵键（`0xFF up`）出现在 `0x57 down` **之前**，但幽灵键是处理 W-down 时才发出的。原因是 **`SendInput` 在钩子回调内部会同步重入同一个钩子** —— 注入事件立刻又被回调处理一遍并入队，所以排在了当前事件前面。这里无害（不同 VK、回调足够短），但它意味着回调会嵌套执行、栈深度翻倍，**"回调里只做匹配和吞键"这条纪律比原先估计的更重要**。

## 3. M0.3 内存实测 —— **未达标**

### 最终数字（Release，稳态：托盘 + 预热窗口 + 隐藏遮罩）

| 口径 | 数值 |
|---|---|
| **任务管理器「活动的专用工作集」** | **71.8 MB** |
| 完整工作集（`WorkingSet64`） | 148.9 MB |
| 私有提交字节（`PrivateMemorySize64`） | 86.7 MB |
| GC 堆 | 2.1 MB（可忽略） |
| 线程 / 句柄 | 21 / 1485 |

**对照 60MB 目标：未达标。** 我在方案里写过不达标会如实汇报，这里是原始数据。

### 分阶段定位

| 阶段 | 任务管理器口径增量 |
|---|---|
| 应用刚启动（无窗口、无托盘） | 基线 ≈ 47 MB |
| + 托盘图标 | +6 MB |
| **+ 原生 Win32 遮罩窗口** | **+0.1 MB（几乎免费）** |
| **+ WPF 轮盘窗口（AllowsTransparency）** | **+50～90 MB** |

### 关键发现一：遮罩层必须用原生窗口，但省下的是 12-15MB 而非 61MB

最初的对照实验显示「WPF 版遮罩窗口消耗 61MB、原生版只消耗 0.1MB」，我一度以为找到了 61MB 的省法。**这个结论是错的** —— 换成原生遮罩后总内存只降了约 12-15MB。

原因：**WPF 的渲染栈是一次性公共开销**。在同时创建两个 WPF 窗口的测试里，这笔开销记在了先创建的遮罩窗口头上；去掉它之后，同样的开销转移到了轮盘窗口（+50MB → +91MB）。

正确的结论是：遮罩层用原生窗口仍然要做（省 12-15MB，而且把昂贵的 WPF 合成面限制在小尺寸窗口内、避免全屏 `WS_EX_LAYERED` 表面），但**不能指望它把内存降到 60MB**。

### 关键发现二：内存 ≈ 47MB 固定底 + 24 字节每 DIP²

> **单位澄清**：下表所有「窗口边长」都是 **DIP**（WPF 的 `Width`/`Height`），不是物理像素。
> 本机 175% 缩放下，740 DIP 对应的物理窗口是 **1295×1295**。
> 内存模型和 740 这个上限都在 DIP 单位下成立 —— 混用单位会得出错误的窗口尺寸。

轮盘窗口尺寸与内存的关系（任务管理器口径）：

| 窗口边长 | 600² | 700² | 800² | 900² | 1000² |
|---|---|---|---|---|---|
| 内存 | 56.0 | 59.6 | 61.1 | 67.4 | 71.6 MB |

另有一组对照：

| 配置 | 内存 |
|---|---|
| 1000² 逐像素透明 | 71.6 MB |
| 1000² **不透明**（对照） | 58.8 MB |
| 700² 逐像素透明 | 59.6 MB |

**逐像素透明只多花约 13MB，尺寸是主要杠杆。** 47MB 固定底是 .NET + WPF 运行时与渲染栈，无法通过改窗口属性绕开。

### 由此得出的设计约束

要落进 60MB，**轮盘窗口必须 ≤ 约 740×740**。这不是审美选择，是内存预算反推出来的硬约束：

```
窗口 740×740  →  内存 ≈ 59.8 MB
  ├─ 中心死区      r = 56   （占外径 16%，符合 15-25% 规范）
  ├─ 第一层环      r = [52, 200]
  └─ 第二层环      r = [206, 350]   （留 20px 余量给标签外溢与投影）
```

在 1755×1097 的屏幕上，这个轮盘直径 700px，占屏高 64%，足够大。

**⚠️ 但这 59.8MB 是在占位内容下测的**（一个椭圆 + 一行文字）。M2 加入真实扇区绘制、图标缓存、文字排版后内存会上涨，我的预估是**最终落在 65-75MB**。要压在 60MB 以内，需要在 M2 用这套 `--mem-probe` 反复回归，并在必要时取舍（图标按需加载、不缓存整盘位图）。

## 4. M0.5 视觉流水线 —— 方法被推翻，替代方案已验证

### 我在方案里说错了一件事

方案的第二节把「设计期浏览器原型 → `RenderTargetBitmap` 渲染成 PNG → 我读图 → 改 → 再渲染」作为保证视觉质量的核心机制。我提出它的理由是「模型看不见结果就无法做出好看的界面」。

**实际执行时发现：这个会话的模型不支持图像输入，图会被直接丢弃。我看不见自己渲染出的 PNG。** 那条回环对我不成立，方案里的承诺是我说错了。

### 替代方案：把图像问题变成数字，已验证有效

`tools/analyze-render.ps1` 对渲染结果做极坐标采样，输出纯文本：扇区中心/边界的颜色、半径剖面、外缘抗锯齿比例。它能抓住**几何与配色错误**（角度错、半径错、透明失效、颜色偏），抓不住**审美**。

这个替代方案立刻抓到了一个真实的设计缺陷：

**12 点方向原本落在扇区缝隙上，而不是扇区中心。** 沿 0° 做半径剖面，从 r=76 到 r=262 全是背景色 `#26000000`，而同半径下 22.5°/67.5° 等位置都是扇区填充色。根因是 `Distribute` 把 0° 当作第一个扇区的**起始边界**。

修复后复测（1° 精细扫描，r=150）：

```
   0°  #1F1F1F   ← 扇区填充 ✓
  22°  #000000   ← 缝隙
  67°  #000000   ← 缝隙
  90°  #1F1F1F   ← 扇区填充 ✓（正右方）
 112°  #000000   ← 缝隙
 157°  #000000   ← 缝隙
```

缝隙现在落在 22.5°、67.5°… 即相邻扇区中心的中点；**0° 与 90° 都是扇区中心**。契约已用 36 个单测锁住（`tests/WinQuick.Core.Tests/RadialLayoutTests.cs`）。

同时验证通过的部分：
- 中心死区填充 `#FF121212` 正确，不随扇区变化
- 外缘 600/600 采样点存在半透明过渡 → **逐像素 alpha 与抗锯齿确实生效**（不是硬切边）
- 圆盘之外全透明 `#00000000`

### 一个必须知道的细节

渲染出的颜色与指定值有细微偏差：指定 `#EB202020`，实际渲染成 `#EE1F1F1F`。这是合成器色彩/alpha 舍入造成的。**做 HTML ↔ WPF 保真度比对时不能用精确相等，必须带容差。**

### 分工调整

- **几何/配色/透明是否正确** → 我用 `analyze-render.ps1` 自检，不需要人
- **好不好看** → 需要你的眼睛。我会渲染候选方案成 PNG，由你挑选和提意见

## 8. 内存复查（2026-09-20）：一次被自己推翻了结论的经历

用户问"内存还能优化多少"。复查过程中我先得出一个**错误**结论，又用复测把它推翻。
两段都记下来 —— 错的推理路径比正确的结论更有参考价值。

### 8.1 我当时的错判

在**常驻进程**上反复触发菜单热重载（每次都会重建整棵视觉树）：

| 实验 | 私有提交字节 |
|---|---|
| 20 次重建（带图标） | 88.4 → 101.6（**+13.2MB**） |
| 20 次重建（图标换成占位图） | 102.5 → 102.4（**+0.0MB**） |

据此我断定："每次重建净留 ~0.66MB，且不归还，元凶是图标的 Fant 缩放缓存"，
并给出"把它清零"的优化承诺。**这个判据有漏洞**：被测进程里没法强制回收，
而我在最后一次重建后**只等了 2 秒**就读数 —— 那时回收还没发生。

### 8.2 复测（在能强制回收的探针进程里）

给 `--mem-probe` 加了"视觉树重建"阶段（用**产品同一条路径** `RadialRingView.Build(menu, reuse:)`，
前后各强制回收一次）：

| 阶段 | 私有(MB) | 增量 |
|---|---|---|
| 4. 稳态基线（轮盘已显示过） | 91.5 | |
| 5. 视觉树建好（含图标） | 97.5 | +6.0（一次性） |
| 6. 60 次重建后 | 110.3 | +12.8 |
| 7. 强制回收后 | 103.0 | −7.3 |
| 8. **长稳定后（再等几秒）** | **91.6** | **−11.2 → 回到基线** |

**结论反过来：不是泄漏。** 重建期间私有内存临时上浮（60 次约 +13MB），
**停止重建后几秒内自己回落到基线**。之前那个"常驻涨到 195–207MB"的观测，
正是我在它身上跑实验时读到的**峰值**，不是稳态。

**教训**：判断"泄漏还是还没回收"，必须（a）在**能强制回收**的进程里量，
（b）观测窗口要留到**回收之后**。少任何一条都会把"峰值"读成"泄漏"——
而这次两条我都违反了。

### 8.3 复查后的真实构成（Release，稳态）

| 项 | 数值 | 说明 |
|---|---|---|
| 应用启动（无窗口无托盘） | 19.8MB 私有 | CLR + WPF 装配 |
| + 托盘 | +5.0 | |
| + 原生遮罩 | +0.3 | 原生窗口那条省法早就做了 |
| + 轮盘窗口（分层窗口） | **+90.4 工作集 / +70.2 私有** | WPF 渲染栈 + 逐像素透明面 + GPU 侧 |
| 首次建树（含图标） | +27.1 工作集 / +6.0 私有 | 一次性 |
| 重建 churn | 每次约 +0.2 私有，**会回落** | 不需要为此改代码 |
| GC 堆 | 1.7–1.8MB | 可忽略 |

**能省的只有三条，且都要付代价**：① 窗口 740→700（约 −3.6MB，牺牲观感）；
② **空闲时销毁轮盘窗口、唤出时重建**（空闲私有可降约 45MB，代价是首次唤出 +30–60ms ——
现在靠"停放"把这段成本挪到了启动时）；③ 不用 WPF 画轮盘（换渲染栈）。
**基线 88–92MB 基本是这套架构的设计下限**，`60MB 目标`在 WPF + 分层窗口下本来就不可达
（§3 已如实记为未达标）。

### 8.4 顺带做掉的一处渲染开销（与内存无关）

图标原来让 WPF 在渲染时用 `BitmapScalingMode.HighQuality`（Fant 多级滤波）缩 —— 96px 源缩到
34 DIP × 屏幕缩放。改成**取图标时就预缩放到目标设备像素**（`ShellIcons.GetScaled`，
用 RenderTargetBitmap 烘焙一次并缓存），渲染端退到 1:1（`Linear`）。
收益是**每帧渲染不再做缩放**、图标位图从 96²（约 37KB×12）降到设备尺寸（约 14KB×12）。
**代价与判断**：烘焙版与 Fant 重采样的观感差异需要用户过一眼（两者在同尺寸下通常等价）。

## 9. 内存复查（第二轮）—— 结论再次被推翻，这次找到了真因并修掉

§8 里我写了"不是泄漏、会回落"。**那一版测量是无效的**：我让探针在一个**裸 Canvas** 上
重建 `RadialRingView` —— 那从不把内容渲染进分层窗口，所以完全测不到窗口侧的开销。
用户随后实测常驻停在 **~170MB 专用工作集**，逼我把仪器修对。

### 9.1 正确的仪器：真实轮盘窗口

探针改成建并显示一个**真的 `RadialWindow`**，再走产品里"改菜单"（`ApplyMenu`）那条路径重建：

| 阶段 | 工作集 | 私有(MB) | 增量 |
|---|---|---|---|
| 4. 稳态基线（合成窗口、无内容） | 158.6 | 90.4 | |
| 5. **真实轮盘窗口（分层，显示一次）** | 211.7 | 115.2 | +52 / **+24.8** |
| 6. 40 次重建后 | 239.8 | 141.4 | +28 / **+26.2** |
| 7. 强制回收后 | 225.9 | 127.9 | −13.5 |
| 8. 静置 9 秒 | 213.6 | **121.2** | 只回落 8.1，**回不到 90** |

**存在真累积：每次重建约 +0.65MB，强制回收也只回来一半。**
（这也解释了用户看到的 170MB：点皮肤/改菜单几十次就够。）

### 9.2 归因：不是图标，是"新几何"

先做的 A/B 是"把图标全部去掉（走占位图）再重建 40 次"：**+27.9MB**，与带图标的 +26.2MB 无差别
——所以与位图/图标无关。（我最初怀疑的 Fant 缩放缓存是错的；那条 18% 的改善只是噪声。）

再看我第一版"就地换材质"（不新建元素，但**仍重算 12 个扇区几何**）：+21.4MB，只降 18%。
把几何也去掉、**只改画刷**之后：**+0.5MB**。

**机制**：新的几何/元素 = 新的渲染内容 = **新的渲染数据**；
而只改已有元素的画刷 = 复用现有渲染数据。所以"重建"这件事本身（哪怕元素复用）
在**分层窗口里被渲染过**之后就会留下按次累积的渲染数据。

### 9.3 修掉它：换皮肤不再重建视觉树

`RadialRingView.TryApplySkinInPlace(form)`：把新规格的颜色/描边宽度/光晕**就地**套到已有元素上，
一个元素都不新建、几何也不重算。两条守卫保证功能等价（任一不满足就退回重建）：
① 光晕的有无变了（多/少一层几何）；② **环的几何参数**（死区/内外径/间隙/图标尺寸与比例）变了。
调用点在 `RadialWindow.RebuildForSkin`。

| 路径（各 40 次） | 私有内存增量 |
|---|---|
| 改菜单（`ApplyMenu`，结构真的变了 → 必须重建） | **+26.2MB** |
| **点皮肤（`RebuildForSkin` → 就地换材质）** | **+0.5MB** |

**换皮肤这条（真实使用里最主要的 churn）的累积清零了。**

### 9.4 还剩什么、以及两处顺带的修正

- **改菜单仍会重建**（±项数/改标签会动结构）：每次约 +0.65MB，属"低频且必要"。
  若哪天觉得碍事，方向是"内容变了但结构没变时也走就地更新"。
- **首次把轮盘窗口连同内容显示出来**：+52MB 工作集 / +24.8MB 私有（一次性，之后稳定）。
  这部分是 WPF 为分层窗口分配的渲染栈与表面，**不重建就不增长**。
- **`--mem-probe` 的"达标/未达标"判据不可靠**：它用的是工作集，而工作集会被系统大幅裁剪
  （同一份内容我测到 58 / 158 / 178 / 213MB），于是同一份代码能读出"达标"也能读出"未达标"。
  该判据应改用**私有提交字节**。这一条记在这里，未改。
- **图标预缩放**（`ShellIcons.GetScaled`）：与内存无关（见 9.2），但每帧渲染不再做缩放、
  图标位图从 96² 降到设备尺寸 —— 保留。

## 10. 内存复查（第三轮）：用户问"工具自身没有 GC 机制吗"

用户实测："功能正常，但操作后内存维持在 **194M**"（提交 213MB / 专用工作集 180MB / 句柄 1833，
而新启动时是提交 87MB / 句柄 1634 —— 也就是**操作后涨了约 126MB**）。

### 10.1 先回答 GC：有，但它管不到这里

- .NET 的 GC 在（workstation + 并发），**托管堆只有 1.7–1.9MB** —— 它一直很干净。
- 涨的是 **WPF 的非托管渲染数据 + 已提交的虚拟内存**：GC 完全不碰这部分；
  而且 .NET 即使回收了托管对象，**也不会立刻把已提交的页还给系统**（提交量只增不减是常态）。
- 强制回收有效但只回收一部分：实测 40 次重建后 `GC.Collect(Aggressive) + WaitForPendingFinalizers ×3`
  只拿回约一半（−13.5MB / −26MB）。
- 所以"加个 GC"不是解法 —— 解法是**别产生新的渲染数据**（§9.3/§10.2）。

### 10.2 上一轮修复漏掉的两条 churn（都已修）

§9.3 修的是**轮盘**的重建。但真实使用里还有两条同样机制（"新元素 = 新渲染数据"）的路径：

| 路径 | 原来怎么做 | 现在怎么做 |
|---|---|---|
| **皮肤面板的列表** | 每点一次皮肤 `BuildLists()` **清空重建 6+4 行**（每行含 Border/TextBlock/色板） | `UpdateSelectionVisuals()`：只重刷若干 Border 的画刷与文字色，**不新建元素** |
| **皮肤改了 ring2Inner 的档**（霓虹/Material） | `SameRingGeometry` 比较了 ring2Inner → 判定"几何变了"→ **退回整树重建** | 不再比较 ring2Inner/ring2Outer —— 那两条只影响**子环**，而子环几何是**展开那一刻**现算的（ChildArc 的写入点），一级环的现有几何不受影响 |

也就是说：**点皮肤这条路（面板 + 轮盘）现在全都不产生新元素**。

### 10.3 仍然会重建、且是"该重建"的

- **改菜单**（增删项/改标签）：结构真的变了，必须重建 —— 每次约 +0.65MB。
  低频、且这类操作本身就该付代价。若将来仍嫌它累积，方向是"结构没变时也走就地更新"。
- **换形态**（饼形↔圆角↔花瓣↔刻度盘）：几何真的不同，必须重建。

### 10.4 如果要让"静置时的数字"更低，只剩一条大取舍

`--mem-probe` 的稳态私有内存约 87–92MB，其中 ~47MB 是 WPF+CLR 固定底、其余主要是
**分层窗口的渲染栈与表面**（首次显示带内容的轮盘 +24.8MB 私有 / +52MB 工作集，之后稳定）。
要把它降下来只有一条路：**空闲时销毁轮盘窗口、唤出时重建**（约 −45MB 静置占用），
代价是首次唤出 +30–60ms（现在靠"停放"把这段成本挪到了启动时）。**这是设计取舍，等用户拍板。**

## 11. 自动空闲清理（用户要求的功能）

用户："轮盘工具能不能增加一个内存 GC 机制，关闭轮盘到后台常驻时自动清理自身占用的内存"
（实测：唤出再关闭后仍有 ~140MB 常驻；用 MEM REDUCT 清理后未唤出时只有 **1.4MB**）。

### 11.1 那 1.4MB 是什么机制

MEM REDUCT 做的是 **`SetProcessWorkingSetSizeEx(hProcess, -1, -1, 0)`**：让系统把本进程的页
换到 **standby（备用）列表**。所以：

- **工作集**（任务管理器"内存"列）大幅下降 → 这就是用户看到的 1.4MB；
- **提交量（commit）不变** —— 内存没有被"释放"，只是不再驻留物理内存；
  standby 页是"缓存"而非法"已用"，系统随时可以回收它们。
- **代价**：下次唤出要重新缺页（soft fault）。页在 standby 里通常**不触发磁盘读**，
  但首次唤出那几帧会慢一点。

### 11.2 实现（`Diagnostics/MemoryTrim.cs` + 覆盖层生命周期）

1. **顺序很重要**：先 `GC.Collect(Aggressive, compacting) + WaitForPendingFinalizers` ×2
   （WPF 的非托管渲染数据挂在终结器上），**再**交工作集给系统 ——
   反过来做的话，刚换出的页会因为 GC 触碰对象又立刻回来。
2. **触发点**：`OverlayController.FinishHide()`（真正进入休眠之后）起一个延迟定时器；
   **`Show()` 里第一件事就是把它停掉** —— 唤醒时若还在等清理，那一次清理既白做又拖慢唤出。
3. **延迟**：`interaction.idleTrimDelayMs`（令牌，默认 **8000**，范围 0~120000，0 = 不清理）。
   延迟是为了覆盖"关掉马上又打开"这个常见情形：那几秒内不会清理。
4. **开关**：`behavior.trimMemoryWhenIdle`（默认开；关掉它唯一的理由是"不能接受下次唤出慢一点点"）。
5. **不清理启动后的第一次**：预热（Prewarm）刻意让窗口保持热态，第一次唤出不该为省内存变慢。
6. **失败不影响功能**：拿不到句柄/调用失败只写崩溃日志，不影响使用。

### 11.3 怎么验证（分工：用户看数字，我看日志）

- **用户**：唤出 → 关闭 → 等约 10 秒 → 任务管理器的内存列应当从一百多 MB 掉到几 MB；
  然后**再唤出一次**，看首次出现是否与以前一样跟手（这是这条功能唯一的代价）。
- **我**：若数字没掉，查崩溃日志有没有"空闲内存清理失败"（那是唯一会留下痕迹的失败路径）。

### 11.4 一条排查记录（避免下次误判）

复习内存时崩溃日志里出现过
`Cannot set Visibility or call Show ... after a Window has closed`（栈在热键→`Show()`）。
那条**不是产品的缺陷**，是我跑的 `--overlay-probe` 收尾时自己的问题：
探针进程里也建了一套 `ResidentHost` + 热键，`Application.Shutdown` 之后热键又到达一次。
判据：**日志里的 PID 属于探针进程**（当前常驻 PID 从不出现在日志里）。
