## 2. 点击扇区：区分三种失败可能

「点击没反应」可能是三件事之一，必须分清才能对症：

| 可能 | 验证方式 | 结果 |
|---|---|---|
| ① 点击事件没被检测到 | `--overlay-probe`：把光标移到扇区中心、投递按键消息、核对 `SectorActivated` | **正常**，命中索引 0 与几何计算一致 |
| ② 检测到了但没人执行 | 代码走查 | **这就是问题所在** —— 当时没有动作执行层 |
| ③ 执行了但启动失败 | `--action-probe`：启动一个会留下可核对痕迹的子进程 | **正常** |

① 与 ③ 都是好的，所以问题确实只在 ②。

### 动作执行层（新）

`Actions/ActionExecutor.cs`，支持四种动作类型：

| 类型 | 用途 |
|---|---|
| `launch` | 启动程序，可带参数与工作目录 |
| `open` | 用默认程序打开文件或文件夹 |
| `url` | 用默认浏览器打开网址（自动补 `https://`） |
| `shell` | 交给资源管理器解释 shell 路径，**UWP 应用走这条** |

三条刻意的设计：

1. **不阻塞调用方。** 启动进程可能耗时（UAC 提权、磁盘慢），而调用它的是覆盖层的关闭路径。
   放到线程池上跑，失败通过回调报告。
2. **先收界面、再执行动作。** 反过来新程序窗口会先冒出来再被覆盖层挡住，观感像闪屏。
   而且 `Hide()` 会立刻归还前台焦点，这是「按下就立刻响应」的前提。
3. **失败必须让用户看见。** 静默失败会被当成程序坏了，而路径不存在、权限不足恰恰最容易发生。
   失败走托盘气泡 + 崩溃日志双写。

**没有动作的项必须明确报错**，不能静默无事发生——后者会被当成程序坏了。
实测输出：`「有子菜单的项」还没有配置动作`。

## 3. 文字：三级策略，从最可读到最不得已

根因其实是那个 `LabelMaxChars = 6` 的**硬截断**——`PowerShell` 被砍成 `PowerSh`。

现在的处理顺序：

1. **原样显示** —— 放得下就不动它（当前菜单 8 项全部落在这一级）
2. **自动缩小字号** —— 缩到下限 11px 为止。缩到 11px 仍比滚动可读，因为滚动文字一眼看不完，
   而菜单是「看一眼就要点」的东西
3. **悬停时滚动** —— 只在前两级都放不下时启用，且**只在悬停时滚**

为什么不做成无条件滚动：饼菜单的使用节奏是「看准了立刻点」，滚动的文字在那 200ms 里读不完，
反而比缩小字号更难用。静止状态下所有标签一起滚动也会很吵。
滚动用**往返**而不是单向循环——单向循环会让文字跳回起点，观感像闪烁。

文字位置同时内移：`labelRadiusRatio` 0.78 → 0.62（半径 168 → 145）。
标签可用宽度取该半径处扇区的**弦长**（文字是直的，能用的就是弦那么宽）扣掉两侧缝隙，8 扇区下约 99 DIP。

### 兜底逻辑必须被验证过

常规情况下 0 项需要滚动、0 项被缩小——这意味着两条兜底逻辑**没被触发过**。
未经验证的兜底代码等于没有，所以加了 `--stress-labels` 压力测试：

| 场景 | 需要滚动 | 自动缩小 | 最大溢出 |
|---|---|---|---|
| 常规标签 | 0 / 8 | 0 / 8 | 0 px |
| 压力标签（追加长后缀） | **8 / 8** | **8 / 8** | **76.9 px** |

两级兜底都确实会生效。

## 4b. 第三轮反馈：左右两侧重叠 + 悬停形变

### 问题一：3 点/9 点方向文字与图标重叠

**根因（算出来的，不是猜的）**：标签是**轴对齐矩形**，而扇区中心线在不同方向性质不同 ——
- 在 3 点/9 点方向，扇区中心线水平，落在**半径方向**上的是标签的**宽度**（最宽 99px）
- 在 12 点/6 点方向，落在半径方向上的是标签的**高度**（约 19px）

所以只有左右两侧会撞。原配置：图标 34px 在 r=102、标签在 r=145，径向间隔只有 43px，
而需要 `图标半宽 17 + 标签半宽 49.5 = 66.5px` 才不重叠。

**修复分两步**：
1. **标签折成最多两行** —— 宽度直接减半，这是关键（中文可在任意汉字间断行）
2. 调整图标与标签的径向位置：图标 34→30px 移到 r≈91，标签移到 r≈150，间隔增至 59px

可用宽度不再只由扇区弦长决定，而是取两者的更严格者：

```
LabelMaxHalfWidth = min(
    径向间隔 - 图标半宽 - 余量,          // 不压到图标（3/9 点方向是最坏情况）
    扇区在标签半径处的弦长 / 2 - 缝隙     // 不越出自己的扇区
)
```

8 扇区下算出 80.1 DIP。这条约束已写进 `DesignTokens.Validate()` 并由单测锁住
（`Validate_CatchesIconLabelCollision` 会构造一个图标贴着标签的配置并断言被拦下）。

**结果**：常规标签 8/8 折行、0 需滚动、0 需缩小；压力标签 8/8 折行 + 8/8 自动缩小。
折行一次解决了「重叠」与「显示不全」两个问题，滚动退化为真正的最后手段
（只有不可断行的超长单词才会用到）。

### 问题二：悬停扇区向外延伸的形变动画

**为什么用逐帧驱动几何，而不是挂一个 ScaleTransform**：缩放是**以某中心等比放大**，
会把扇区内缘也推向圆心、让它离开中心死区。而「向外延伸」的正确形态是
**内缘不动、外缘外扩** —— 扇区像抽屉一样被拉出来。WPF 的几何不是可动画属性，
也不支持对 Path 做非等比的径向变形，所以只能逐帧重建几何。

代价可控：同一时刻最多两个扇区在变化（新悬停的鼓出、旧悬停的缩回），
每个扇区每帧重建一次小几何；静止时**整条渲染回调会断开**，不产生任何逐帧开销。

为此在 Core 里新增了 `CubicBezier` 求值器 —— WPF 的 `KeySpline` 能在声明式动画里
精确使用曲线，但**不提供求值接口**，而逐帧驱动的动效需要自己算缓动值。

**验证**：悬停扇区外缘从 r=200 扩到 **r=210~212**（径向剖面实测），
外侧从 213 起透明。静止后几何还原为冻结的基准几何。

### 顺带修掉的两处自己的问题

**一、逐帧回调的泄漏隐患。** 形变动画挂的是 `CompositionTarget.Rendering`，
覆盖层隐藏时若不复位，回调会继续逐帧跑 —— 变成看不见的 CPU 占用。
已在 `OverlayController.FinishHide()` 里接了 `ResetInteraction()`。

**二、测试里的参考值是凭印象写的。** `CubicBezierTests` 第一版我随手填了
`0.94 / 0.66 / 0.31` 作为三条曲线在 p=0.5 处的值，**全错**。手算：
`cubic-bezier(0,0,0,1)` 的 x(t)=t³，解 x=0.5 得 t=0.7937，y=3(1-t)t²+t³=**0.890**。
测试立刻抓到了。已改为算出的值并注明「这几个期望值是算出来的，不是凭印象写的」。

## 4c. 环 2 子菜单与 hover 状态机

### 状态机抽成纯逻辑

子菜单的悬停规则涉及两个延迟、斜向缓冲、以及「指针移进子弧后不该收起」这类状态依赖。
靠人工反复点击验证几乎不可行 —— 要精确控制 199ms 与 201ms 这种边界、
还要模拟"斜着移向子弧"的轨迹。所以状态机（`Core/Interaction/SubmenuHoverMachine.cs`）
把时钟改成外部注入，用假时钟把边界一次测清。

**这条决定立刻换来了回报。** 状态机单测抓到一个真 bug：
请求收起旧子弧之后，每次指针轮询都会把新子弧的展开计时重置，
结果是**指针停在新父扇区上不动时，新子菜单永远不会展开**。
这种 bug 靠手点几乎不可能定位 —— 现象只是"有时候不弹"，而"有时候"取决于指针是否恰好动了一下。

规则与依据：
- 展开 200ms / 收起 350ms：收起必须明显慢于展开，否则指针掠过扇区边缘时子弧会闪
- 另一个父扇区有子项时，旧的子弧**立即**收起而不是走 350ms 延迟 ——
  同时只能显示一个子弧，让旧的滞留而新的 200ms 后就出现，两个子弧会重叠成一团
- 斜向缓冲：指针从父扇区斜着移向子弧的途中会越过缝隙与相邻扇区，
  那些落点通过单独的 `HitZone.ChildArcGap` 识别为"仍在子弧内"，不触发收起

轮询而不是"只在指针移动时判断"：延迟的推进需要时间，指针停住不动时若只在移动时才检查，
子菜单就永远不会展开。所以窗口可见期间以 25ms 轮询喂入当前指针位置，隐藏时停止。

### 子弧几何与命中

子弧画在父扇区外侧的环带 [206, 350] 上，以父扇区中心角为中线，跨度 90°
（会被 `childMinSectorDegrees × 子项数` 顶大 —— 12 扇区父级下 90° 里塞 8 个子项只剩 11°，点不中）。
父级保持可见，子项与父项方向一致 —— 方向一致是第二层能形成肌肉记忆的前提。

子弧的角度跨度可能**超出父扇区**（2 个子项时是 90°，而父扇区只有 45°），
所以命中测试按子弧自己的跨度判断，不是按父扇区的。

展开动画：子扇区从内缘"长"到外缘（起始时内外半径重合、退化成没有厚度的弧），
167ms + `cubic-bezier(0.55,0.55,0,1)`（官方规范里「已有元素点对点」那一档）。

### 中心与 Esc = 返回上一层

有子弧展开时，点中心或按 Esc 先收子弧（返回上一层），没有子弧时才关闭整棵菜单。
这与饼菜单的两条既有语义都吻合：Don Hopkins 的规范里中心就是取消，
Kurtenbach 的标记菜单里指向子菜单中心则是返回上一级。

### 验证

| 项 | 结果 |
|---|---|
| 几何（沿子项中心 292.5° / 337.5° 剖面） | 扇区填充从 **r≈207 延续到 r≈349**，正好是环带 [206,350]；350–351 抗锯齿过渡，352 起全透明 |
| 展开路径（覆盖层探针） | 子弧已展开、进度 1、渲染出 2 个子项 |
| 收起路径 | 收起后不再可见；视觉树无残留（29 → 35 → 29，二轮仍 29） |
| 子环图标 | PNG 像素级 2/2 彩色 |

**分析脚本的使用陷阱**：验证子弧时不要把剖面角度设成子弧的**中心角** ——
子项为偶数个时那里正好是两个子项之间的缝隙，沿它剖下去会看到一片透明，
很容易被误判成"子弧没画出来"（我就这么误判过一次）。
已把这个提示写进脚本输出。

### 又一次被验证机制抓到的问题

`--overlay-probe` 的收起核对报出「收起后仍可见」。
根因是收起动画走完时只拆了视觉、没清"子弧存在"这个状态位。
后果不只是显示问题：**Esc 与点中心会去执行"返回上一层"而不是退出，
表现为第一次按没反应、要按两次**。已改为走完整善后。

## 4d. 第四轮反馈：子环压住鼓出扇区 + 子环图标缺失

### 问题一：子环与鼓出的扇区重叠

**根因是数值之间缺少约束**：父扇区悬停鼓出 12px，外缘从 200 变 212；
而子环带内缘是 **206** —— 212 > 206，重叠 6px。这两个数值当初各自独立定，
没人检查它们的关系。

修复：子环内缘 206 → **218**（环一外缘 200 + 鼓出 12 + 余量 6），
并把这条关系写进 `DesignTokens.Validate()`：

```
ring2Inner >= ring1Outer + hoverBulgePx + 余量
```

单测 `SecondRing_ClearsTheHoverBulge` 与 `Validate_CatchesSecondRingOverlappingTheBulge`
锁住它。**这类"两个数值各自合理、放在一起不合理"的问题靠看代码看不出来，
只能靠显式的约束检查。**

**几何验证**（沿父扇区 7 内部的两个方向剖面）：

```
r=212..213   #B6D8F2  A=231   ← 鼓出扇区的外缘（含抗锯齿）
r=214..217   #000000  A=0     ← 透明间隙
r=220..349   #1F1F1F  A=235   ← 子环扇区
```

不再相接。

### 问题二：子环只有文字没有图标

**根因是"对象建好但没接进视觉树"**：`AddChildIcon` 返回了 Image 对象，
调用方也把它收进了 `_childIcons` 列表，但**没有任何一行把它加进画布**。
对象模型里一切看起来都正常（`RenderedIconCount` 之类都会报对），只是屏幕上不出现。

同类错误在本项目里已经出现过两次（第一次是遮罩窗口的可见性状态与 Win32 实际状态脱节）。
两次的共同点都是**只看代码或只看自己的状态变量都发现不了，必须去核对真实产物**。

修复：补上 `Root.Children.Add(image)`；顺带补上"取不到图标时画首字占位"的分支，
与第一层环行为一致。

**验证**（沿子项中心角采样图标区域，按饱和度区分真图标与灰度占位）：

```
位置 0  角度  292.5°  最大饱和度  14%  -> 彩色（真图标）
位置 1  角度  337.5°  最大饱和度  67%  -> 彩色（真图标）
彩色 2 / 2，无彩色 0
```

### 顺带修掉的第三处：占位图的视觉树残留

顺着上面那条分支发现，占位图（圆 + 首字）由 `AddPlaceholder` 直接加进画布、
**没有登记**，所以收起时不会被移除 —— 每展开一次残留一份。
对当前默认菜单不可见（子项都有图标），但用户配的子项没图标时就会累积。

修复：`AddPlaceholder` 支持把创建出来的图形收进一个列表，子弧收起时一并移除。

**新增的验证手段：视觉树泄漏计数。**
`--overlay-probe` 现在会记录画布直接子元素数量，走两轮展开/收起：

```
展开前 29  →  展开后 35  →  收起后 29
第二轮回合后 29
```

「每次收起都留下几个元素」这类泄漏在性能劣化前完全不可见，
只有靠这种结构计数才抓得住。

## 5. ~~UWP 缺口~~（已解决，见 §7）

Win11 上「设置」「计算器」「画图」「照片」等常用应用**没有可执行文件**，
既不能用文件路径取图标，也不能用文件路径启动。实测确认
`System32\SystemSettings.exe` 与 `System32\mspaint.exe` 都已不存在。

`MenuAction.Uwp(aumid)` 与 `shell` 动作类型已经就绪（实现为
`explorer.exe shell:AppsFolder\<AUMID>`），但**还没有获取 AUMID 的途径**——
需要枚举 `shell:AppsFolder`（`IShellFolder`），这是一块独立的工作。
在那之前，用户配不进这些应用。这是 M4 配置系统之前要补的。

```
src\WinQuick.App\bin\Release\net10.0-windows\WinQuick.exe
```

## 7. UWP / 商店应用支持（原 §5 的缺口已补上）

### 为什么必须走 shell 枚举

实测确认 Win11 上「设置」「计算器」「画图」「照片」**都没有可执行文件**
（`System32\SystemSettings.exe` 与 `mspaint.exe` 都不存在）。它们既不能用文件路径取图标，
也不能用文件路径启动 —— 唯一标识是 AppUserModelId，只能从 `shell:AppsFolder` 枚举出来。

### 实现上规避的一个风险

`IShellItem2::GetString` 能直接读属性，但它的方法很多，而 **COM 接口的方法顺序一旦写错
不会报错，只会静默读到垃圾数据甚至崩溃**。我没有可靠的一手依据记住 IShellItem2 vtable 的
尾部顺序，所以只用 `IShellItem`（5 个方法，顺序确定），靠 `GetDisplayName` 的不同
`SIGDN` 取值去拿 AUMID，先用探针把各种取值都打出来实测确认，而不是凭记忆猜。

结果：**枚举到 339 个条目，其中 28 个是 UWP**。AUMID 形如
`Microsoft.WindowsCalculator_8wekyb3d8bbwe!App`，传统桌面程序的"AUMID"则是它的完整文件路径
（例如 `C:\MentorGraphics\...\LMTOOLS.EXE`），两者都能作为启动目标。

### 按 AUMID 而不是显示名定位

默认菜单用 **AUMID 前缀**查找内置应用：

```
Microsoft.WindowsTerminal_   Microsoft.WindowsCalculator_   Microsoft.Paint_
Microsoft.Windows.Photos_    windows.immersivecontrolpanel_（设置）
```

原因：**AUMID 与系统语言无关**（中文系统与英文系统下都是同一串），而显示名会变
（中文叫「计算器」、英文叫「Calculator」）。显示名交给 shell 提供，自动跟随系统语言。
找不到就跳过该项 —— 用户没装某个商店应用时，菜单里出现点不动的死项比少一项更糟。

### 验证

| 项 | 结果 |
|---|---|
| 枚举 | 339 条目 / 28 个 UWP |
| UWP 图标 | 走 `shell:AppsFolder\<AUMID>` 取到 96×96 |
| **UWP 启动** | **端到端验证通过**：计算器进程 0 → 1 出现，随后自动关闭不留窗口 |
| 默认菜单 | 8 项（顶层固定 8，符合 CHI'93 的错误率拐点），其中 5 项是 UWP |
| 默认菜单图标 | 8/8 全部取到 |

顶层固定 8 项是有依据的：CHI'93 实测 8 扇区是错误率拐点，Kando 官方经验值也是 8、
绝不超过 12。8 的另一个好处是「上 / 右上 / 右 / …」的钟面直觉成立，
而奇数个扇区会让每项的角度都变得不好记。

### 顺带修掉的验证工具缺陷

图标核对原本只按**饱和度**判定，结果对 Windows Terminal 报出"无彩色（占位或无内容）"——
它的图标是黑底白字的**单色**图标，饱和度天然为 0。这是假阴性。

改为以**内容像素数**为主判据（检测图标区域有多少像素偏离扇区填充色），
饱和度降为辅助信息：

```
位置 1  角度 45°  内容像素 519  最大饱和度  0%  -> 有内容但无彩色 —— 单色图标
位置 7  角度 315° 内容像素 109  最大饱和度  0%  -> 占位图（内容像素数也明显更小）
```

「几乎无内容」才是能确定问题的信号，它对应的正是"图形对象建好了但没挂到视觉树"
那个真 bug。单色图标不该被判成故障。

### 新增诊断命令

```
WinQuick.exe --apps-probe            枚举 shell:AppsFolder，核对 AUMID 与图标
WinQuick.exe --action-probe --uwp    实际启动一个 UWP 应用并自动关闭（默认不做，会弹窗）
```

## 启动程序时的工作目录（用户报"部分软件在工具里打不开"）

**症状**：某些程序（用户举的例子是 OBS）外部双击正常，从轮盘打开就报错。

**查下来先排除了一条**：不是"没把工作目录交给子进程"。受控实验（自建一条快捷方式，
目标是复制到临时目录的 cmd.exe，让它把自己的工作目录写进文件）显示：
用我们现在的调用方式打开 `.lnk` 时，**shell 会把快捷方式自带的「起始位置」交给子进程**。
所以"打开快捷方式"这条路本身是对的。

**但确实有一个真实差距**：开始菜单永远带「起始位置」（快捷方式里存着），
而我们**直接存 exe 路径**时没有这个信息 —— 子进程会继承**我们**的目录。
不少程序要求从自己目录启动（OBS 就是），否则报错。这正好是"外部正常、工具里报错"的形状。

**修法**：直接启动 exe 且未指定工作目录时，兜底为**目标自己所在的目录**。
对 `.lnk` / `.url` **不这样兜底** —— 那会把快捷方式自己的「起始位置」覆盖成
快捷方式所在的文件夹（比如桌面），反而更糟；那两种交给 shell 解析。

**验证**（`--action-probe` 新增一节）：把 cmd.exe 复制到临时目录，用 `ActionExecutor`
启动它并让它写出自己的工作目录，断言等于那个临时目录。用副本而不是 System32 里的原件，
是因为后者的目录恰好是默认值 —— 那样测了也分不出"兜底生效了"还是"本来就是那样"。

## 排查过程中的一次自我污染（记录教训）

为了验证启动方式，我反复用 `Stop-Process -Force` 关掉 OBS。OBS 遇到非正常退出会在
`%APPDATA%\obs-studio\.sentinel` 留一个标记，之后**每次**启动都弹"检测到 OBS Studio 崩溃"。
于是我的复现实验里看到的"OBS 报错"，**是我自己造成的**，不是用户的问题。

那个对话框的标题是我枚举 OBS 进程的顶层窗口读到的（`EnumWindows` + `GetWindowText`），
而不是靠肉眼 —— 白边框那次也是靠把截图降采样成字符画才"读"到。
清掉标记后，从我们这条 `.lnk` 启动 OBS 完全正常（窗口标题 `OBS 32.2.1 - 配置文件…`，日志 174 行）。

**教训**：验证"启动外部程序"这类行为时，用强制结束会改变被验证对象的状态。
要么用受控替身（这次最后就是复制 cmd.exe 到临时目录），要么在结束前恢复现场。
