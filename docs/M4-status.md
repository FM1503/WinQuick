## 1. 两份配置的分工

| 文件 | 位置 | 谁定 | 内容 |
|---|---|---|---|
| `config.json` | `%APPDATA%\WinQuick\` | **用户偏好** | 热键、遮罩透明度、悬停延迟、是否动画、自启（也可由设置界面改） |
| `menus.json` | 同上 | **用户内容** | 菜单项、图标、动作、子菜单、角度 |
| `design/tokens.json` | 仓库内，随程序嵌入 | **设计基线** | 配色、半径、时长、缓动曲线 |

**这个分层是刻意的。** `config.json` 里所有可选的旋钮默认值都是 `null`，含义是
「沿用设计基线」，只有显式设了才覆盖。原因是**同一个值不能有两个来源** ——
两处都能改同一个值时，改了 A 没改 B 会静默分叉，而分叉要到界面看起来不对才发现。
这正是我在 M2 建立 `tokens.json` 单一真源时规避的问题，配置系统不能把它重新引入。

## 2. 三条刻意的行为

### 配置写错绝不导致打不开

手写 JSON 出错太容易（少个逗号、多个括号）。最简单的失败方式是"改错配置就再也启动不了"。
所以解析或校验失败时**保留上一份有效配置**，在托盘气泡与日志里报告问题，程序继续运行。

实测验证了四种坏法，全部正确保留并给出可读错误：

| 坏法 | 报出的问题 |
|---|---|
| 语法错误（截断的 JSON） | `menus.json 解析失败：Expected end of string… | LineNumber: 74 | BytePositionInLine: 42` |
| 角度未严格递增 | `items[2]（丙）的 angle=45 未严格大于前一项的 90；显式角度必须严格递增。可以省略 angle 让程序均匀分布。` |
| 热键无法解析 | `hotkey「Ctrl+NotAKey」无法解析：无法识别的主键「NotAKey」` |
| 同一项既有子项又有动作 | `items[0]（甲）同时配了子项和动作 —— 点击时无法确定该展开还是执行` |

错误信息都带**位置**和**怎么改**，而不是一句"解析失败"让用户去猜。

### 首次运行写出可直接编辑的配置

- `config.json` 是**带注释的模板**（解析器支持 JSONC）。注释让"这个字段是干什么的"
  直接在文件里看到，不必翻文档。
- `menus.json` 直接序列化**当前装配好的菜单** —— 用户拿到的是一份填好真实路径、
  可以直接改的配置，而不是空模板。

### 热重载带防抖

编辑器保存一个文件经常连续触发多次变更事件（先清空再写入），不做防抖会读到写了一半的
文件并报一堆假错误。400ms 静默后才真正重载。

菜单变更时会**重建轮盘窗口**（视觉树是构造时用菜单建立的），替换后立刻预热，
所以随后的首次唤出仍然不慢。热键变更会重新注册。

## 4. 排查中发现的三个问题

### 一、我自己引入的标签回归

生成出来的菜单是 `explorer.exe / 终端 / notepad.exe / 计算器 / 设置 / 画图 / Taskmgr.exe / 开发工具`
—— 中文和文件名混在一起。原因是我创建 `DefaultMenu.cs` 时用了
`Path.GetFileNameWithoutExtension` 当标签，而 UWP 项的标签来自 shell，两者来源不一致。

修复过程中试错了两次，值得记下来：

1. **`SHGetFileInfo(SHGFI_DISPLAYNAME)`** —— 返回的是**带扩展名的文件名**。
   那只是资源管理器的"显示扩展名"开关在起作用，不是友好名。
2. **文件名去扩展名** —— 得到 "notepad"、"Taskmgr"。
3. **正确答案：可执行文件的版本资源 `FileDescription`** ——
   任务管理器的「描述」列、开始菜单里的名字都是它。实测值：
   `notepad.exe → 记事本`、`explorer.exe → Windows 资源管理器`、`regedit.exe → 注册表编辑器`。

顺带发现很多系统组件都以 "Windows " 开头（"Windows 资源管理器"、"Windows 命令处理程序"），
在 80px 宽的标签里会折得难看，所以读取时去掉这个前缀。

最终：`资源管理器 / 终端 / 记事本 / 计算器 / 设置 / 画图 / 任务管理器 / 开发工具`，
全部来自系统资源、自动跟随语言，代码里没有硬编码任何标签。

### 二、热重载"失败"其实是我的测试数据错了

第一次跑热重载验证报"未生效"。查日志才发现**文件监视触发了、防抖触发了、重载也跑了**，
只是我测试数据里的 JSON 转义写错了一层（`\W` 是非法转义），配置被**正确地拒绝**了
并保留了上一份 —— 也就是说这次"失败"顺带验证了容错路径在真实文件监视下也生效。

教训：探针只报"未生效"是不够的，**必须把它观察到的原因一并显示出来**，
否则一次测试数据的错误会被误读成功能缺陷。已改成同时输出重载报出的问题。

### 三、生成的 JSON 键名风格不一致

序列化默认输出 PascalCase（`Version` / `Menus` / `Label`），能读回来（大小写不敏感），
但和 `config.json`、和文档里写的 camelCase 不一致，会让人以为两份配置是两种格式。
已加 `PropertyNamingPolicy = CamelCase`，并关闭非 ASCII 转义 ——
中文标签被转成 Unicode 转义序列后手写编辑会非常难受。

## 5. 一条我写错又改回来的校验

我最初把 `hoverOpenDelayMs < 150` 也当成非法配置拦下。后来意识到那是**越权**：
研究结论是「低于 150ms 容易误展开」，那是给**默认值**的建议，不是硬约束。
用户明确要"几乎无延迟"是合理选择。

现在的分界：**硬约束只有两条**（不能为负、收起必须慢于展开），
其余建议写进配置模板的注释里让用户自己权衡。

（这和之前贝塞尔参考值那次是同一类错误：断言了一件自己没想清楚的事。
两次都是测试把它抓了出来。）

## 6. 设置界面

托盘菜单 →「设置…」打开。存在的**首要理由不是"少改 JSON"，而是热键的实时测试**：
热键是唯一的入口，而 Windows 上大量组合被系统或其他程序占用（实测 Win+W、Win+A 都返回 1409）。
用户需要敲一个组合就立刻知道能不能用，而不是改完配置、重启、发现没反应、再猜哪里错了。

| 功能 | 说明 |
|---|---|
| 热键录制 | 点输入框后按组合键，实时显示规范化结果（如 `Ctrl+Win+W`） |
| 热键测试 | 「应用」试注册，报可用 / 被占用（1409）/ 不合法，并对只带 Win 键的组合给出「叠加 Ctrl」的建议 |
| 遮罩不透明度 | 滑块 |
| 悬停高亮色 | 文本框，自动补 `#` |
| 悬停展开/收起延迟 | 留空即沿用设计基线 |
| 动画 | 跟随系统 / 始终播放 / 始终不播放 |
| 开机自启 | 写注册表，读的也是注册表（事实来源） |

三条刻意的设计：

**「应用」与「保存」分开。** 录制出一个组合后**不自动应用** —— 用户可能只是想看看它长什么样，
而误改一个正在生效的热键会让工具突然"消失"，代价比多点一次按钮大。

**热键探测会临时释放当前热键。** 否则探测一个"正好等于当前生效"的组合会因被自己占用
而返回 1409，用户会看到"当前热键被占用"这种莫名其妙的结论。探测完立刻装回去 ——
用户打开设置看一眼、什么都没改，热键不能因此没了。

**「留空」写回 `null` 而不是当前设计值。** 否则用户只是打开设置看一眼，配置里就会多出
一个显式值，从此设计基线再改也影响不到他。

### 验证（`--settings-probe`）

界面好不好看只能靠人看，但这几件事可以程序化核对，而且恰恰是风险最高的：

```
XAML 加载                     通过   （控件名与 code-behind 对不上会直接抛异常）
窗口可显示                      通过   （480 x 608，句柄已创建）
正常保存写入正确                   通过   （热键、延迟、透明度、高亮色，# 自动补齐）
保存后保住注释                    通过   （见 §7）
留空写回 null                  通过
非法输入被拦下且不落盘                通过   （「悬停展开延迟「abc」不是整数。」）
收起快于展开被拦下                  通过
```

为验证保存路径加了一个**刻意做小的测试接缝**（`SaveCurrentSettings` +
几个 `SetXxxForTest`）。这段"从控件读值 → 组装模型 → 校验 → 落盘"的逻辑绑着控件、
原本完全无法测，而它恰恰集中了最多约定（留空语义、滑块默认值、非法输入反馈）。
接缝做小一点，好过让这段没验证。

## 7. 测试工程扩到能引用 App 层

设置界面的逻辑原本是测试盲区（在 code-behind 里、绑着控件）。把测试工程的
目标框架从 `net10.0` 改成 `net10.0-windows` 并引用 App 工程后，
App 层里的纯逻辑也进入了单测覆盖 —— 新增 20 条 `HotkeyRecorder` 测试：

- 组合键的规范化顺序（Ctrl → Win → Alt → Shift）
- 只按修饰键**不算错误**，只是"还没输完"（若报成错误，用户按住 Ctrl 的瞬间会看到红字）
- 不支持的键要说明**能用什么**，而不是只说"不行"
- OEM 键显示符号而不是 WPF 名字（`-` 而不是 `OemMinus`）
- 录制结果必须能被解析器重新解析（避免"界面显示 Ctrl+Win+W，写进配置却解析失败"）

## 8. 打包分发

`tools/publish.ps1`，默认自包含单文件（约 125 MB，不依赖 .NET 运行时），
`-FrameworkDependent` 则产出约 1 MB 的 exe（需目标机装 .NET 桌面运行时）。

### 一个差点就发布出去的回归

最初我用了 `EnableCompressionInSingleFile=true`（常识上"压缩=好"），产出 59 MB 的单文件。
实测常驻内存后发现**翻倍了**：

| 方案 | 磁盘 | 任务管理器口径内存 |
|---|---|---|
| 自包含单文件 **+ 压缩** | 59 MB | **128.5 MB** |
| 自包含单文件 不压缩 | 125 MB | 66.4 MB |
| 自包含散装目录 | 133 MB | 65.4 MB |
| 框架依赖 | ~1 MB | 67.2 MB |

**原因：压缩后的程序集无法被内存映射**，运行时必须把它解压到私有内存里，
于是私有工作集大涨。压缩是拿内存换磁盘的开关 ——
它花 62 MB 常驻内存去省 66 MB 磁盘，而本项目的内存目标就在 60 MB 量级。

这正是"每一项决定都要实测"的价值所在：这个开关在文档里写的是"减小发布体积"，
听起来纯赚，而它对本项目最在意的指标的影响只在实测里才看得见。
脚本文件头写明了原因，避免以后有人"优化"回去。

### 独立运行的验证

把 exe 复制到与仓库无关的目录后：
- 进程正常启动常驻，无崩溃日志
- 探针产物落到明确的兜底目录 `%LOCALAPPDATA%\WinQuick\probe-output\`，
  而不是散落在 exe 旁边（`Paths.RepoRoot` 找不到仓库根时会走这条兜底路径）
- 配置仍在 `%APPDATA%\WinQuick\`，与构建方式无关

## 9. 托盘图标与左上角操作条

用户反馈「系统托盘看不到托盘图标，也找不到设置入口」。排查后做了三件事。

### 一、托盘图标：从占位改成正式图标

原代码用 `System.Drawing.SystemIcons.Application` 当图标，而且加载失败时只写了
`Debug.WriteLine` —— **异常被静默吞掉**。这是真正的隐患：托盘图标加载失败时，
Windows 可能根本不显示那个条目，而用户看到的现象是"托盘里什么都没有"，
与真正的原因之间没有任何线索。

改成从嵌入资源加载正式图标（`assets/winquick.ico`，`tools/make-icon.py` 生成），
失败时写日志 + 气泡提示；并退回系统图标兜底。

另按系统请求的小图标尺寸选帧：`Icon(stream)` 默认会自己挑一帧（实测挑到 48px）再由外壳缩小，
多一次缩放就多一分糊。现在按 `SM_CXSMICON` 选 —— 本机请求 28px，加载到的就是 28×28，零缩放。

### 二、左上角操作条（设置 + 退出）

托盘图标在 Windows 11 上**默认被收进溢出区**，用户不一定找得到，而托盘当时是唯一的设置入口
与退出入口。热键唤出的覆盖层是用户必然会看到的地方，把入口放在这里可靠得多。

「退出」同样重要：托盘图标不可见时，用户原本**没有任何退出途径**。

实现为独立的小窗口（132×38）而不是画在已有窗口里，理由：
- 遮罩层是原生 Win32 窗口（为了内存刻意不用 WPF），画按钮就得手写 GDI 绘制与命中测试
- 轮盘窗口只有 740×740 且跟着光标走，覆盖不到屏幕角落

内存代价实测 **0.4 MB**（65.3 → 65.7 MB）。符合 M0 测出的模型（47MB 固定底 + 面积相关）：
渲染栈的一次性开销已被轮盘窗口付过，第二个窗口只按面积计费。

### 三、图标绘制踩的两个坑

**坑一：PIL 的 `pieslice` 同时传 `fill`/`outline`/`width` 时行为不符合预期**，
第一版整个环形被描边色盖住。改成自己构造环形扇区多边形 + 单独的 `line` 描边，
每一步都可预期。

**坑二（更重要）：我两次得出"图标画错了"的结论，都是因为采样点打在了扇区之间的缝隙上。**
扇区跨 `i*60+4` 到 `i*60+56`，而我按 `i*60` 采样 —— 正好是缝。
这和之前验证子弧时把剖面打在缝隙上是同一个错误。

最终改用**无假设的整圈扫描**（沿环带每度采样、报颜色连续区间）才看到真实结构：
6 个浅色扇区 + 1 个蓝色扇区在 71-107°（正是索引 1）+ 透明缝隙 + 边缘描边。

教训：**验证方法本身的错误会伪装成被测对象的缺陷**。凡是"沿某个方向采样"的验证，
采样点必须明确落在被测结构的内部，而不是边界上 —— 或者干脆改成扫描 + 报区间的形式，
让结构自己显现出来。

## 10. 第二轮反馈：操作条点击与托盘图标

### 一、两个按钮"点了都只是关闭"

用户反馈点「设置」没打开设置界面、点「退出」也只是关闭。根因是**焦点链**：
点操作条会让轮盘窗口失去焦点 → 触发"失去焦点即关闭" → 整个覆盖层（**包括操作条自己**）
在按钮的 Click 完成之前就被隐藏了。

修了两处：

1. **操作条设为 `WS_EX_NOACTIVATE`**，点击不再把焦点从轮盘抢走。
2. **失去焦点时要判"是不是自己人抢的"**：`OnRadialFocusLost` 检查新的前台窗口
   是否属于我们（轮盘 / 操作条 / 遮罩），是就不关。这一条同时修掉了原先
   `Deactivated` 与 `WM_KILLFOCUS` 两条路径上的同类问题。

### 二、改成 NOACTIVATE 之后按钮又点不动了

这是本轮最有价值的一个发现，而且是一条**文档里写着、但很容易被忽略的 Windows 约束**：

> **Only the foreground window can capture the mouse.**

WPF 的 `Button.Click` 依赖"按下时捕获鼠标、抬起时判断落点是否仍在按钮内"这套逻辑。
操作条是 NOACTIVATE 的、永远不是前台窗口，于是**鼠标捕获永远失败，Click 永远不完成** ——
现象和"按钮坏了"一模一样。

改在鼠标按下的**隧道**路径上处理（`PreviewMouseLeftButtonDown`）：它在捕获逻辑之前触发，
不依赖捕获，NOACTIVATE 窗口照样收得到（原生遮罩窗口的 `WM_LBUTTONDOWN` 也是这么工作的）。

验证方式：探针把光标移到按钮中心并投递按下/抬起消息，核对设置请求是否触发。
改之前是"否"，改之后是"是"。

### 三、设置窗口可能开在别的窗口后面

同一根源：用户点 NOACTIVATE 的操作条时，前台窗口不改变，**我们进程没有获得前台权限**，
此时 `SetForegroundWindow` 会被系统拒绝，设置窗口可能开在别的窗口后面 ——
表现又是"点了没反应"。

已在 `OpenSettings` 里加显式的前台获取（`ForegroundFocus.AttachTo`，内含 `AttachThreadInput` 兜底）。
探针现在核对"前台窗口就是设置窗口"：**是**。

### 四、托盘图标：`IsCreated = 是`

用 H.NotifyIcon 的 `IsCreated` 属性（之前不知道它存在）核对：**外壳确实接受了这个图标**。

所以"托盘里看不到"**不是程序问题，而是 Windows 11 的行为**：
默认把**新的**托盘图标收进溢出区（任务栏的 `^` 箭头里）。
排查方法：点开 `^` 看有没有；或「设置 → 个性化 → 任务栏 → 其他系统托盘图标」里把它打开。

顺带修了两处可能让它更脆弱的地方：
- **先设图标、再设可见**（原先顺序相反，会先以"没有图标"的状态创建再更新）
- 显式 `ForceCreate()` 并核对 `IsCreated`，失败写日志 —— 之前既没核对也没报错，
  所以"托盘里什么都没有"一直是个没有线索的黑盒

## 11. 设置面板改为开在覆盖层里

用户反馈：设置界面太丑、风格不统一，希望做进全屏遮罩里，并让改动立刻可见。

### 改了什么

原来的设置是一个独立的 480×608 对话框，**样式在 XAML 里硬编码颜色**，
与轮盘各写一套 —— 很快就长得不一样，而且不受 `tokens.json` 与规格护栏约束。

现在：

1. **样式全部走令牌**。新增 `TokenResources`，把 tokens 装进 `Application.Resources`，
   面板的 XAML 全部用 `DynamicResource` 引用。与轮盘同源，改设计基线两边一起变。
2. **开在覆盖层会话里**。面板与轮盘同时在场，所以拖遮罩滑块、改高亮色、调悬停延迟，
   都能立刻在旁边的轮盘上看到效果 —— 独立对话框做不到，它会占住前台、覆盖层已经关掉了。
3. **改动即应用 + 去抖落盘**。面板没有保存按钮：每次改动立刻生效，
   500ms 手停下来之后才写配置（拖一次滑块会触发很多次改动，逐个写盘既无必要也伤磁盘）。
4. 删掉了旧的独立窗口 —— 留着会变成两套设置界面。

### 面板与操作条的焦点策略是相反的

操作条是 `WS_EX_NOACTIVATE`（绝不能抢焦点），而面板**需要**激活 ——
热键录制与文本框都要键盘输入。它会夺走轮盘的焦点，由"焦点是否落在自己人身上"
那条守卫兜住，不会误关覆盖层。关面板后显式把焦点还给轮盘，否则 Esc 就失效了。

### 探针抓到的一个真崩溃

```
System.InvalidOperationException: 转换对于 Window 无效。
   at SettingsPanel.PlayEntrance() → RenderTransform = scale
```

WPF 的 `Window` 会对 `RenderTransform` 做强制转换并抛异常 —— 变换必须挂在根内容元素上。
**轮盘窗口当初正是为此把变换挂在根视觉元素上的，我写面板时忘了**。
这个崩溃只在真正打开面板时发生，也就是用户报的"点设置没反应"的那个场景。

这条只有走**真实集成路径**的探针才抓得到：直接 `new SettingsPanel()` + `Show()` 不会触发它，
必须先 `overlay.Show()` 再 `overlay.OpenSettings()`。所以探针里补了这一段，
并核对：轮盘仍可见（可即时预览）、面板取得前台（可输入）、关面板后轮盘重获焦点。

### 同时修掉探针自身的一个缺陷

第一次跑出异常时，探针**崩溃了却报"总体全部通过"** —— 异常被捕获后只汇总了之前累积的结果。
这比没有探针更糟，因为它会让人以为这块已经验证过了。现在异常会记成一条失败结果。

### 另有一条我的探针期望写错了

我最初断言"输入到一半的数值不该被应用"（比如把 200 改成 300 时中途出现的 `3`）。
但 `3` 是语法合法的整数，而我实现的解析器就认为它有效 —— **那是我没实现的意图，不是设计缺陷**。

允许中间值生效才是对的：面板是实时预览，让中间值即时生效符合"改动即预览"；
真正防止坏值落盘的是去抖保存。真正要保证的是**非数字输入不生效也不刷红字**
（用户打字时刷红字比静默等待更烦），这一条已通过。

## 12. 第三轮反馈：面板置顶 + 菜单项图形化编辑

### 一、面板没有置顶，根本点不到

遮罩窗口与轮盘窗口都设了 `Topmost`，**而面板没有** —— 于是它被压在最上层的遮罩下面，
既看不见也点不到。

修：面板加 `Topmost`，并纳入覆盖层的置顶重申（`_topmostTimer`）。

连带发现并修掉两处：

- **面板开着时轮盘不该夺焦点**。菜单变更会重建轮盘窗口，而重建会 `SetForegroundWindow` 到轮盘 ——
  用户正在面板里打字时焦点会被抢走。现在 `Show()` 里判了"面板开着就不夺"。
- **菜单变更不再关面板**。之前的逻辑是"先收面板再重建轮盘"，理由是不打断预览；
  但菜单变更正是面板里的操作引起的，关掉面板反而把用户想看的预览打断了。
  面板是独立窗口，重建轮盘不影响它。

### 二、菜单项改为图形化编辑

用户反馈：加一项还要手改 `menus.json`，太麻烦，希望能从文件浏览器选程序自动加。

面板里新增「菜单项」一节：

| 操作 | 说明 |
|---|---|
| 列出当前项 | 名称可**直接改**（自动取的名字有时很长，如「Windows 命令处理程序」） |
| ＋ 添加程序… | 打开文件浏览器，选中程序即加入 |
| ✕ 移除 | 逐项移除；只剩一项时拒绝（空轮盘是明显的配置错误） |
| 打开 menus.json | 需要手改时仍可直达 |

**名称从程序的版本信息自动取**（`ShellNames`），与内置默认菜单同源 ——
这样用户加进来的项和预置项长得一致、自动跟随系统语言，也不必自己想名字。
实测加入 `notepad.exe` 得到名称「记事本」。

增删改都**立刻写回 menus.json 并重建轮盘**，所以改完马上能在轮盘上看到。
超过 12 项会拒绝并说明原因（CHI'93 实测 8 扇区是错误率拐点，Kano 经验值绝不超 12）。

### 三、面板可能比屏幕还高

加上菜单列表后，面板实测 **909 DIP（1590 物理像素）**。本机 1920 高的屏幕放得下，
但小屏幕上底部的按钮会被截掉、点不到。

修：内容包一层 `ScrollViewer`，并在定位时把 `MaxHeight` 限制在屏幕可用高度内。

**这里又踩了一次"估的尺寸和实际不符"**：定位时用的高度是在布局完成前测的，
实际高度变了之后底部就溢出。探针的「面板完整落在屏内」核对抓到了它
（矩形 `(...)` 与屏幕 `(...)` 一并打印，一眼能看出是竖直方向溢出）。

改成**两遍定位**：先按最大高度估一个位置（避免窗口出现时可见的跳动），
显示并完成布局后再按真实尺寸重摆一次并钳制在屏内。

## 14. 就地编辑菜单：环里的「＋」与右键扇区

用户提出：**能不能在每级环里直接放一个"添加"扇区，点了就弹文件浏览器**，
这样设置面板里就不必再列菜单项了。

这是一条比"把列表搬到别处"更好的方向 —— 菜单的改动效果本来就呈现在轮盘上，
任何"在另一个窗口里改、再回头看轮盘"的设计都让人来回张望。

### 14.1 做法

| 入口 | 位置 | 作用 |
|---|---|---|
| 左键「＋」扇区 | 每级环的**末尾**（含子环） | 弹文件浏览器，选中即加入该级 |
| 右键任意扇区 | 就地 | 弹出改名 / 移除小面板 |
| 设置面板 → 「打开 menus.json」 | 面板 | 批量或手动编辑 |

「＋」排在所有项**之后**并占用一个真实扇区位，理由是角度分配只能有一套规则。
引入一个固定角度位置的特殊扇区，就等于有了两套角度映射，用户更难预判哪个位置是什么。
代价是增删一项时既有扇区的角度会重排 —— 而这与原本的均匀分布行为一致，并非本轮引入。

菜单满 12 项时不再显示「＋」：环已经满了，再加只会细到点不中。

「＋」不是菜单项：写成 `menus.json` 里的一条假项会让配置文件多出一个用户没建过、
也删不掉的东西。它只存在于渲染层（虚线描边以示区别），
`RenderedIconCount` 这类计数也把它排除在外。

### 14.2 顺带修掉的一个真机问题

点「＋」会弹出文件对话框，而对话框夺走前台焦点时，轮盘会收到 `Deactivated`。
原来的判定是"前台窗口不是我们的人 → 用户离开了 → 关闭覆盖层" ——
于是用户选完文件回来，覆盖层已经没了，而"再加一项"这件事还没做完。

对话框期间必须同时做两件事，缺一件都会出错：

1. **屏蔽"失去焦点就关闭"**（`_modalDialogDepth`）。
2. **提高置顶重申频率** —— 对话框只是"有所有者的窗口"，不会自动变成 topmost，
   不重申就会被遮罩盖住一闪。这条是上一轮修 z 序时加的，现在由
   `OverlayController.PickExecutableForMenu` 统一负责，两条编辑入口共用一份实现。

### 14.3 设置面板里的列表去掉了，改名与移除去哪了

去掉列表确实会丢掉两个操作，所以不是单纯地删：**原名与移除搬到了扇区的右键菜单**。

右键菜单画在轮盘窗口**内部**而不是用系统右键菜单或另开窗口。
理由是明确的：本项目最大的风险面一直是"多个顶层窗口之间争层级与焦点"
（遮罩、轮盘、操作条、设置面板、文件对话框已经五个了）。
菜单每多开一个窗口，就多一次"看得见却点不动"的机会。
画在窗口内则完全不存在这个问题 —— 层级由 Canvas 的子元素顺序决定，
点击也不涉及跨窗口的捕获与激活。

### 14.4 规则搬到 Core 且可单测

增删改的规则（上限、"不能删到空"、索引合法性）原先散在界面代码里，靠人点界面确认。
现在有两条编辑入口，规则写两处迟早分叉，所以整体搬进 `WinQuick.Core.Config.MenuEditor`：

- 纯函数，不修改传入的菜单，被拒绝时原样返回并给出原因；
- 由 `MenuEditorTests` 覆盖（新增 21 项单测）；
- 界面层不再重复校验 —— 校验写在两处，迟早有一处忘了改。

其中两条规则值得单独说：

- **第一层不能删空**：整个菜单就没东西可显示了。
- **子层也不能删空**：父项会变成一个既无子项、又无动作的**死扇区** ——
  点它什么都不发生，而用户看不出为什么。与其留下一个点不动的扇区，不如明确拒绝。

### 14.5 验证

新增 `--add-sector-probe`（17 项全通过）。它的做法值得说明：
**点击走的是窗口真正的分派函数**（`ClickForProbe` 调的就是鼠标事件调的那个
`HandleClick`），而不是探针自己重新判断一遍。否则探针验证的是"探针的规则"，
不是程序的规则 —— "遮罩点击关闭"曾经就在这个坑里躺过（文档写着已实现，实际从未生效）。

核对内容：每个扇区中心逐个命中自己（第一层 9 个、子弧 5 个）、
点「＋」发出的是加项请求而不是执行、点真实项仍是执行、12 项时没有「＋」、
恢复菜单后「＋」重新出现、加项后轮盘矩形不变（不跳）、
加项后轮盘中心仍由轮盘窗口拿走（点得到）、右键弹出编辑面板且指向正确的项、
面板开着时左键只收面板不执行下面的项、Esc 先收面板而不关闭覆盖层、
右键「＋」不弹面板而按取消处理。

几何侧另用 `analyze-render.ps1` 新增的**十字核对**确认画出来的确实是加号
（四臂内容 100%、四角 0%）—— 只报"那里有内容"不足以区分加号和别的形状。

探针写完后自己出过两次错，都记在这里：
采样框的尺寸公式在第一层环碰巧接近正确值、到子弧就差了 6 倍，
把"没测到"报成了"形状不符"；
另一处是"右键「＋」"的核对放在了菜单已被换成 12 项之后，那时那里根本没有「＋」。

### 14.6 一个仍存在的粗糙处

右键的编辑面板没有做"点面板以外的地方收起但把这一次点击传递下去"，
只做了"收起并吃掉这一次点击"。少点一次才能执行下面的项，
比"想改名却启动了程序"要好，但不如前者顺滑。

## 15. 两处修正：改为就地刷新、编辑入口收进设置态

用户试用后提了两条，都是对的。

### 15.1 改一项菜单不该重开一次覆盖层

**症状**：每次改快捷选项，工具都要"重新打开一次"。

**原因**：改菜单走的是 `RebuildForMenu` → 销毁轮盘窗口 + 新建 + `Show()`。
那等于把整个覆盖层重开一遍：轮盘消失、再播一遍入场动画长出来。

**改法**：`RadialWindow.ApplyMenu` 就地替换视觉树，窗口本身不动。
省掉的不只是动画 —— 窗口句柄不变意味着不重新插入 topmost band、不重新抢焦点、
不必重新定位，也就没有"重建过程中顺序错了导致点不到"的机会。
位置保留更是不再需要显式处理：窗口压根没动过。

**判据用窗口句柄**：`--add-sector-probe` 核对刷新前后句柄相同
（`0x380802 → 0x380802`）。比"看起来没闪"可靠得多 —— 后者取决于机器快慢，
换台机器就未必成立。

**顺手抓到的一个泄漏**：`CompositionTarget.Rendering` 是**静态**事件，
而换菜单恰恰发生在用户正在操作轮盘的时候（形变动画很可能正在播）。
旧视觉树上的动画器的订阅会一直留在静态事件上 —— 于是那个动画器、它引用的扇区、
乃至整棵旧视觉树都不会被回收，而且每一帧还在跑。这种泄漏在性能劣化到肉眼可见
之前完全没有症状。

修法是在丢树之前调 `_view.ResetInteraction()`。为了让它可验证，
两个动画器各加了一个活跃回调计数，探针先制造一次进行中的形变再换树，
核对换树后计数为 0。**这条核对确认过能失败**：把那行删掉，它就报红
（`动画中 1 → 换树后 1`）。不能失败的核对等于没有核对。

### 15.2 编辑入口不该常驻在轮盘上

**原始做法**：「＋」扇区一直在（只要没满 12 项）。用户指出这不合适 ——
日常使用时轮盘里应当只有自己的项，编辑入口属于设置场景。

**改法**：编辑态由"设置面板是否打开"驱动。点左上角「设置」或从托盘进设置，
轮盘上出现「＋」；关掉设置就收回。「＋」的可见性紧跟面板，所以
"打开设置 → 看见「＋」"是同一个视野里的变化。

由此带来一个副作用需要说明：编辑态下扇区数从 8 变 9（角度重排），
所以进出设置时轮盘上各项的角度会变一次。这是刻意的 —— 它本身就提示了"现在在编辑态"。

核对也相应扩到**走正式路径**（`overlay.OpenSettings()`），而不是探针后门：
"打开设置后出现「＋」"与"关闭设置后收回"两条就是这么验的。

### 15.3 一处因此暴露的顺序问题

`Show()` 里原先打算把编辑态对齐到"面板是不是开着"，但那一行如果放在
**恢复面板之前**，读到的 `IsSettingsOpen` 是过时的（`Hide()` 时把面板藏了），
结果是"面板是开着的、轮盘上却没有「＋」"。改成放在恢复面板之后。

这类"读的状态在几行之后才被修正"的错，不写下来下次还会犯。

## 16. 子环容量与新建分组

用户试用后提的两条。

### 16.1 子环的项数上限不能只有 12

**症状**：外圈子环最多 12 项，12 项也只铺得下 300°，剩下 60° 一直空着 ——
想围成完整一圈做不到。

这里其实是**两个**限制叠在一起，只改一个没用：

| 限制 | 原来 | 现在 |
|---|---|---|
| 弧跨度封顶 | 300° | **360°** |
| 项数上限 | 12（与第一层共用同一个常量） | **20**（子层单独一个） |

弧跨度那条才是主因：12 项按每项 25° 算只需要 300°，所以跨度一直没到过 360°。

加宽规则改成**平滑**的：每项恒定 25°，一路加到 360° 封顶，缺口一度一度收拢。
之所以不是"项数够多就切整圈"：后者会让 11 项（275°）到 12 项（360°）之间跳一下，
扇区宽度其实没变、总跨度却突变。平滑加宽没有这个跳变。
实际效果是 **15 项起**就是完整一圈。

上限 20 不是拍的，取两处约束里更紧的那个：

- **标签**：子环文字半径约 304、图标 30。扇区降到 18° 时，按弦长算出的可用半宽
  正好降到与"不压到图标"的限值相等（约 35）。再细分下去楔形就不再是瓶颈，
  所以 18° 是"再分也不损失文字宽度"的转折点。360 / 18 = 20。
- **点中**：18° 在子环内缘（218）上是约 68px 的弧长，远大于任何可点性下限。

这条换算由 `DesignTokens.Validate` 的一条新核对锁住：它按 `MaxChildSectors` 反算
最细那一档的角度、再算标签能拿到多少宽度，不够 30 就报错。
**这条核对我确认过能失败**：把子环带压窄到 280 就会报"子环按 20 项铺满整圈时……"。
作用是把"环的尺寸"和"子项上限"绑在一起 —— 以后谁改了一边，另一边会先失败，
而不是等用户看到一圈挤成一团的标签。

验证：`--add-sector-probe` 用一个 16 子项的菜单核对，逐项命中自己（17 格全部）、
弧跨度 360°；`--render-preview --children=N` 是为此加的参数，
逐像素扫描确认 12 项时有一块 60° 的空白（`alpha=0`，跨度 104-166°），
20 项时完全没有空白 —— 几何是这么验的，不是看代码推的。

### 16.2 没有途径新建带子项的项

**症状**：能加程序，但**没有任何途径**加一个像「开发工具」那样带子菜单的项。

**原因**：点「＋」直接进文件浏览器，路径上只有"加一个叶子"这一种结果。

**改法**：点「＋」先弹一块小面板问一句：「添加程序…」还是「新建分组…」。
选后者则先起名字，再选一个程序作为它的第一项。

分组**必须带着第一项一起建**：空分组会渲染成一个既无子项、又无动作的扇区，
点它什么都不发生、悬停也不展开任何东西，而用户完全看不出为什么。
宁可要求"先给它放一样东西"，建好之后在它的子环里继续加就是了。
这条同时让 `MenuEditor.Remove` 里"不许把子层删空"那条规则自洽了 ——
分组永远有至少一个子项，不存在"删空了怎么办"的状态。

分组只在第一层建：子环里再放分组就是第三层，而当前只支持两层
（方案第七节：8 扇区下超过 2 层错误率对专家都不可接受）。
所以子环的「＋」不弹这块面板，直接进文件浏览器 —— 那里也给不出两个选项。

两块面板（右键编辑、点「＋」选择）合用一个实现：形态完全一样
（贴着扇区、宽度固定、越界在窗内钳制），差别只在行内容。
分成两份的话锚点算法会开始漂移。

**这里被探针抓到一个真 bug**：「＋」扇区的索引是**伪索引**（等于项数），
不是任何一项的位置。`ShowAddChoice` 起初把它直接透传上去，于是上层收到了
一个越界的父项索引（探针报 `parent=8`，应当是 `-1`）。
索引语义的边界就是这样，不写成核对就只能靠读代码发现。

### 16.3 顺手修掉一条会时好时坏的核对

上一轮那条"换树后没有残留的逐帧回调"原来先制造形变动画、`await Task.Delay(30)`
再换树。但形变只有 130ms，而探针里的 `Task.Delay` 会因为调度器忙而超时很远 ——
等 30ms 实际可能过了 200ms，动画早播完、回调也摘干净了，核对就变成
"没抓到"而不是"没问题"。已经改成同步：挂回调本来就是同步发生的，
同步读就是确定的。连跑三次都是 `动画中 1 → 换树后 0`。

**核对"时好时坏"比核对失败更危险** —— 失败会被看见，时好时坏会被当成通过。
