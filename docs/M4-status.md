## 1. 两份配置的分工

| 文件 | 位置 | 谁定 | 内容 |
|---|---|---|---|
| `config.json` | `%APPDATA%\WinQuick\` | **用户偏好** | 热键、遮罩透明度、悬停延迟、是否动画、自启（也可由设置界面改） |
| `menus.json` | 同上 | **用户内容** | 菜单项、图标、动作、子菜单、角度 |
| `design/tokens.json` | 仓库内，随程序嵌入 | **设计基线** | 配色、半径、时长、缓动曲线 |

**这个分层是刻意的。** `config.json` 里所有可选的旋钮默认值都是 `null`，含义是
「沿用设计基线」，只有显式设了才覆盖。原因是**同一个值不能有两个来源** ——
两处都能改同一个值时，改了 A 没改 B 会静默分叉，而分叉要到界面看起来不对才发现。
这正是我在 M2 建立 `tokens.json` 单一真源时规避的问题，配置系统不能把它重新引入。

## 2. 三条刻意的行为

### 配置写错绝不导致打不开

手写 JSON 出错太容易（少个逗号、多个括号）。最简单的失败方式是"改错配置就再也启动不了"。
所以解析或校验失败时**保留上一份有效配置**，在托盘气泡与日志里报告问题，程序继续运行。

实测验证了四种坏法，全部正确保留并给出可读错误：

| 坏法 | 报出的问题 |
|---|---|
| 语法错误（截断的 JSON） | `menus.json 解析失败：Expected end of string… | LineNumber: 74 | BytePositionInLine: 42` |
| 角度未严格递增 | `items[2]（丙）的 angle=45 未严格大于前一项的 90；显式角度必须严格递增。可以省略 angle 让程序均匀分布。` |
| 热键无法解析 | `hotkey「Ctrl+NotAKey」无法解析：无法识别的主键「NotAKey」` |
| 同一项既有子项又有动作 | `items[0]（甲）同时配了子项和动作 —— 点击时无法确定该展开还是执行` |

错误信息都带**位置**和**怎么改**，而不是一句"解析失败"让用户去猜。

### 首次运行写出可直接编辑的配置

- `config.json` 是**带注释的模板**（解析器支持 JSONC）。注释让"这个字段是干什么的"
  直接在文件里看到，不必翻文档。
- `menus.json` 直接序列化**当前装配好的菜单** —— 用户拿到的是一份填好真实路径、
  可以直接改的配置，而不是空模板。

### 热重载带防抖

编辑器保存一个文件经常连续触发多次变更事件（先清空再写入），不做防抖会读到写了一半的
文件并报一堆假错误。400ms 静默后才真正重载。

菜单变更时会**重建轮盘窗口**（视觉树是构造时用菜单建立的），替换后立刻预热，
所以随后的首次唤出仍然不慢。热键变更会重新注册。

## 4. 排查中发现的三个问题

### 一、我自己引入的标签回归

生成出来的菜单是 `explorer.exe / 终端 / notepad.exe / 计算器 / 设置 / 画图 / Taskmgr.exe / 开发工具`
—— 中文和文件名混在一起。原因是我创建 `DefaultMenu.cs` 时用了
`Path.GetFileNameWithoutExtension` 当标签，而 UWP 项的标签来自 shell，两者来源不一致。

修复过程中试错了两次，值得记下来：

1. **`SHGetFileInfo(SHGFI_DISPLAYNAME)`** —— 返回的是**带扩展名的文件名**。
   那只是资源管理器的"显示扩展名"开关在起作用，不是友好名。
2. **文件名去扩展名** —— 得到 "notepad"、"Taskmgr"。
3. **正确答案：可执行文件的版本资源 `FileDescription`** ——
   任务管理器的「描述」列、开始菜单里的名字都是它。实测值：
   `notepad.exe → 记事本`、`explorer.exe → Windows 资源管理器`、`regedit.exe → 注册表编辑器`。

顺带发现很多系统组件都以 "Windows " 开头（"Windows 资源管理器"、"Windows 命令处理程序"），
在 80px 宽的标签里会折得难看，所以读取时去掉这个前缀。

最终：`资源管理器 / 终端 / 记事本 / 计算器 / 设置 / 画图 / 任务管理器 / 开发工具`，
全部来自系统资源、自动跟随语言，代码里没有硬编码任何标签。

### 二、热重载"失败"其实是我的测试数据错了

第一次跑热重载验证报"未生效"。查日志才发现**文件监视触发了、防抖触发了、重载也跑了**，
只是我测试数据里的 JSON 转义写错了一层（`\W` 是非法转义），配置被**正确地拒绝**了
并保留了上一份 —— 也就是说这次"失败"顺带验证了容错路径在真实文件监视下也生效。

教训：探针只报"未生效"是不够的，**必须把它观察到的原因一并显示出来**，
否则一次测试数据的错误会被误读成功能缺陷。已改成同时输出重载报出的问题。

### 三、生成的 JSON 键名风格不一致

序列化默认输出 PascalCase（`Version` / `Menus` / `Label`），能读回来（大小写不敏感），
但和 `config.json`、和文档里写的 camelCase 不一致，会让人以为两份配置是两种格式。
已加 `PropertyNamingPolicy = CamelCase`，并关闭非 ASCII 转义 ——
中文标签被转成 Unicode 转义序列后手写编辑会非常难受。

## 5. 一条我写错又改回来的校验

我最初把 `hoverOpenDelayMs < 150` 也当成非法配置拦下。后来意识到那是**越权**：
研究结论是「低于 150ms 容易误展开」，那是给**默认值**的建议，不是硬约束。
用户明确要"几乎无延迟"是合理选择。

现在的分界：**硬约束只有两条**（不能为负、收起必须慢于展开），
其余建议写进配置模板的注释里让用户自己权衡。

（这和之前贝塞尔参考值那次是同一类错误：断言了一件自己没想清楚的事。
两次都是测试把它抓了出来。）

## 6. 设置界面

托盘菜单 →「设置…」打开。存在的**首要理由不是"少改 JSON"，而是热键的实时测试**：
热键是唯一的入口，而 Windows 上大量组合被系统或其他程序占用（实测 Win+W、Win+A 都返回 1409）。
用户需要敲一个组合就立刻知道能不能用，而不是改完配置、重启、发现没反应、再猜哪里错了。

| 功能 | 说明 |
|---|---|
| 热键录制 | 点输入框后按组合键，实时显示规范化结果（如 `Ctrl+Win+W`） |
| 热键测试 | 「应用」试注册，报可用 / 被占用（1409）/ 不合法，并对只带 Win 键的组合给出「叠加 Ctrl」的建议 |
| 遮罩不透明度 | 滑块 |
| 悬停高亮色 | 文本框，自动补 `#` |
| 悬停展开/收起延迟 | 留空即沿用设计基线 |
| 动画 | 跟随系统 / 始终播放 / 始终不播放 |
| 开机自启 | 写注册表，读的也是注册表（事实来源） |

三条刻意的设计：

**「应用」与「保存」分开。** 录制出一个组合后**不自动应用** —— 用户可能只是想看看它长什么样，
而误改一个正在生效的热键会让工具突然"消失"，代价比多点一次按钮大。

**热键探测会临时释放当前热键。** 否则探测一个"正好等于当前生效"的组合会因被自己占用
而返回 1409，用户会看到"当前热键被占用"这种莫名其妙的结论。探测完立刻装回去 ——
用户打开设置看一眼、什么都没改，热键不能因此没了。

**「留空」写回 `null` 而不是当前设计值。** 否则用户只是打开设置看一眼，配置里就会多出
一个显式值，从此设计基线再改也影响不到他。

### 验证（`--settings-probe`）

界面好不好看只能靠人看，但这几件事可以程序化核对，而且恰恰是风险最高的：

```
XAML 加载                     通过   （控件名与 code-behind 对不上会直接抛异常）
窗口可显示                      通过   （480 x 608，句柄已创建）
正常保存写入正确                   通过   （热键、延迟、透明度、高亮色，# 自动补齐）
保存后保住注释                    通过   （见 §7）
留空写回 null                  通过
非法输入被拦下且不落盘                通过   （「悬停展开延迟「abc」不是整数。」）
收起快于展开被拦下                  通过
```

为验证保存路径加了一个**刻意做小的测试接缝**（`SaveCurrentSettings` +
几个 `SetXxxForTest`）。这段"从控件读值 → 组装模型 → 校验 → 落盘"的逻辑绑着控件、
原本完全无法测，而它恰恰集中了最多约定（留空语义、滑块默认值、非法输入反馈）。
接缝做小一点，好过让这段没验证。

## 7. 测试工程扩到能引用 App 层

设置界面的逻辑原本是测试盲区（在 code-behind 里、绑着控件）。把测试工程的
目标框架从 `net10.0` 改成 `net10.0-windows` 并引用 App 工程后，
App 层里的纯逻辑也进入了单测覆盖 —— 新增 20 条 `HotkeyRecorder` 测试：

- 组合键的规范化顺序（Ctrl → Win → Alt → Shift）
- 只按修饰键**不算错误**，只是"还没输完"（若报成错误，用户按住 Ctrl 的瞬间会看到红字）

- 录制结果必须能被解析器重新解析（避免"界面显示 Ctrl+Win+W，写进配置却解析失败"）

## 8. 打包分发

`tools/publish.ps1`，默认自包含单文件（约 125 MB，不依赖 .NET 运行时），
`-FrameworkDependent` 则产出约 1 MB 的 exe（需目标机装 .NET 桌面运行时）。

### 一个差点就发布出去的回归

最初我用了 `EnableCompressionInSingleFile=true`（常识上"压缩=好"），产出 59 MB 的单文件。
实测常驻内存后发现**翻倍了**：

| 方案 | 磁盘 | 任务管理器口径内存 |
|---|---|---|
| 自包含单文件 **+ 压缩** | 59 MB | **128.5 MB** |
| 自包含单文件 不压缩 | 125 MB | 66.4 MB |
| 自包含散装目录 | 133 MB | 65.4 MB |
| 框架依赖 | ~1 MB | 67.2 MB |

**原因：压缩后的程序集无法被内存映射**，运行时必须把它解压到私有内存里，
于是私有工作集大涨。压缩是拿内存换磁盘的开关 ——
它花 62 MB 常驻内存去省 66 MB 磁盘，而本项目的内存目标就在 60 MB 量级。

这正是"每一项决定都要实测"的价值所在：这个开关在文档里写的是"减小发布体积"，
听起来纯赚，而它对本项目最在意的指标的影响只在实测里才看得见。
脚本文件头写明了原因，避免以后有人"优化"回去。

### 独立运行的验证

把 exe 复制到与仓库无关的目录后：
- 进程正常启动常驻，无崩溃日志
- 探针产物落到明确的兜底目录 `%LOCALAPPDATA%\WinQuick\probe-output\`，
  而不是散落在 exe 旁边（`Paths.RepoRoot` 找不到仓库根时会走这条兜底路径）
- 配置仍在 `%APPDATA%\WinQuick\`，与构建方式无关

## 9. 托盘图标与左上角操作条

用户反馈「系统托盘看不到托盘图标，也找不到设置入口」。排查后做了三件事。

### 一、托盘图标：从占位改成正式图标

原代码用 `System.Drawing.SystemIcons.Application` 当图标，而且加载失败时只写了
`Debug.WriteLine` —— **异常被静默吞掉**。这是真正的隐患：托盘图标加载失败时，
Windows 可能根本不显示那个条目，而用户看到的现象是"托盘里什么都没有"，
与真正的原因之间没有任何线索。

改成从嵌入资源加载正式图标（`assets/winquick.ico`，`tools/make-icon.py` 生成），
失败时写日志 + 气泡提示；并退回系统图标兜底。

另按系统请求的小图标尺寸选帧：`Icon(stream)` 默认会自己挑一帧（实测挑到 48px）再由外壳缩小，
多一次缩放就多一分糊。现在按 `SM_CXSMICON` 选 —— 本机请求 28px，加载到的就是 28×28，零缩放。

### 二、左上角操作条（设置 + 退出）

托盘图标在 Windows 11 上**默认被收进溢出区**，用户不一定找得到，而托盘当时是唯一的设置入口
与退出入口。热键唤出的覆盖层是用户必然会看到的地方，把入口放在这里可靠得多。

「退出」同样重要：托盘图标不可见时，用户原本**没有任何退出途径**。

实现为独立的小窗口（132×38）而不是画在已有窗口里，理由：
- 遮罩层是原生 Win32 窗口（为了内存刻意不用 WPF），画按钮就得手写 GDI 绘制与命中测试
- 轮盘窗口只有 740×740 且跟着光标走，覆盖不到屏幕角落

内存代价实测 **0.4 MB**（65.3 → 65.7 MB）。符合 M0 测出的模型（47MB 固定底 + 面积相关）：
渲染栈的一次性开销已被轮盘窗口付过，第二个窗口只按面积计费。

### 三、图标绘制踩的两个坑

**坑一：PIL 的 `pieslice` 同时传 `fill`/`outline`/`width` 时行为不符合预期**，
第一版整个环形被描边色盖住。改成自己构造环形扇区多边形 + 单独的 `line` 描边，
每一步都可预期。

**坑二（更重要）：我两次得出"图标画错了"的结论，都是因为采样点打在了扇区之间的缝隙上。**
扇区跨 `i*60+4` 到 `i*60+56`，而我按 `i*60` 采样 —— 正好是缝。
这和之前验证子弧时把剖面打在缝隙上是同一个错误。

最终改用**无假设的整圈扫描**（沿环带每度采样、报颜色连续区间）才看到真实结构：
6 个浅色扇区 + 1 个蓝色扇区在 71-107°（正是索引 1）+ 透明缝隙 + 边缘描边。

教训：**验证方法本身的错误会伪装成被测对象的缺陷**。凡是"沿某个方向采样"的验证，
采样点必须明确落在被测结构的内部，而不是边界上 —— 或者干脆改成扫描 + 报区间的形式，
让结构自己显现出来。

## 10. 第二轮反馈：操作条点击与托盘图标

### 一、两个按钮"点了都只是关闭"

用户反馈点「设置」没打开设置界面、点「退出」也只是关闭。根因是**焦点链**：
点操作条会让轮盘窗口失去焦点 → 触发"失去焦点即关闭" → 整个覆盖层（**包括操作条自己**）
在按钮的 Click 完成之前就被隐藏了。

修了两处：

1. **操作条设为 `WS_EX_NOACTIVATE`**，点击不再把焦点从轮盘抢走。
2. **失去焦点时要判"是不是自己人抢的"**：`OnRadialFocusLost` 检查新的前台窗口
   是否属于我们（轮盘 / 操作条 / 遮罩），是就不关。这一条同时修掉了原先
   `Deactivated` 与 `WM_KILLFOCUS` 两条路径上的同类问题。

### 二、改成 NOACTIVATE 之后按钮又点不动了

这是本轮最有价值的一个发现，而且是一条**文档里写着、但很容易被忽略的 Windows 约束**：

> **Only the foreground window can capture the mouse.**

WPF 的 `Button.Click` 依赖"按下时捕获鼠标、抬起时判断落点是否仍在按钮内"这套逻辑。
操作条是 NOACTIVATE 的、永远不是前台窗口，于是**鼠标捕获永远失败，Click 永远不完成** ——
现象和"按钮坏了"一模一样。

改在鼠标按下的**隧道**路径上处理（`PreviewMouseLeftButtonDown`）：它在捕获逻辑之前触发，
不依赖捕获，NOACTIVATE 窗口照样收得到（原生遮罩窗口的 `WM_LBUTTONDOWN` 也是这么工作的）。

验证方式：探针把光标移到按钮中心并投递按下/抬起消息，核对设置请求是否触发。
改之前是"否"，改之后是"是"。

### 三、设置窗口可能开在别的窗口后面

同一根源：用户点 NOACTIVATE 的操作条时，前台窗口不改变，**我们进程没有获得前台权限**，
此时 `SetForegroundWindow` 会被系统拒绝，设置窗口可能开在别的窗口后面 ——
表现又是"点了没反应"。

已在 `OpenSettings` 里加显式的前台获取（`ForegroundFocus.AttachTo`，内含 `AttachThreadInput` 兜底）。
探针现在核对"前台窗口就是设置窗口"：**是**。

### 四、托盘图标：`IsCreated = 是`

用 H.NotifyIcon 的 `IsCreated` 属性（之前不知道它存在）核对：**外壳确实接受了这个图标**。

所以"托盘里看不到"**不是程序问题，而是 Windows 11 的行为**：
默认把**新的**托盘图标收进溢出区（任务栏的 `^` 箭头里）。
排查方法：点开 `^` 看有没有；或「设置 → 个性化 → 任务栏 → 其他系统托盘图标」里把它打开。

顺带修了两处可能让它更脆弱的地方：
- **先设图标、再设可见**（原先顺序相反，会先以"没有图标"的状态创建再更新）
- 显式 `ForceCreate()` 并核对 `IsCreated`，失败写日志 —— 之前既没核对也没报错，
  所以"托盘里什么都没有"一直是个没有线索的黑盒

## 11. 设置面板改为开在覆盖层里

用户反馈：设置界面太丑、风格不统一，希望做进全屏遮罩里，并让改动立刻可见。

### 改了什么

原来的设置是一个独立的 480×608 对话框，**样式在 XAML 里硬编码颜色**，
与轮盘各写一套 —— 很快就长得不一样，而且不受 `tokens.json` 与规格护栏约束。

现在：

1. **样式全部走令牌**。新增 `TokenResources`，把 tokens 装进 `Application.Resources`，
   面板的 XAML 全部用 `DynamicResource` 引用。与轮盘同源，改设计基线两边一起变。
2. **开在覆盖层会话里**。面板与轮盘同时在场，所以拖遮罩滑块、改高亮色、调悬停延迟，
   都能立刻在旁边的轮盘上看到效果 —— 独立对话框做不到，它会占住前台、覆盖层已经关掉了。
3. **改动即应用 + 去抖落盘**。面板没有保存按钮：每次改动立刻生效，
   500ms 手停下来之后才写配置（拖一次滑块会触发很多次改动，逐个写盘既无必要也伤磁盘）。
4. 删掉了旧的独立窗口 —— 留着会变成两套设置界面。

### 面板与操作条的焦点策略是相反的

操作条是 `WS_EX_NOACTIVATE`（绝不能抢焦点），而面板**需要**激活 ——
热键录制与文本框都要键盘输入。它会夺走轮盘的焦点，由"焦点是否落在自己人身上"
那条守卫兜住，不会误关覆盖层。关面板后显式把焦点还给轮盘，否则 Esc 就失效了。

### 探针抓到的一个真崩溃

```
System.InvalidOperationException: 转换对于 Window 无效。
   at SettingsPanel.PlayEntrance() → RenderTransform = scale
```

WPF 的 `Window` 会对 `RenderTransform` 做强制转换并抛异常 —— 变换必须挂在根内容元素上。
**轮盘窗口当初正是为此把变换挂在根视觉元素上的，我写面板时忘了**。
这个崩溃只在真正打开面板时发生，也就是用户报的"点设置没反应"的那个场景。

这条只有走**真实集成路径**的探针才抓得到：直接 `new SettingsPanel()` + `Show()` 不会触发它，
必须先 `overlay.Show()` 再 `overlay.OpenSettings()`。所以探针里补了这一段，
并核对：轮盘仍可见（可即时预览）、面板取得前台（可输入）、关面板后轮盘重获焦点。

### 同时修掉探针自身的一个缺陷

第一次跑出异常时，探针**崩溃了却报"总体全部通过"** —— 异常被捕获后只汇总了之前累积的结果。
这比没有探针更糟，因为它会让人以为这块已经验证过了。现在异常会记成一条失败结果。

### 另有一条我的探针期望写错了

我最初断言"输入到一半的数值不该被应用"（比如把 200 改成 300 时中途出现的 `3`）。
但 `3` 是语法合法的整数，而我实现的解析器就认为它有效 —— **那是我没实现的意图，不是设计缺陷**。

允许中间值生效才是对的：面板是实时预览，让中间值即时生效符合"改动即预览"；
真正防止坏值落盘的是去抖保存。真正要保证的是**非数字输入不生效也不刷红字**
（用户打字时刷红字比静默等待更烦），这一条已通过。

## 12. 第三轮反馈：面板置顶 + 菜单项图形化编辑

### 一、面板没有置顶，根本点不到

遮罩窗口与轮盘窗口都设了 `Topmost`，**而面板没有** —— 于是它被压在最上层的遮罩下面，
既看不见也点不到。

修：面板加 `Topmost`，并纳入覆盖层的置顶重申（`_topmostTimer`）。

连带发现并修掉两处：

- **面板开着时轮盘不该夺焦点**。菜单变更会重建轮盘窗口，而重建会 `SetForegroundWindow` 到轮盘 ——
  用户正在面板里打字时焦点会被抢走。现在 `Show()` 里判了"面板开着就不夺"。
- **菜单变更不再关面板**。之前的逻辑是"先收面板再重建轮盘"，理由是不打断预览；
  但菜单变更正是面板里的操作引起的，关掉面板反而把用户想看的预览打断了。
  面板是独立窗口，重建轮盘不影响它。

### 二、菜单项改为图形化编辑

用户反馈：加一项还要手改 `menus.json`，太麻烦，希望能从文件浏览器选程序自动加。

面板里新增「菜单项」一节：

| 操作 | 说明 |
|---|---|
| 列出当前项 | 名称可**直接改**（自动取的名字有时很长，如「Windows 命令处理程序」） |
| ＋ 添加程序… | 打开文件浏览器，选中程序即加入 |
| ✕ 移除 | 逐项移除；只剩一项时拒绝（空轮盘是明显的配置错误） |
| 打开 menus.json | 需要手改时仍可直达 |

**名称从程序的版本信息自动取**（`ShellNames`），与内置默认菜单同源 ——
这样用户加进来的项和预置项长得一致、自动跟随系统语言，也不必自己想名字。
实测加入 `notepad.exe` 得到名称「记事本」。

增删改都**立刻写回 menus.json 并重建轮盘**，所以改完马上能在轮盘上看到。
超过 12 项会拒绝并说明原因（CHI'93 实测 8 扇区是错误率拐点，Kano 经验值绝不超 12）。

### 三、面板可能比屏幕还高

加上菜单列表后，面板实测 **909 DIP（1590 物理像素）**。本机 1920 高的屏幕放得下，
但小屏幕上底部的按钮会被截掉、点不到。

修：内容包一层 `ScrollViewer`，并在定位时把 `MaxHeight` 限制在屏幕可用高度内。

**这里又踩了一次"估的尺寸和实际不符"**：定位时用的高度是在布局完成前测的，
实际高度变了之后底部就溢出。探针的「面板完整落在屏内」核对抓到了它
（矩形 `(...)` 与屏幕 `(...)` 一并打印，一眼能看出是竖直方向溢出）。

改成**两遍定位**：先按最大高度估一个位置（避免窗口出现时可见的跳动），
显示并完成布局后再按真实尺寸重摆一次并钳制在屏内。

## 14. 就地编辑菜单：环里的「＋」与右键扇区

用户提出：**能不能在每级环里直接放一个"添加"扇区，点了就弹文件浏览器**，
这样设置面板里就不必再列菜单项了。

这是一条比"把列表搬到别处"更好的方向 —— 菜单的改动效果本来就呈现在轮盘上，
任何"在另一个窗口里改、再回头看轮盘"的设计都让人来回张望。

### 14.1 做法

| 入口 | 位置 | 作用 |
|---|---|---|
| 左键「＋」扇区 | 每级环的**末尾**（含子环） | 弹文件浏览器，选中即加入该级 |
| 右键任意扇区 | 就地 | 弹出改名 / 移除小面板 |
| 设置面板 → 「打开 menus.json」 | 面板 | 批量或手动编辑 |

「＋」排在所有项**之后**并占用一个真实扇区位，理由是角度分配只能有一套规则。
引入一个固定角度位置的特殊扇区，就等于有了两套角度映射，用户更难预判哪个位置是什么。
代价是增删一项时既有扇区的角度会重排 —— 而这与原本的均匀分布行为一致，并非本轮引入。

菜单满 12 项时不再显示「＋」：环已经满了，再加只会细到点不中。

「＋」不是菜单项：写成 `menus.json` 里的一条假项会让配置文件多出一个用户没建过、
也删不掉的东西。它只存在于渲染层（虚线描边以示区别），
`RenderedIconCount` 这类计数也把它排除在外。

### 14.2 顺带修掉的一个真机问题

点「＋」会弹出文件对话框，而对话框夺走前台焦点时，轮盘会收到 `Deactivated`。
原来的判定是"前台窗口不是我们的人 → 用户离开了 → 关闭覆盖层" ——
于是用户选完文件回来，覆盖层已经没了，而"再加一项"这件事还没做完。

对话框期间必须同时做两件事，缺一件都会出错：

1. **屏蔽"失去焦点就关闭"**（`_modalDialogDepth`）。
2. **提高置顶重申频率** —— 对话框只是"有所有者的窗口"，不会自动变成 topmost，
   不重申就会被遮罩盖住一闪。这条是上一轮修 z 序时加的，现在由
   `OverlayController.PickExecutableForMenu` 统一负责，两条编辑入口共用一份实现。

### 14.3 设置面板里的列表去掉了，改名与移除去哪了

去掉列表确实会丢掉两个操作，所以不是单纯地删：**原名与移除搬到了扇区的右键菜单**。

右键菜单画在轮盘窗口**内部**而不是用系统右键菜单或另开窗口。
理由是明确的：本项目最大的风险面一直是"多个顶层窗口之间争层级与焦点"
（遮罩、轮盘、操作条、设置面板、文件对话框已经五个了）。
菜单每多开一个窗口，就多一次"看得见却点不动"的机会。
画在窗口内则完全不存在这个问题 —— 层级由 Canvas 的子元素顺序决定，
点击也不涉及跨窗口的捕获与激活。

### 14.4 规则搬到 Core 且可单测

增删改的规则（上限、"不能删到空"、索引合法性）原先散在界面代码里，靠人点界面确认。
现在有两条编辑入口，规则写两处迟早分叉，所以整体搬进 `WinQuick.Core.Config.MenuEditor`：

- 纯函数，不修改传入的菜单，被拒绝时原样返回并给出原因；
- 由 `MenuEditorTests` 覆盖（新增 21 项单测）；
- 界面层不再重复校验 —— 校验写在两处，迟早有一处忘了改。

其中两条规则值得单独说：

- **第一层不能删空**：整个菜单就没东西可显示了。
- **子层也不能删空**：父项会变成一个既无子项、又无动作的**死扇区** ——
  点它什么都不发生，而用户看不出为什么。与其留下一个点不动的扇区，不如明确拒绝。

### 14.5 验证

新增 `--add-sector-probe`（17 项全通过）。它的做法值得说明：
**点击走的是窗口真正的分派函数**（`ClickForProbe` 调的就是鼠标事件调的那个
`HandleClick`），而不是探针自己重新判断一遍。否则探针验证的是"探针的规则"，
不是程序的规则 —— "遮罩点击关闭"曾经就在这个坑里躺过（文档写着已实现，实际从未生效）。

核对内容：每个扇区中心逐个命中自己（第一层 9 个、子弧 5 个）、
点「＋」发出的是加项请求而不是执行、点真实项仍是执行、12 项时没有「＋」、
恢复菜单后「＋」重新出现、加项后轮盘矩形不变（不跳）、
加项后轮盘中心仍由轮盘窗口拿走（点得到）、右键弹出编辑面板且指向正确的项、
面板开着时左键只收面板不执行下面的项、Esc 先收面板而不关闭覆盖层、
右键「＋」不弹面板而按取消处理。

几何侧另用 `analyze-render.ps1` 新增的**十字核对**确认画出来的确实是加号
（四臂内容 100%、四角 0%）—— 只报"那里有内容"不足以区分加号和别的形状。

探针写完后自己出过两次错，都记在这里：
采样框的尺寸公式在第一层环碰巧接近正确值、到子弧就差了 6 倍，
把"没测到"报成了"形状不符"；
另一处是"右键「＋」"的核对放在了菜单已被换成 12 项之后，那时那里根本没有「＋」。

### 14.6 一个仍存在的粗糙处

右键的编辑面板没有做"点面板以外的地方收起但把这一次点击传递下去"，
只做了"收起并吃掉这一次点击"。少点一次才能执行下面的项，
比"想改名却启动了程序"要好，但不如前者顺滑。

## 15. 两处修正：改为就地刷新、编辑入口收进设置态

用户试用后提了两条，都是对的。

### 15.1 改一项菜单不该重开一次覆盖层

**症状**：每次改快捷选项，工具都要"重新打开一次"。

**原因**：改菜单走的是 `RebuildForMenu` → 销毁轮盘窗口 + 新建 + `Show()`。
那等于把整个覆盖层重开一遍：轮盘消失、再播一遍入场动画长出来。

**改法**：`RadialWindow.ApplyMenu` 就地替换视觉树，窗口本身不动。
省掉的不只是动画 —— 窗口句柄不变意味着不重新插入 topmost band、不重新抢焦点、
不必重新定位，也就没有"重建过程中顺序错了导致点不到"的机会。
位置保留更是不再需要显式处理：窗口压根没动过。

**判据用窗口句柄**：`--add-sector-probe` 核对刷新前后句柄相同
（`0x380802 → 0x380802`）。比"看起来没闪"可靠得多 —— 后者取决于机器快慢，
换台机器就未必成立。

**顺手抓到的一个泄漏**：`CompositionTarget.Rendering` 是**静态**事件，
而换菜单恰恰发生在用户正在操作轮盘的时候（形变动画很可能正在播）。
旧视觉树上的动画器的订阅会一直留在静态事件上 —— 于是那个动画器、它引用的扇区、
乃至整棵旧视觉树都不会被回收，而且每一帧还在跑。这种泄漏在性能劣化到肉眼可见
之前完全没有症状。

修法是在丢树之前调 `_view.ResetInteraction()`。为了让它可验证，
两个动画器各加了一个活跃回调计数，探针先制造一次进行中的形变再换树，
核对换树后计数为 0。**这条核对确认过能失败**：把那行删掉，它就报红
（`动画中 1 → 换树后 1`）。不能失败的核对等于没有核对。

### 15.2 编辑入口不该常驻在轮盘上

**原始做法**：「＋」扇区一直在（只要没满 12 项）。用户指出这不合适 ——
日常使用时轮盘里应当只有自己的项，编辑入口属于设置场景。

**改法**：编辑态由"设置面板是否打开"驱动。点左上角「设置」或从托盘进设置，
轮盘上出现「＋」；关掉设置就收回。「＋」的可见性紧跟面板，所以
"打开设置 → 看见「＋」"是同一个视野里的变化。

由此带来一个副作用需要说明：编辑态下扇区数从 8 变 9（角度重排），
所以进出设置时轮盘上各项的角度会变一次。这是刻意的 —— 它本身就提示了"现在在编辑态"。

核对也相应扩到**走正式路径**（`overlay.OpenSettings()`），而不是探针后门：
"打开设置后出现「＋」"与"关闭设置后收回"两条就是这么验的。

### 15.3 一处因此暴露的顺序问题

`Show()` 里原先打算把编辑态对齐到"面板是不是开着"，但那一行如果放在
**恢复面板之前**，读到的 `IsSettingsOpen` 是过时的（`Hide()` 时把面板藏了），
结果是"面板是开着的、轮盘上却没有「＋」"。改成放在恢复面板之后。

这类"读的状态在几行之后才被修正"的错，不写下来下次还会犯。

## 16. 子环容量与新建分组

用户试用后提的两条。

### 16.1 子环的项数上限不能只有 12

**症状**：外圈子环最多 12 项，12 项也只铺得下 300°，剩下 60° 一直空着 ——
想围成完整一圈做不到。

这里其实是**两个**限制叠在一起，只改一个没用：

| 限制 | 原来 | 现在 |
|---|---|---|
| 弧跨度封顶 | 300° | **360°** |
| 项数上限 | 12（与第一层共用同一个常量） | **20**（子层单独一个） |

弧跨度那条才是主因：12 项按每项 25° 算只需要 300°，所以跨度一直没到过 360°。

加宽规则改成**平滑**的：每项恒定 25°，一路加到 360° 封顶，缺口一度一度收拢。
之所以不是"项数够多就切整圈"：后者会让 11 项（275°）到 12 项（360°）之间跳一下，
扇区宽度其实没变、总跨度却突变。平滑加宽没有这个跳变。
实际效果是 **15 项起**就是完整一圈。

上限 20 不是拍的，取两处约束里更紧的那个：

- **标签**：子环文字半径约 304、图标 30。扇区降到 18° 时，按弦长算出的可用半宽
  正好降到与"不压到图标"的限值相等（约 35）。再细分下去楔形就不再是瓶颈，
  所以 18° 是"再分也不损失文字宽度"的转折点。360 / 18 = 20。
- **点中**：18° 在子环内缘（218）上是约 68px 的弧长，远大于任何可点性下限。

这条换算由 `DesignTokens.Validate` 的一条新核对锁住：它按 `MaxChildSectors` 反算
最细那一档的角度、再算标签能拿到多少宽度，不够 30 就报错。
**这条核对我确认过能失败**：把子环带压窄到 280 就会报"子环按 20 项铺满整圈时……"。
作用是把"环的尺寸"和"子项上限"绑在一起 —— 以后谁改了一边，另一边会先失败，
而不是等用户看到一圈挤成一团的标签。

验证：`--add-sector-probe` 用一个 16 子项的菜单核对，逐项命中自己（17 格全部）、
弧跨度 360°；`--render-preview --children=N` 是为此加的参数，
逐像素扫描确认 12 项时有一块 60° 的空白（`alpha=0`，跨度 104-166°），
20 项时完全没有空白 —— 几何是这么验的，不是看代码推的。

### 16.2 没有途径新建带子项的项

**症状**：能加程序，但**没有任何途径**加一个像「开发工具」那样带子菜单的项。

**原因**：点「＋」直接进文件浏览器，路径上只有"加一个叶子"这一种结果。

**改法**：点「＋」先弹一块小面板问一句：「添加程序…」还是「新建分组…」。
选后者则先起名字，再选一个程序作为它的第一项。

分组**必须带着第一项一起建**：空分组会渲染成一个既无子项、又无动作的扇区，
点它什么都不发生、悬停也不展开任何东西，而用户完全看不出为什么。
宁可要求"先给它放一样东西"，建好之后在它的子环里继续加就是了。
这条同时让 `MenuEditor.Remove` 里"不许把子层删空"那条规则自洽了 ——
分组永远有至少一个子项，不存在"删空了怎么办"的状态。

分组只在第一层建：子环里再放分组就是第三层，而当前只支持两层
（方案第七节：8 扇区下超过 2 层错误率对专家都不可接受）。
所以子环的「＋」不弹这块面板，直接进文件浏览器 —— 那里也给不出两个选项。

两块面板（右键编辑、点「＋」选择）合用一个实现：形态完全一样
（贴着扇区、宽度固定、越界在窗内钳制），差别只在行内容。
分成两份的话锚点算法会开始漂移。

**这里被探针抓到一个真 bug**：「＋」扇区的索引是**伪索引**（等于项数），
不是任何一项的位置。`ShowAddChoice` 起初把它直接透传上去，于是上层收到了
一个越界的父项索引（探针报 `parent=8`，应当是 `-1`）。
索引语义的边界就是这样，不写成核对就只能靠读代码发现。

### 16.3 顺手修掉一条会时好时坏的核对

上一轮那条"换树后没有残留的逐帧回调"原来先制造形变动画、`await Task.Delay(30)`
再换树。但形变只有 130ms，而探针里的 `Task.Delay` 会因为调度器忙而超时很远 ——
等 30ms 实际可能过了 200ms，动画早播完、回调也摘干净了，核对就变成
"没抓到"而不是"没问题"。已经改成同步：挂回调本来就是同步发生的，
同步读就是确定的。连跑三次都是 `动画中 1 → 换树后 0`。

**核对"时好时坏"比核对失败更危险** —— 失败会被看见，时好时坏会被当成通过。

## 17. 两个「＋」行为不一致（用户报"点＋直接进文件浏览器"）

**症状**：点「＋」扇区直接打开了文件浏览器，看不到「新建分组」选项。

**根因**：两个「＋」的行为不一样，而这一点只有读代码才看得出来 ——

| 位置 | 改前 | 改后 |
|---|---|---|
| 第一层的「＋」 | 弹选择面板（添加程序 / 新建分组） | 弹选择面板 |
| 子环的「＋」 | **直接进文件浏览器** | 弹面板（只有"添加程序"，并写明分组在外圈建） |

上一版给子环的「＋」留了直通，理由是"那里给不出两个选项，一块面板只放一行按钮没必要"。
这个理由站不住：用户点到的恰好是那一个，于是"新建分组"完全不存在于他的视野里。
**两个入口做同一件事却走不同路径，本身就是缺陷**，哪怕每条路径单独看都合理。

现在两边都先出一块面板。子环那块仍然只有一个按钮，但把"分组在哪里建"写清楚了：
多一次点击，换掉一次困惑。这个症状从"取决于你点了哪个加号"变成不可能发生。

### 17.1 我复现不出用户报的那条路径

值得记下来：**第一层的「＋」我始终没能复现出"直接进文件浏览器"**。试过三种方式：

1. 把命中结果直接喂给分派函数（探针后门）；
2. `PostMessage(WM_LBUTTONDOWN)` 打一次**真实**的鼠标按下；
3. 完全照用户的路径 —— 先按左上角「设置」，再点「＋」。

三种都得到 `AddChoice` 面板。所以上面那条"子环「＋」"是唯一能造成用户所见现象的路径，
但**我没有证据说用户点的就是它**。另一可能是用户在旧进程上试的（常驻程序不重启就还是老代码）。

结论是把它做成"无论点哪个都不可能直接进文件浏览器"，而不是继续猜用户点了哪里。

### 17.2 为了让这个结论可信，加了一条状态探针

排查中最有用的一步是加了一个把三个量一起打出来的诊断接口：
`(编辑态, 菜单项数, 「＋」索引)`。单看「＋」索引 = -1 说明不了什么 ——
可能是没进编辑态，也可能是菜单满了 12 项。三个数一起看，一眼就是
`(True, 12, -1)`：编辑态开着、但菜单是 12 项那一份，所以本来就不该有「＋」。
**"这个数不对"和"这个数为什么不对"是两件事**，前者靠打印，后者靠把相关的量一起打印。

### 17.3 顺手修掉我自己在探针里挪错的一段

排查过程中我在探针里搬动"用户路径"那一段，结果把一条断言和它的动作分开了 ——
断言留在原处（读到的还是按下之前的状态），动作被搬到了几十行之后，
于是它报红。这类"搬代码搬出半截"的错误，表现是核对失败而不是编译失败，
很容易被当成真缺陷去查。教训：**搬一段代码时，用唯一的锚点，并且搬完立刻跑一次**。

## 18. 子环的悬停鼓出

一级早就有鼓出（内缘不动、外缘外扩 12px），子环只有高亮变色、没有形变。
用户报的这条，补上。

### 18.1 为什么子环迟了一轮

子环比一级多一个变量：**外径同时受展开进度控制**。
一级的外径只由鼓出决定，所以它的动画器可以自己算几何（内径外径都传进去）；
子环不行 —— 展开动画与悬停形变是两条独立的逐帧回调，
谁都可以在任何一帧动这个扇区，各写各的 `Data`，后写的就把前一个的效果抹掉。

改法是把几何的所有权收给调用方：动画器不再自己算环带，只回答
"每个扇区此刻该鼓出多少像素"，几何由视图写。子环那边把
**展开进度 + 鼓出**在一处合成（`WriteChildSectorGeometry`），
从此这个扇区的 `Data` 只有一个写入点。

这么拆还有个好处：缓动、逐帧回调、快速划过的接续、回调计数
（那个抓泄漏的 `ActiveHookCount`）两个环原样复用，没有第二份实现。

### 18.2 验证

**几何**：`--render-preview` 分别渲出两种状态，沿不同角度做径向剖面，
比最后一个不透明带的结束半径 ——

| | 被悬停 | 未悬停 | 差值 |
|---|---|---|---|
| 一级（`--state=hover`） | 210 | 198 | **12** |
| 子环（`--state=child-leaf`） | 361 | 349 | **12** |

一级那行是**回归核对**：这次重构动了它，必须证明没弄坏。
（绝对值 210/198 而不是 212/200，是因为剖面取的是颜色相同的最后一行，
差 2px 是抗锯齿；差值才是判据。）

**行为**：`--add-sector-probe` 用**真实指针**停在子项上，走悬停状态机那条路，
读到的鼓出量是 12px —— 直接调 `SetChildHover` 只能证明"画得出来"，
证明不了"悬停时真的会鼓"。另外两条核对覆盖立即落定（离屏渲染靠它）与收起后归零
（归零很重要：鼓出动画的回调写的是即将被移除的扇区，不复位会一直挂在静态事件上）。

**预算**：`DesignTokens.Validate` 新增一条 —— `ring2Outer + hoverBulgePx` 不能超过窗口半径。
子环是最外圈，鼓出去就是真的出界，会被窗口边缘裁掉，表现为"悬停子项时某个方向少一块"，
而且只在特定方向上出现，很难看出来。这条核对我确认过**能失败**：把鼓出量改成 30 就报出来。

### 18.3 一个自己造成的坑

这一轮有两个补丁脚本跑完报"ok"，实际什么都没改 —— `rep()` 这个辅助函数
**返回**新字符串，而我调用时没有接返回值，于是所有替换都被丢掉了。
表现是"脚本说成功了、代码没变"，直到编译报出一个只在别处加过的字段才暴露。

之所以能发现，是因为后续编译失败了；如果那些改动恰好不引起编译错误，
就会变成"以为改了、其实没改"，然后在别的地方找原因。
**辅助函数是纯函数（返回新值）还是就地改（改参数）必须一眼看得出**，
混着用就会出现这种静默失效。这次之后统一成"传路径与替换对，内部负责读写"。

## 19. 长文本裁剪与悬停位移；流畅度

### 19.1 悬停位移：两处来源，都在"动文字"

用户报"文本较长时会被裁剪，鼠标悬停时会发生位移"。查下来是两件事，都在标签上：

| 来源 | 现象 |
|---|---|
| 悬停把字重从 Normal 换成 SemiBold | SemiBold 更宽，而文字是按 Normal 的宽度居中的 —— 换字重后没有重新测量，整段字往右挪，右边还可能被裁掉 |
| 悬停启动一条 **Forever 的来回滚动动画** | 指针停在上面期间文字持续左右滑 |

滚动本身是上一轮用户要求的（"看看能否做成滚动文本"）。但它的代价比当时估计的大：
菜单的用法是「看一眼就要点」，动的字反而读不到；而且它要挂一条常驻动画时钟，
悬停期间每帧推进，换来的可读性接近零。

**改成"截断 + 中心显示完整文字"**：静止的字一个像素都不动，完整文字仍然拿得到。
死区是界面上唯一整块空着的地方，而它的语义正是"当前没指向任何项"——
用它显示"当前指向的那一项的完整名字"不占任何额外空间，只有被截断的项才占用它，
所以 "Esc" 提示在其余时候照常显示。

字重也不再随悬停变化：悬停的反馈由扇区高亮与向外鼓出承担，已经足够明显。

### 19.2 裁剪的真实原因不是宽度，是**行数**

第一版我以为"裁断"是横向溢出，于是按宽度判断。探针一跑就露了：

```
被截断的标签数   0        ← 明明是一条 43 字符、放不下的长标签
最长溢出        0 px
```

原因是判据写错了。折行之后 `DesiredSize.Width` 被 `MaxWidth` 夹住，
**永远"刚好合适"**；真正超的是**高度**（三行以上）。于是代码以为放得下，
而第三行往后被裁剪框直接切掉 —— 文字少了半截、还没有任何提示。
这恰恰是最难自己发现的一种缺陷：宽度那一项看起来完全正常。

修法是把判据换成 `FitsWithinBox()`（宽和高一起看），并新增"两行 + 省略号"的兜底：
二分查找能装进两行的最长前缀，加省略号。用二分而不是逐字减 ——
构建期最多 6 次文字测量，逐字减在长文本上是几十次。
保留两行而不是退化成一行：两行能容下的字多一倍，而完整文字在中心还能读全。

`IsElided` 的判据也跟着改成"显示的文本 ≠ 原始文本"，不再看溢出像素 ——
溢出像素在"行数超限"这种情况里可以是 0，用它判断会让中心读出永远不触发，
而那正是被截断文字的唯一补救途径。

### 19.3 流畅度：先能测，再改

新增 `--perf-probe`：用**真实交互**驱动（指针扫过扇区、展开子弧、扫过子项），
采集 `CompositionTarget.Rendering` 的到达间隔，给出 p50/p95/p99/最大、
长帧占比、以及测量期间的托管分配。

关键一点：**不自己造假的动画循环**。假循环测出来的数字与用户看到的东西无关。

改动前后的数字（本机 120Hz，理想间隔 8.33ms）：

| | p50 | p95 | 最大 | 托管分配 |
|---|---|---|---|---|
| 改动前（1 次） | 8.67 | 17.19 | **44.93** | 2378 KB/s |
| 改动后（3 次） | 8.34–8.38 | 16.66–16.95 | **25.29–27.40** | 1931–2080 KB/s |

p50 本来就贴着帧预算（说明常态没问题），**变化主要在长帧**：
最大帧从 45ms 降到 25–27ms，超过 33ms 的帧从 2 个降到 0，分配降了约 16%。
如实说明：改动前只跑了 1 次，"前 vs 后"的对比因此有噪声；
但"改动后 3 次的长帧上限都明显低于改动前那 1 次"是一致的。

改动内容：

1. **悬停只改变化过的那两个扇区**，不再遍历全环重赋一遍属性。
   赋相同的值不触发重绘，所以旧写法"结果正确"、只是白做 ——
   而悬停是轮盘上最频繁的动作，这些白做的活直接变成掉帧。
2. **画刷按 (颜色, 透明度) 缓存**。`TokenBrushes.Brush` 原来每次调用都新建并冻结一个
   `SolidColorBrush`；一次悬停切换要造好几个。冻结画刷不可变，共享完全安全。
3. **去掉悬停时的字重变化与滚动动画** —— 文字重排是悬停路径上最贵的一步。

### 19.4 又踩了一次同一个坑

补丁脚本的 `rep()` **返回**新字符串，而调用时没接返回值 —— 两个文件的修改被静默丢弃，
脚本还打印了"ok"。这和上一轮那次是同一个错误。

这次能立刻发现，是因为其中一处改了函数签名导致编译失败。
**判据：辅助函数是纯函数还是就地修改，必须一眼看得出。**
现在统一成 `patch(路径, 替换对列表)`，内部负责读写，不再暴露"返回值要不要接"这个问题。

## 20. 撤销"中心读出"：它把 Esc 提示顶掉了

用户报：像 "Adobe Photoshop 2025" 这样的项，悬停时轮盘中心的 "Esc" 被换成了这个名字。

这个"中心读出"是上一轮我自己加的，用来给被截断的项一个看全的地方。**它有两处错**：

1. **Esc 是界面上唯一的取消提示，不该因为某个项名字长就消失。**
   用户把它报成 bug 是对的 —— 我为了一个次要信息，挪掉了一个主要信息。
2. **它根本做不到它承诺的事。** 死区直径只有 112px，长名字在那里**同样要截断** ——
   等于把同一个缺陷画了两遍（扇区里截一次、中心再截一次）。
   实测 "Adobe Photoshop 2025" 在中心读出里显示的就是 "Adobe Photoshop 2025" 被截断的版本。

所以直接删掉，不加开关。

### 20.1 但根因是"三行装不下两行"，不是"没地方显示"

回头看这个例子："Adobe Photoshop 2025" 在 11px 下总宽约 118px，
而标签框宽上限是 80px（这个上限由 3 点/9 点方向的**图标净距**决定，
不是楔形弦长 —— 那里标签的宽度方向正好压在半径上，环内已经没有余量）。
所以两行怎么排都要有一行超过 80px，于是被截断。

而三行完全放得下：`Adobe` / `Photoshop` / `2025`，每行都远小于 80px。
径向空间也够 —— 三行的盒子高 41px，落在半径 129~170 之间，
外圈环带到 200、图标止于 105.6，两头都不碰。

于是把 `labelMaxLines` 从 2 放宽到 3。效果：
**"Adobe Photoshop 2025" 现在以 14px 原字号完整显示，既不缩字也不截断。**
这比"截断 + 想办法把完整名字显示到别处"直接得多 —— 问题出在容量，就该加容量。

### 20.2 顺带把"没被悄悄裁掉"变成了可核对的不变量

原来那条核对是"超长标签必须被截断"。放宽到三行之后它失效了 ——
43 字符的名字现在装得下（那正是想要的效果），于是核对报红。
**核对失效本身说明它锁的是手段而不是目的。**

换成锁目的：任何标签都必须满足 `FitsBox || IsElided` —— 要么真装下了，
要么明确标出了截断。两者都不满足就是"少了一截还没有提示"，
也就是最初那个缺陷的形态。探针现在逐个标签核这一条，并列出违例的文字。

（"FitsBox" 把宽度和高度一起看。最初漏掉高度就是这个缺陷的成因：
折行后宽度被 MaxWidth 夹住、永远"刚好合适"，真正超的是行数。）

## 21. 文件右键菜单集成（M5）

「右键文件 → WinQuick → 添加 → 添加到一级环/分组」。
完整说明与调研证据见 [M5-shell-menu.md](M5-shell-menu.md)，这里只记三件别的：

**一、入口在旧版菜单里，这是 Win11 的硬限制而不是取舍。**
注册表方式注册的右键项只出现在「显示更多选项」（`Shift+F10`）里；
进新版紧凑菜单需要"打包应用 + 原生 COM DLL"，而且**新版只支持一层子菜单**，
`WinQuick → 添加 → 目的地` 在那里根本做不出来。所以付了那个代价也拿不到你要的结构，
不如不付。微软文档、微软自己的问答、以及 PowerToys/Everything/7-Zip 的实际状况都指向同一结论。

**二、计划里的命名管道换成了请求文件。**
原计划是加一条命名管道让第二个进程把请求送到常驻实例。实现时发现常驻实例
**本来就在监视配置目录**（`FileSystemWatcher` + 400ms 防抖），
复用它比维护管道的连接/超时/并发实例数简单得多，而保证完全一样：
仍然只有一个 `menus.json` 写入者（避免和设置保存互相覆盖）、仍然原子（先写 .tmp 再改名）、
仍然有防抖。这是实现期对计划的简化，结论不变。

**三、顺带修掉一个既有的数据丢失路径。**
`SaveMenu` 只序列化当前那一份菜单，于是 `menus.json` 里有两份菜单的用户
在任何一次界面上的增删之后都会丢掉另一份，且没有任何提示。
这个缺陷本来就存在，而本功能让它更常被走到（右键菜单每加一项都要写一次盘），
所以一并修了：只替换同名的那一份，其余原样保留。

## 22. 扇区改成"完整点击才执行"

用户报：鼠标**按住**扇区就直接执行打开了，要求改成"在扇区范围内按住又松开"才触发。

原来在 `MouseLeftButtonDown` 里直接执行。问题很实在：**按错了没法反悔** ——
想挪开再松手，程序已经启动完了。程序启动是不可撤销的，这种误触代价比"少一次响应"大得多。

改法是分成按下/抬起两个阶段：

- **按下只记下落点**，不做任何事；
- **抬起时**要求"同一区域、同一索引"，才当成一次完整点击去执行。

中途移到别处（另一个扇区、环外、中心）都当作放弃。比较的是**区域与索引**而不是只比区域，
所以"按下在 A、松开在 B"不会去执行 B —— 那会让用户想取消时反而打开另一个程序。

「＋」扇区同样适用（它也是"打开"一个面板）。中心死区、环外关闭这些也一并走这条路径。

### 22.1 探针的失败恰好证明了改动生效

加完新核对之后，**原有的两条核对反而红了**：`真实鼠标按下「＋」弹出的是选择面板` 和
`--overlay-probe` 的 `点击扇区是否被检测到`。原因一样：这两条都只投递了 `WM_LBUTTONDOWN`，
没有抬起 —— 在新语义下"只有按下"本来就不该有任何动作。

也就是说**探针的输入序列不再是完整点击**，代码是对的。这同时是个好消息：
它证明新语义在**真实鼠标消息**路径上也生效，而不只是探针自己调的那两个入口。
两条都补上了配对的 `WM_LBUTTONUP`。

（`--overlay-probe` 那条原本自己带了一句"合成消息与真实鼠标输入不完全等价，若你手动点击能生效
则说明是探针的限制"——这种措辞会掩盖真问题，这次差点被它糊过去。核对失败就该查到底，
不能靠一句免责声明收尾。）

### 22.2 新增的核对（`--add-sector-probe`，共 48 项）

| 核对 | 意图 |
|---|---|
| 只按下不执行 | 按住可以反悔 |
| 同一扇区内按下又松开才执行 | 完整点击的定义 |
| 按下后挪到**别的扇区**松开不执行 | 不会误开另一个程序 |
| 按下后挪到**环外**松开不执行 | 拖出去也算放弃 |
| 「＋」也要完整点击才弹面板 | 打开面板同属"打开操作" |

### 22.3 没跟着改的地方

遮罩上点击关闭、左上角操作条的两个按钮，仍然按下即响应。
它们是"点一下就走"的轻量操作（不启动外部程序），按下即响应更跟手；
而误触的代价只是覆盖层关了，再按一次热键即可。扇区不同：误触会启动一个程序。

## 23. 长按 2 秒进入编辑态，拖拽重排扇区

用户要求：长按某扇区 2 秒让整个轮盘进入编辑模式，扇区可以自由拖拽调整排列，
效果类似安卓长按桌面进编辑模式。

### 23.1 三条设计决定（已与用户确认）

| 决定 | 选择 |
|---|---|
| 拖拽的结果 | **按格子重排**：顺序就是 `menus.json` 的数组顺序，扇区始终均匀分布 |
| 拖拽范围 | 同一层内（第一层之间，或某个子环内部）；跨层仍走"移除 + 添加" |
| 编辑态 | 与原来那个（设置面板驱动、管「＋」与右键）**合并成一个** |

选"按格子重排"还有个实现上的好处：`menus.json` 里的 `angle` 字段目前是
**解析了但渲染不用**（渲染只走均匀分布），所以重排**不需要新增任何字段**，
挪数组就够了；盘面顺序与文件顺序也始终一致，手写配置一眼能看懂。

### 23.2 一处既有设计随之改变

编辑态原先**由"设置面板是否打开"推导**（`SetEditMode(IsSettingsOpen)`）。
加长按之后这个推导不成立了：长按进入时面板并没开，而重排会触发一次菜单重建，
那次重建会把编辑态重算成"关"。

改成：**编辑态是独立状态，有自己的出口**（Esc / 点中心 / 点环外 / 关闭覆盖层）。
连带变化：**关掉设置面板不再退出编辑态**（以前会）。理由是用户可能想关掉面板、
继续在轮盘上拖拽排版。

编辑态下**点击扇区不执行程序**（编辑时误触启动的代价太大）；
但**点有子项的扇区仍会展开** —— 要重排子环里的项就得先进得去。

### 23.3 验证

**单测**：`MenuEditor.Move` 的前移/后移/同位置/越界/连续重排（205 项全过）。

**`--add-sector-probe` 新增 13 条核对**（共 55 项全过），其中几条是专门为这个功能
容易出错的地方设的：

- 长按 2 秒进入编辑态；
- **长按不顺带执行该项**、**长按后松手不执行**（否则长按就变成一次误启动）；
- 长按后**继续按住就进入拖拽**（一个连续手势，不用松手再按）；
- 拖拽时目标格子有可见标记，且落点格子与指针所在扇区一致；
- 松手发出重排请求（含从哪到哪）；**重排后编辑态仍在**（那条状态推导的回归锁）；
- **拖回同一格不发出请求**（不产生无意义的写盘）；
- 编辑态下点击扇区不执行；编辑态下 Esc 只退出编辑态、不关覆盖层。

**只能由人判断的部分**：拖拽手感（2 秒是否偏长、跟随是否跟手、目标格子是否看得清）。

### 23.4 验证过程中查出的两个真缺陷

1. **`_longPressFired` 置位在"指针是否挪开"的校验之前。** 指针恰好在计时到点的那一刻
   抖到隔壁，标志已置位却没进编辑态 —— 随后的松手被当成"长按后的松手"吞掉，
   **用户点一下完全没有反应**，而且看不出任何原因。置位挪到所有提前返回之后。
2. **长按的取消判据用了"是否还在同一扇区"，太苛刻。** 12 扇区时缝隙只有几度，
   按住两秒的过程中抖过一条缝，长按就作废 —— 而用户明明"按住没动"。
   改成按移动距离判定（14 DIP 的宽容度）。

### 23.5 一次值得记下的排查弯路

加完这个功能后，`--add-sector-probe` 里 **7 条既有核对突然全红**，现象是
"覆盖层自己关掉了"，而失败点离原因隔了整整一节。

根因是：**切换编辑态会改变第一层的槽数（9 ↔ 8）**，于是父扇区的中心角从 280° 变成 315°，
子弧的位置整体挪走。探针里预先算好的坐标于是落到了**环外** ——
而"点环外"的语义正是**关闭覆盖层**。

教训有两条：

- **核对里的坐标是按布局算的，而布局会变。** 凡是切换过布局（编辑态、增删项、
  菜单重建）之后再用旧坐标，都是同一个坑。
- 最后我是**删掉了一条冗余核对**才收干净的：那条要核"子项被点击时执行"，
  为此必须中途关掉编辑态，于是把整节的坐标作废。而抑制执行走的是同一段
  `!_editMode` 判断，第一层那条已经覆盖了它 —— **核对的代价也是成本**，
  用一条冗余核对搅乱整节状态不划算。

## 24. 长按重排的三条修正（用户实测反馈）

1. **2 秒太长 → 改成 1 秒。** `design/tokens.json` 的 `longPressMs: 1000`。
   做成令牌正是为了这种时候改一个数就行。
2. **编辑态要持续，松开鼠标不该退出。** 核对证实行为上它本来就一直在
   （`松手之后编辑态保持` 通过，只有 Esc / 点中心 / 点环外才退）。
   但屏幕上缺一个**不随拖拽起落变化**的标记 —— 被拖那一项的"抬起"与虚线目标框
   一松手就消失，看起来就像模式结束了。所以加了一圈持续显示的虚线环作编辑态标识。
3. **子环里长按拖的是一级环（真缺陷）。** 拖拽预览原先只操作第一层的扇区数组，
   于是子环里长按会拖到"同一索引的一级扇区"上。改成两级共用同一套预览逻辑，
   差别只在用哪一组扇区/图标/标签、哪个环带与弧段。

### 24.1 顺带修掉的另一个真缺陷

子环里**按住不动**时，悬停状态机在 350ms 后把子弧收掉了：指针落在子项上，
状态机认为"你离开父项了"。于是 1 秒长按触发时子环已经没了 ——
拖拽要么拖不动、要么拖到别的东西上。

修法：**按住期间冻结悬停**（`_pressed is not null` 时 `EvaluateHover` 直接返回）。
按下之后用户不是在用悬停导航，而是在点击或长按，两种意图都不该让盘面在指下变动。

### 24.2 一处**没有查清**的地方（如实记录）

`--add-sector-probe` 里有两项仍未通过：子环长按拖拽的启动与发出的重排请求。

已确认的事实：按下点命中 `ChildSector/0` ✓、按下时判定 `索引=0 / 是子环=True` ✓、
子弧已展开 ✓、无面板 ✓、覆盖层可见 ✓、同一时刻对**第一层**长按仍能正常进入拖拽 ✓。
也就是说按下判定与长按机制都是对的，但拖拽没有启动。

**还没查清原因，留给下一轮。** 这个用例已交给用户手动验证。
其余 56 项通过。

### 24.3 又一次同一个坑

这一轮里我又两次把**坐标按错误的布局**算：切换编辑态会改变第一层槽数（9 ↔ 8），
父扇区中心角随之在 280° / 315° 之间变。第一次是子环那一节用了日常态的角度，
第二次是新加的子环拖拽核对用了日常态的角度。两次都是"坐标算对了、布局变了"。
现在探针里凡是用到角度的地方都注明是按哪一套布局算的。

## 25. 编辑态下按下即拖拽；子环也有编辑态虚线

用户继续反馈两条：

### 25.1 进了编辑态就该直接能拖，不必再长按

长按的语义只是"**进入**编辑态"；进了之后每次拖拽还要再按住一秒很烦，
安卓也不是这样（进编辑态之后图标直接就能拖）。

改成：`HandleLeftDown` 里若已在编辑态且按在真实项上，**立即** `BeginDrag`，
不再走长按计时。长按计时只在日常态用（它的唯一职责就是进入编辑态）。

副作用是好的：子环里的项同样按下即拖（先悬停父项展开子环，再按子项），
所以编辑态下"点父项立即展开子菜单"这条路径不再需要 —— 悬停本来就会展开。

### 25.2 子环也有编辑态虚线

与第一层同形的一圈虚线画在子环环带外（`Ring2Outer + 6`）。
少了它，在子环里操作时分不清"现在编辑的是子环还是第一层"。

它按需增删（`SyncChildEditOutline`）：子弧可能是**日常态**下展开的，
那时不加虚线，之后切到编辑态不会再走"展开"那条路径 —— 所以展开的**提前返回分支**
里也要补一次，不能只在"首次展开"时加。

### 25.3 顺带修掉一个会让程序崩掉的缺陷

探针在子环拖拽那一段抛出 `IndexOutOfRangeException`，指向拖拽预览里访问
子环扇区数组的那一行。根因是：

**子环的收起动画是在按下之前就被悬停状态机排上的**（指针当时不在父项上），
167ms 后才播完 —— 而用户此刻已经在拖这一环里的项了。收起动画播完把子环的
扇区数组清空，下一帧的预览就去访问数组之外了。

三处一起改才够：

1. 拖拽开始时把在途的收起**落定为展开**（`SetChildArcImmediate(true)`）；
2. 子环视觉被移除时**作废针对它的拖拽状态**（`ClearDragState`，只清状态不碰视觉）；
3. 预览与结束路径都先判断"被拖那一级的扇区还在不在"，不在就作废而不是按索引访问。

这也解释了上一轮"没查清"的那两条核对：它们失败与崩溃是同一个原因，
只是当时表现为"拖拽没启动"。**上一轮我说原因未查明是对的 —— 但应该有耐心再多挖一层，
而不是先把它记成"待查"就收工。**

现在 `--add-sector-probe` 60 项全过（含"编辑态下按下即拖拽""子环里按下即拖拽且拖的是子环里的项"
"子环也有编辑态虚线描边"），单测 205 项，其余探针无回归。

## 26. 设置面板可拖动；粒子动画预研

### 26.1 面板可拖动

用户反馈"设置面板有时候会挡住轮盘"。面板本来是按"光标所在屏的另一侧"自动摆位的，
但那个"另一侧"是估的 —— 轮盘跟着光标走，总有些位置会重叠。

改成：**标题栏按住即可拖动**（`DragMove`）。用 `DragMove` 而不是自己算鼠标位移，
是因为它由窗口管理器处理，会把 DPI 缩放、多显示器边界、拖动重入这些细节一起处理掉；
自己算的话每个显示器缩放比都要单独对一遍。

**拖过之后不再自动摆位**（`PlacedByUser`）—— 面板挡住轮盘正是拖开它的动机，
若之后又被自动摆回去等于白拖。最大高度那段仍然照做（它不移动窗口，
只保证小屏上底部按钮不被截掉）。

拖动的实际手感只能由人判断（真实的 `DragMove` 在探针里模拟不了，它要真鼠标按住），
所以没有对应的自动核对。

### 26.2 粒子动画预研

见 [M6-particles.md](M6-particles.md)。核心结论：

- **粒子不会把帧率打垮**：从 0 到 800 颗，p50 只从 16.22 → 16.65ms。
- **代价落在分配上**：图形对象方案 800 颗时 10.4 MB/s，最大帧的抖动是 GC 停顿而非渲染跟不上。
- **不需要新窗口**：粒子可以直接画进现有轮盘窗口，而它在任何动画时本来就在逐帧更新 ——
  不会引入新的呈现代价。这一点比"另开透明窗口放粒子"重要得多（那会多一份面积相关的拷贝，
  还多一个争层级与焦点的窗口）。
- 建议以**短促爆发**为主（10–50 颗，0.3–0.6 秒），不做持续背景粒子。

**一处没查清**：那次采样里帧节拍只有约 60Hz，而同一天 `--perf-probe` 在同一窗口上量到 120Hz。
绝对值因此不可靠（但跨粒子数的相对变化可靠，结论正是建立在相对变化上）。
真要做粒子之前值得先弄清 —— 它可能意味着逐帧改 `Canvas.Left/Top` 会触发每帧布局。

### 26.3 "面板拖不动" —— 查清了，而且是我自己的两个错

用户实测反馈拖不动。查下来是两件事叠在一起：

**一、`Window.DragMove()` 拖不动，而我把失败静默吞了。**

`DragMove` 内部要求窗口处于**激活状态**，不满足就抛异常 —— 而我写了
`catch (InvalidOperationException) { }` 把它吞掉。于是表现成"按下去毫无反应"，
连原因都看不到。**吞异常比抛异常更坏**：抛出来至少能顺着栈找到那一行。

改成自己实现拖动：记下按下的屏幕坐标与窗口位置，之后按位移挪窗口；
全部用物理像素（`GetCursorPos` / `GetWindowRect` / `SetWindowPos`），
绕开 DIP 换算在非整数缩放下的逐帧累积误差。
好处是**不依赖激活状态、也不需要捕获鼠标**（后者正是本项目踩过的坑：
只有前台窗口能捕获鼠标）。

**二、探针里"投递的鼠标按下"收不到 —— WPF 会拿真实按键状态校验。**

这条更值得记：我最初用 `PostMessage(WM_LBUTTONDOWN)` 验证拖动，
探针报"按下后没有进入拖动状态"，看着像产品缺陷。
实际上 WPF 会拿**真实按键状态**校验鼠标消息，投递的按下与真实状态不一致时会被丢掉。
改用 `SendInput` 合成**真实**按键事件之后，同一段代码立刻报
"按下后进入拖动状态 ✓、面板移动量 (105, 70) 与期望完全一致 ✓"。

也就是说：**探针的手法和真实输入不等价时，它会把自己的局限报成产品的缺陷。**
（`--add-sector-probe` 里那几条投递式点击能生效，是因为那条路径恰好没有这层校验 ——
"有时行有时不行"正是这类不等价最典型的症状。）

**三、顺带修掉一处偶发**：新的拖动核对会真的移动光标并点击，光标可能停在下一次
探针的轮盘窗口里，真实 `MouseMove` 就会在合成拖拽之间覆盖指针位置，导致落点格子
偶尔算错。修法是这一节开始前把真实光标停到屏幕角落（轮盘是跟着**唤出时**的光标摆的，
不会追过去）。连跑三次都是 60/60。

## 27. 打开面板/首次唤出时"先闪一下再缩放"

用户反馈：打开设置面板时会**先显示面板、再播入场缩放动画**，看起来像闪了一下；
程序启动后**首次**唤出轮盘同样有。

### 27.1 原因很直接：窗口先显示了，动画之后才开始

原顺序是 `Show()` → 之后才 `PlayEntrance()`。而 **`BeginAnimation` 要到下一帧才生效** ——
所以 `Show()` 之后合成器取走的那一两帧画的是**还没被动画接管的属性值**（终态，完整大小），
动画才开始把它从 0.94 缩放到 1.0。看起来就是"先闪一帧完整尺寸"。

首次唤出最明显：那一次窗口刚被映射，首帧被取走得更早。

### 27.2 改法：把起始状态在显示**之前**落定

拆成两步：

- `PrepareEntrance()`：把起始值**写死**（缩放 0.9 / 透明度 0），在 `Show()` **之前**调用；
- `PlayEntrance()`：从那个状态开始播动画，`Show()` 之后调用。

轮盘与设置面板同源同改。面板那边还有一处细节：它的变换原本是**在 `PlayEntrance` 里新建**的，
所以拆分时必须复用同一个变换对象 —— 否则"显示的起始状态"和"动画的起点"会是两个不同的对象，
改一处忘一处。

**不播动画时（系统关了动画）不要落定起始状态** —— 否则会停在那个人为的缩小状态。

### 27.3 顺带收掉一处三重复制

「要不要播动画」这个判断原先在**三个地方各写了一遍**（轮盘窗口、覆盖层、探针），
这次要给面板用就是第四份 —— 于是收进 `Design/MotionPreference`
（优先用户显式设置，否则跟随系统「在 Windows 中显示动画」这个无障碍开关）。

### 27.4 能自动核对的部分

只能核到"起始状态确实被落定了"。"**不闪**"本身观测不到 ——
闪的是合成器在两帧之间取走的那一帧，从进程内部看不见。
所以这一条与拖拽手感、Explorer 菜单渲染一样，属于**只能由人确认**的部分。

## 28. 刷新内容时的频繁闪烁：两个机制

用户继续反馈：不只是打开时闪，**轮盘和设置界面每次刷新内容都会闪**，观感很差。

上一节修的是"显示之前先落定起始状态"，只解决了**打开那一下**。这次的"刷新时频繁闪"
是另外两个机制 —— 而且两个都只在**分层窗口**上才会显成闪烁：

### 28.1 设置面板：窗口高度随内容变，而分层窗口改高度会重建整块表面

面板是 `SizeToContent="Height"`，而页脚那行状态文本**每次操作都会变**
（"已加入…""名称已改。""已移除。"），一旦换了行数，窗口高度就变 ——
**分层窗口改高度会重建整块表面**，看起来就是每操作一次闪一下。

修法：给页脚一个**写死的两行高度占位**，让状态文本的变化不影响窗口尺寸。
（本项目"尺寸一律走令牌、不写死"的原则针对的是视觉规格；这里写死的是一个
"防止窗口反复改尺寸"的占位高度，不参与观感设计 —— 这一条在代码注释里写明了，
免得后来的人把它当成违反原则。）

### 28.2 轮盘：菜单重建时替换了 `Window.Content`

`ApplyMenu` 原来是把新建的视觉树**整个赋给 `Content`**。换掉窗口的内容对象会让
整棵内容失效、走一次**完整的窗口级测量/排列**，在分层窗口上就表现为闪一下 ——
而改一次菜单就重建一次，所以"频繁"。

修法：`RadialRingView.Build` 增加 `reuse` 参数，**复用同一个画布**、只清空并重建它的子元素。
窗口的内容对象自始至终没变，失效范围就只在那棵画布内部。

### 28.3 教训：分层窗口对"结构性变更"比普通窗口敏感

普通 WPF 窗口改尺寸、换 Content 通常看不出什么；分层窗口因为要走
`UpdateLayeredWindow`（整块表面交给合成器），**任何会导致表面重建的操作都会显成闪一下**：
改尺寸、换内容对象、显示/隐藏、`SetWindowPos`。所以在这两个窗口上，
"能就地改就不要重建"不只是一条性能建议，也是观感要求。

### 28.4 还没查的

"不闪"本身只能由人看（闪的是合成器在两帧之间取走的那一帧）。
如果仍有残留闪烁，下一个候选是"重申 z 序时对分层窗口调 `SetWindowPos`"——
它现在有 `NeedsReassert` 的条件保护，但**每次真正重申都会让所有分层窗口重新合成一次**。
要确认得给窗口级操作加计数器，看闪的那一刻到底是什么操作。

## 29. "还是会闪烁"：把「闪」量出来，而不是继续推

用户第三次报闪烁：**不只是打开时**，轮盘与设置界面**刷新内容时也频繁闪**。

前两次我都是"读代码找机制 → 改掉 → 等用户看"，两次都没解决。问题不在改得对不对，
而在**判据**：闪是合成器在两帧之间取走了一块没准备好的表面 —— 它只存在于屏幕上，
进程内部的任何布尔量都看不见。所以这一轮先造量具。

### 29.1 两件量具

| 探针 | 量什么 | 结论形式 |
|---|---|---|
| `--flicker-probe` | 每个刷新动作触发了哪些**窗口级操作**（改尺寸 / 换内容对象 / `SetWindowPos` / 显隐 / 重建遮罩） | 纯内容刷新应当**一项都不涨**（18 项核对） |
| `--flash-probe` | 直接抓**屏幕像素**：后台线程连续采样（≈60Hz，受合成节拍限制），触发动作打时间戳；另有"动作前后逐像素相同"与"应用侧逐帧入场状态" | 峰值与噪声底同量级才算没闪（9 项核对） |

`--flash-probe` 的采样**必须在后台线程**：第一版放在 UI 线程，而触发动作是同步跑的 ——
采样恰好在动作执行的那一瞬停摆，而闪就发生在那一瞬。那版量出来的"峰值 0"是
**测得不准**，不是"没有闪"。

### 29.2 先排除掉的（都带数字）

- **纯内容刷新**：换菜单（同项数 / 8→9 项）、编辑态开关、悬停、拖拽重排、展开收起子弧、
  面板页脚与热键状态文字、遮罩滑块、延迟、强调色 —— 轮盘与面板**一个像素都没变**，
  窗口级操作也一项不涨（`--flicker-probe` 18/18）。
- **`Window.Content` 复用有效**：换菜单时"换视觉树×1、换内容对象×0"。
- **加一项的完整流程**（弹文件对话框 → 关闭）：轮盘画面与操作前**逐像素相同**（差 0）。
  中途那几段变化是文件对话框自己的出现/移动/消失（它比轮盘还大，按 owner 居中，
  轮盘上没有一处不被它盖住 —— 所以"对话框期间轮盘不变"这条不能核，量到的是对话框）。
- **自我更正**：我在文档里写过"无条件重申会让分层窗口持续重新合成，表现为闪烁"。
  实测**不成立**：一次不改变层叠顺序的重申，屏幕**0 像素**变化。条件化的守卫仍值得留
  （省 CPU），但它从来不是闪的原因。

### 29.3 真正找到的三个缺陷（都修了，都有量出来的前后对比）

**A. z 序重申是逐窗发的，中间那一帧整屏压暗。**

`ZOrderManager.Reassert()` 逐个窗口 `SetWindowPos(HWND_TOPMOST)`，而循环第一刀插的是
最底层 —— **全屏遮罩**。于是有那么几毫秒，遮罩压在轮盘与面板之上；合成器只要在这一瞬
取走一帧，用户看到的就是"整个界面黑了一下又回来"。

量出来的形状完全对得上：连续重申 15 次，**面板区有 6~7 次**留下坏帧，**整块**变化、
**每次幅度完全相同**（＝遮罩的固定 alpha）；轮盘区偶尔也有。

改成 `BeginDeferWindowPos` / `DeferWindowPos` / `EndDeferWindowPos` **整组一次性提交**后，
同样的 15 次，两个区域**一次坏帧都没有**（连跑三轮均如此）。

这条之所以"频繁"：重申在每次弹模态对话框时进/出各一次、每次前台变更（≤4/s）、
以及 800ms 定时器判断需要时都会发生。

**B. 设置面板的入场会先闪一下完整的面板。**

`SettingsPanel.PrepareEntrance()` 写 `Opacity = 0` 之前**没有清掉上一轮残留的动画**，
而 `PlayEntrance` 挂的关键帧动画默认 `HoldEnd` —— 结束后"动画值 1"一直压着本地值。
于是**从第二次打开起**：这里写的 0 被残留动画的 1 盖掉，面板先以**终态**完整显示几帧，
然后才被新动画拽回 0 重新长出来。

量出来的形状：应用侧逐帧不透明度序列是 `1 0 0.48 0.76 …`（触发后首帧 = 终态）。
补上 `BeginAnimation(OpacityProperty, null)`（轮盘那份一直有，面板当初照抄漏了）之后，
三次运行的首帧都是 **0**。

——**用户前后报的"打开设置面板像闪了一下"，就是这一条。** 也解释了为什么只有第一次打开
是对的（那时还没有残留动画）。

**C. 入场动画基本被跳过。**

动画时钟在 `PlayEntrance()` 就起跑，而 UI 线程随后还要忙一阵（摆位、遮罩、焦点、托盘、
重申），等第一帧真正呈现时动画已经走过大半 —— 时间驱动的动画迟到一帧就跳一格。
实测不透明度是 `0 0.71 0.8 …`（8ms 内到七成），167ms 的缩放淡入被压成"啪地出现"。
改成把 `PlayEntrance` 排到 `DispatcherPriority.Loaded`（等当前这批工作做完再起跑）后，
首帧回到 0 并逐帧上升。

### 29.4 量具自己的三个 bug（记下来，因为它太像"产品没闪"）

1. **在 UI 线程上采样** → 恰好错过同步动作执行的那一瞬（见 29.1）。
2. **首帧永远"全变"**：上一帧缓冲是全零，第一次比较必然是整块差异 → 基线是垃圾。
   修法：丢掉每块取样区的第一帧。
3. **`Elapsed(diff)` 把差值当时间戳又减了一次**（印出"触发后 4.98 亿毫秒"），
   外加**在采样窗口结束前就汇总**（触发后 1.4 秒的样本还没到，于是"触发后峰值"被低估、
   漏报）。两个都修了之后，才出现 29.3 那些结论。

顺带修正一条此前"无法解释"的记录：屏幕取样在本机被**合成节拍限制在 ≈60Hz**
（440×440 区域每次 BitBlt 后要等下一帧），与 M6 里那个来路不明的 60Hz 帧节奏是同一件事。

### 29.5 还没解决的

- **入场曲线极度前置**：`cubic-bezier(0,0,0,1)` 在 167ms 里几乎把全部位移集中在前 ~40ms。
  即使调度修好了，观感仍偏"啪"。这是观感取向问题（令牌 `Motion.Easing`），
  不判真假，交由人工决定要不要换更柔和的曲线。
- **面板里仍有两处"内容变→窗口变高"的可能来源**：页脚已加两行高度下限，
  但热键状态那行没有。尚未实测到它把窗口撑高（`--flicker-probe` 里那一步是干净的），
  留作下一次的核对点。
- 用户侧仍然只有他的眼睛能确认"不闪了"。这一轮给出的可复现断言是：
  纯内容刷新 0 像素变化、连续 15 次重申 0 坏帧、加一项前后逐像素相同、
  面板入场首帧不透明度 0。
