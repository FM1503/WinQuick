# M5：文件右键菜单集成

右键任意文件或文件夹 → **WinQuick → 添加 → 添加到xxx**。

## 1. 前提：入口只在旧版菜单里

这是 Win11 的硬限制，不是实现取舍，所以写在最前面：

**注册表方式注册的右键项只出现在旧版菜单**（`显示更多选项`，或按 `Shift+F10`）。

新版那个紧凑菜单只接受**打包应用 + 原生 COM DLL 实现 `IExplorerCommand`**。证据是微软自己的文档与原话：

> Use **Show more options** only to inspect legacy context-menu extensions.
> — [Add a File Explorer context menu command to a packaged desktop app](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer)

> Unfortunately, the context menu in Windows 11 cannot be modified to add new items
> through the registry. The registry can only affect the classic context menu.
> — [Microsoft Q&A](https://learn.microsoft.com/en-nz/answers/questions/3894991/create-a-cascaded-menu-in-modern-windows-11-contex)

同类工具的实际状况一致：PowerToys（[#35974](https://github.com/microsoft/PowerToys/issues/35974)）、
Everything（[voidtools 论坛](https://voidtools.com/forum/viewtopic.php?p=77476)）、7-Zip 目前都只在旧版菜单里。

**还有一条决定性的事实**：新版菜单**只支持一层子菜单**。也就是说即使付了"原生 DLL + 签名 MSIX + 放弃绿色单文件"的代价，
`WinQuick → 添加 → 目的地` 这个结构在那里也做不出来，只能压平成 `WinQuick → 目的地`。

综合下来选了注册表方式：零 DLL、零签名、不改绿色形态、结构完整，代价是多点一下。

## 2. 结构

```
HKCU\Software\Classes\*\shell\WinQuick            ← 也写一份到 Directory\shell
    MUIVerb      = "WinQuick"
    Icon         = <exe 路径>
    SubCommands  = ""            ← 空值才是「可展开」
    （不能有 command 子键，也不能有 (Default)）
  Shell\AddTo
    MUIVerb                  = "添加"
    ExtendedSubCommandsKey   = "WinQuick.AddTo"      ← 引用动词库，不再嵌一层 Shell

HKCU\Software\Classes\WinQuick.AddTo\shell          ← 动词库（两个作用域共用这一份）
    D_0   MUIVerb="添加到一级环"       Icon=…  MultiSelectModel=Single
          command\(Default) = "…\WinQuick.exe" --add-to="root" "%1"
    D_1   MUIVerb="添加到「开发工具」"  command\(Default) = "…" --add-to="group:开发工具" "%1"
```

几条不是随便定的：

- **目的地用 `ExtendedSubCommandsKey` 引用动词库，而不是继续嵌一层 `Shell\` 子键。**
  链式嵌套能用，但第三级弹出面板会被画上一圈**老式 3D 白边框**。
  判断依据是"同机制不同结果"：第一级到第二级也是链式级联、那一级没有边框，
  差别只在于目的地那级是链式的**第二段**；而微软文档对"`ExtendedSubCommandsKey`
  指向的键里能否再嵌套级联"始终没有验证 —— 我原来的结构正好踩在这个未验证位置上。
  Windows 自己用的是 `ExtendedSubCommandsKey`（本机实测 EFS 那条级联就是），照它的写。
- **空 `SubCommands` 是"可展开"的关键。** 微软文档里没写这一点，是社区验证出来的；
  少了它级联可能整个不渲染，而现象只是"菜单里没有这一项"。`--shell-probe` 专门核这一条。
- **每个目的地都要写 `Icon`。** 判据来自对照：本机两个"已知良好"的级联叶子
  （Windows 的 EFS `Decrypt`、VS Code）都写了 Icon，只有我们没写。图标借用程序自身的。
- **键名是 ASCII 序号 `D_0`、中文写在 `MUIVerb` 里**：分组改名时只改文案，键名不动。
- **`%1` 和 exe 路径都带引号**：路径里有空格就会被 shell 拆成多个参数，
  而这个错误在路径短的时候完全看不出来。
- **`MultiSelectModel=Single`**：多选时隐藏该项。旧版动词默认"每个选中文件起一个进程"，
  而本功能一次只处理一个路径 —— 与其让用户以为会全部添加，不如多选时就不显示。
- **目的地用分组名而不是索引**：索引会在增删项时移位，而注册表可能停留在上一轮写入的状态，
  那时点击会加进错误的分组且没有任何报错。

## 3. 点击之后怎么生效

```
Explorer 启动 WinQuick.exe --add-to="…" "<文件路径>"
      │
      ├─ 已有常驻实例 → 把请求写进 %APPDATA%\WinQuick\request-add.json，安静退出
      │                    常驻实例本来就在监视这个目录（400ms 防抖），自己拾取
      └─ 没有实例在跑 → 自己常驻起来，启动流程顺带把这条请求应用掉
```

**只有常驻实例会改 menus.json。** 如果让第二个进程自己改，它就会和常驻实例的设置保存互相覆盖
（最后写入者赢，用户刚在设置面板里做的改动会被悄悄回退）。

计划里原本写的是命名管道。实现时换成了请求文件：常驻实例的配置目录监视器本来就存在，
复用它比维护一个管道的生命周期（连接、超时、并发实例数）简单得多，
而**保证完全一样** —— 仍然只有一个写入者，仍然有防抖，仍然原子（先写 `.tmp` 再改名）。

## 4. 验证

`--shell-probe`（28 项）：真的写 HKCU，然后**逐键读回**比对 ——
`MUIVerb`、`Icon`、`SubCommands` 是否为空、父项有没有多余的 `(Default)`/`command`、
每一条目的地的文案与命令行（含引号）、`MultiSelectModel`、含空格的分组名是否被引号包住、
含引号的分组名是否被跳过、文件夹作用域是否也注册了，最后**核对注销后没有任何残留键**。

还核了请求文件的往返：含中文与空格的路径原样取回、取走后文件被删（否则会重复应用）、
重复取走返回空、**损坏的请求文件被清掉而不是卡住**（留着会让每次重载都失败一遍、永不自愈）。

**一条核对确认过能失败**：把 `SubCommands` 的写入拿掉，探针就报
`不通过 SubCommands 存在且为空（否则不展开）  缺失`。不能失败的核对等于没有核对。

对照：探针会把 Windows 自带的同类级联（`HKCR\*\shell\UpdateEncryptionSettingsWork`，
本机实测存在）读出来做形状对照，确认我们与系统自己的写法一致、不是自创。
这一条是信息性的，不参与判定 —— 那些键在别的系统版本上可能不存在。

## 5. 本探针证明不了的一件事

**Explorer 实际渲染出来的样子，只有人点一次才知道。**
注册表结构能逐值核对，但"菜单里长什么样、点下去是否真的加进去了"必须由你右键试一次。
这是本功能唯一无法自动化的环节。

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| 只在旧版菜单 | 见第 1 节。要进新版菜单得走打包 + 原生 DLL，而且只能两层 |
| 不能多选批量添加 | 多选时该项隐藏（`MultiSelectModel=Single`） |
| 覆盖文件与文件夹 | 不含文件夹空白处/桌面背景 —— 那里没有具体文件，语义不同 |
| 超长路径 | `%1` 传递的路径可能被限制到 MAX_PATH 附近，未特别处理 |
| 分组名含引号 | 该分组不会出现在右键菜单里（会破坏命令行引号），并在托盘说明 |
| 从菜单点下去有启动延迟 | 每次新起一个进程读参数、落请求、退出（自包含单文件约 0.5–1s），随后由常驻实例应用 |
| 右键项不随程序删除而消失 | 它指向 exe 路径；程序被移动时启动会重写，彻底移除要在设置里取消勾选 |

## 7. 上线后立刻踩到的两个坑（都已修）

### 7.1 探针把用户正在用的注册项删掉了

**症状**：功能上线后用户右键还能看到 WinQuick，跑完一轮探针之后再看就没了。

**原因在我**：`--shell-probe` 要核对"注销后无残留"，所以在结尾调 `Uninstall()`，
而它同时也是在**真的写用户注册表**的 —— 于是它把用户正在用的那一份一起删了。
更糟的是常驻实例只在启动/菜单变化/开关变化时写注册表，所以它一直没补回来。

**这是探针设计缺陷**：观测不应改变被观测的东西。
修法是先 `Export()` 备份现场、跑完 `Import()` 原样写回，并在结果里报出
"写回的值数"（数据：34 个值 → 34 个值）。探针现在还会核一条
"原有的注册项被原样写回"。

### 7.2 常驻实例对"注册项被别人删掉"毫无察觉

即使没有我的探针，注册项也是**别人地盘上的东西**：其它右键菜单工具、
清理软件、任何"重置文件关联"的操作都可能删掉它，而程序不会有任何察觉，
用户只看到"菜单项莫名其妙没了"。

所以加了自愈：挂在已有的 5 秒钩子健康检查上，开关打开时若发现注册项不在就补回来。
代价是每 5 秒一次 `OpenSubKey`，可以忽略。**做成自愈比做成"记得别删"可靠。**

### 7.3 一点没查清的事

用户反馈那一刻，常驻实例已经不在运行了（启动时间早于反馈，且之后没有崩溃记录）。
它为什么退出我没有确证 —— 用户可能在排查时从托盘退出了它。
自愈那条能覆盖"实例还在跑但注册项被删"的情况；
实例本身退出时注册项仍在（这是有意的：程序没跑时右键点一下也能启动它并加进去）。

## 8. 第三级子菜单上那圈白色描边（诊断记录）

**现象**（用户反馈 + 截图）：右键菜单里「WinQuick → 添加 → 添加到xxx」这**第三级**
（目的地列表所在的那个弹出面板）有一圈浅色描边，前两级没有。

### 8.1 截图怎么看的

驱动这个项目的模型**读不了图**，所以把截图降采样成字符画再读（`tools/read-screenshot.ps1`），
同时统计颜色分布。结果很明确：

- 底色 `#2C2C2C`（深灰，27648 次）—— 深色主题的经典菜单。
- 描边 `#F0F0F0` / `#FFFFFF`（1258 + 630 次）—— **一条竖线 + 一条底边 + 一条右边**，
  围住的是**右侧那个面板**（里面是 4 行文字 = 4 个目的地）；
  左侧包含上层菜单的面板没有这圈线。

### 8.2 找到的确定差异：目的地缺 `Icon`

把三类叶子项逐值比对（我的目的地 / Windows 自带的 EFS `Decrypt` / VS Code）：

| | 我的目的地 | Windows EFS 叶子 | VS Code |
|---|---|---|---|
| `MUIVerb` | 有 | 有 | 有 |
| **`Icon`** | **没有** | `edputil.dll,-1002` | `Code.exe` |
| `command` | 有 | 有 | 有 |

**唯一缺的就是 `Icon`。** 而它恰好只影响叶子那一级：第一级有图标、第二级是级联父项
本来就不画图标位。已给每个目的地补上图标（借用程序自身的），并在 `--shell-probe`
里加了一条核对钉住它（缺了就在菜单里留一圈空图标位，只看注册表看不出来）。

### 8.3 如果补图标之后描边还在

那么最可能是**由旧的级联实现画出来的默认边框**，而不是我们漏了什么值 ——
深色主题下经典菜单本不该出现这种浅色 3D 边框。

此时有一个**决定性对照**可以一次分清责任：在同一个经典菜单里展开 Windows 自己的级联，
看它的子菜单有没有同样的描边：

> 右键文件 → `显示更多选项` → `发送到` 子菜单（或 `打开方式`）

- **如果「发送到」也有同样的描边** → 那是系统在给"当前激活的子菜单面板"画边框，
  属于经典菜单的既定行为，与我们的注册无关，不该去"修"（也修不了）。
- **如果没有** → 就是 `Shell` 链式级联这条路径特有的渲染，那就改用
  `ExtendedSubCommandsKey`（微软文档化、Windows 自己用的那种写法）重做目的地那一级。

这一条写在这里，是因为**核对代码本身看不出的东西只能靠对照**：
拿系统自己的同类实现当参照物，比继续读文档猜有效。

### 8.4 结论：改用动词库结构

按 8.3 的思路把目的地那一级从"链式嵌套"改成 `ExtendedSubCommandsKey` + 动词库，
理由是本机对照显示 **Windows 自己的级联父项用的就是这个**（它的值里就有
`ExtendedSubCommandsKey`，而没有 `SubCommands`）。改动之后探针 34 项全通过，
其中一条专门钉住这个结构（"用 ExtendedSubCommandsKey 引用动词库、不是嵌套 Shell"）——
改回链式嵌套它就会红。

如果这一版仍然有描边：**最简单的答案是把菜单压成两层**
（`WinQuick → 添加到一级环 / 添加到「开发」`）。这不是妥协 ——
新版 Win11 菜单本身就只允许一层子菜单，两层结构与平台一致，
而且直接消掉了出问题的那一层弹出面板。要不要这么改由你定。
