# M6 预研：粒子动画在本项目里的代价

用户提出"研究粒子动画效果，为更灵动炫酷的动画做准备"。这份是**可行性预研**，不是实现方案。
先量代价再选方案，因为这个工具最硬的约束正对着粒子动画的软肋。

## 1. 为什么必须先量

轮盘窗口是**分层窗口**（`AllowsTransparency=true`）：它的呈现要走一次额外的表面拷贝，
代价与窗口面积相关（见 M0 实测）。而粒子动画天生逐帧 —— **两者叠在一起是最贵的组合**。
所以"能不能做粒子"完全取决于这个代价，而它只能量出来。

## 2. 实测（`--particle-probe`）

在同一台机器、同一个真轮盘窗口上，逐帧动 N 个粒子，量帧间隔：

| 粒子数 | A) 每颗粒子一个 Ellipse | B) 一张 WriteableBitmap + 全幅写回 |
|---|---|---|
| 0（基线） | 16.22 / 18.26 / 23.70 ms │ 153 KB/s | 16.94 / 18.91 / 23.90 ms │ 10239 KB/s |
| 100 | 16.58 / 18.26 / 21.05 ms │ 1775 KB/s | 17.52 / 20.81 / 26.73 ms │ 9894 KB/s |
| 300 | 16.61 / 18.98 / 37.52 ms │ 4058 KB/s | 17.46 / 22.56 / 42.86 ms │ 9731 KB/s |
| 800 | 16.65 / 18.38 / 35.87 ms │ **10361 KB/s** | 16.91 / 22.04 / 24.57 ms │ 10334 KB/s |

（三列依次是 p50 / p95 / 最大帧间隔，最后一列是每秒托管分配）

**先说一个前提**：这次采样里帧节拍只有约 60Hz（基线 p50 16.2ms），
而同一天 `--perf-probe` 在同一窗口上量到 p50 **8.54ms**（120Hz）。
**节拍为什么被压到 60Hz 我没有查明**，所以这一列绝对值不要当准 ——
但**跨粒子数的相对变化是可靠的**，而结论恰恰在相对变化上。

### 可靠的结论

1. **帧间隔对粒子数几乎不敏感。** p50 从 16.22 → 16.65（+0.4ms）、
   p95 从 18.26 → 18.38，即使 800 颗粒子也没有出现"掉帧级联"。
   也就是**粒子本身不会把帧率打垮**。
2. **代价落在分配上，不落在帧率上。** 图形对象方案从 153 KB/s 涨到 **10.4 MB/s**
   （800 颗）。这是 GC 压力的来源，也解释了最大帧为什么在 300/800 档变成 37ms
   —— 那是一次 GC 停顿，不是渲染跟不上。
3. **两种方案的代价结构不同**：
   - A（多个图形对象）：代价**随粒子数线性增长**，但图形对象多、每帧要动的也多。
   - B（WriteableBitmap）：代价**与粒子数无关**（10.2 → 10.3 MB/s 几乎不动），
     因为固定成本是"每帧把整块 360×360 表面写回去"。
     **这一条有明确的优化空间**：我只写了全幅，若改成按脏矩形写（每颗粒子只写它周围几个像素），
     固定成本会降到与粒子面积成正比 —— 那样 B 就同时具备"常数级对象数"和"与粒子数同阶的代价"。

## 3. 一个让人放心的结构性事实

**粒子不需要新的窗口或新的表面。** 它可以直接画进现有的轮盘窗口，
而这个窗口在**任何动画进行时本来就在逐帧更新**（悬停鼓出、子弧展开、入场动画都是）。
也就是说粒子不会引入**新的呈现代价**，只是在已有的逐帧预算里多占一点。

这比"再开一个透明窗口专门放粒子"要好得多：多一个分层窗口就是多一份面积相关的拷贝开销，
而且又多一个要争层级与焦点的窗口 —— 那正是本项目一路踩过来的坑。

## 4. 建议

**做法**：粒子画进现有轮盘窗口；**短促爆发**为主（0.3–0.6 秒），而不是持续背景粒子。

| 效果 | 粒子数 | 预估代价 | 建议 |
|---|---|---|---|
| 悬停扇区时的涟漪/火花 | 10–30，短促 | 与基线几乎无法区分 | **先做这个** |
| 点击选中时的粒子收束（向圆心汇聚后消失） | 20–50，0.4 秒 | 同上 | 第二步 |
| 入场时粒子沿环汇聚成盘面 | 60–120，0.5 秒 | ~1–2 MB/s 分配 | 第二步 |
| 持续背景粒子 | 200+ 常驻 | 4–10 MB/s 分配，最大帧抖动 | **不建议**（收益低、持续付费） |

**实现选型**：短促爆发的粒子数少（≤ 50），用 A（多个图形对象）**最简单且代价可忽略**
（100 颗 = +1.6 MB/s）。只有当粒子数上百、或者要做"持续更替的粒子池"时才值得上 B，
而且那时**必须**改成按脏矩形写。

**不要做**：
- 不要为粒子另开窗口（见第 3 节）。
- 不要用 WPF 的 `Effect`（模糊/发光）做粒子光晕 —— 每个 Effect 占一张中间表面，
  叠几个窗口就退化到软件渲染（这是本项目从一开始就避开的坑）。
  光晕用预渲染的圆点贴图（PNG 带 alpha），一次性贴上去，代价是纯位图合成。
- 不要追求上千颗粒子。这个工具的粒子是"点缀"，不是主体；
  上千颗是游戏引擎的活（需要 `D3DImage` 接真 GPU 粒子管线），
  而为本工具引那条路，代价与收益完全不成比例。

## 5. 还没做的

- 上面全是**代价**数据，**观感**（粒子好看不好看、节奏对不对）只能做出来给人看。
- 节拍被压到 60Hz 那件事没查清。真要做粒子之前值得先弄清 ——
  它可能意味着"逐帧改 `Canvas.Left/Top` 会触发每帧布局"，
  那样的话粒子该改用 `TranslateTransform` 或直接改几何（与鼓出动画一致）。
