# WinQuick · 代码审查与架构性能分析（2026-09）

> 审查范围：`src/WinQuick.Core`、`src/WinQuick.App`、`tests/`、`tools/`、`docs/`（约 2.2 万行 C#）。
> 所有数字都是本次实测或从代码里数出来的，不是印象；性能结论优先引用项目自己的实测记录。
> 执行记录见本文末尾（每完成一项追加一条）。

## 1. 结论

**这是一个"验证纪律远强于代码结构"的项目。**

- **最值钱的资产**：决策链条 —— 先量再改（探针/帧分布/内存预算）、核对必须能失败（每条探针带对照检查）、
  教训写进文档而不是留在脑子里。近五轮它靠这套抓出了分层窗口的 5 个真实缺陷。
- **最大的两处结构性风险**：
  1. **探针与产品代码同体**：`M0` 探针 **6486 行 = App 的 36%**，且发布 exe 里带着
     "能改注册表（`--shell-probe` 装/卸 HKCU 右键菜单）、能移动真实鼠标（`--add-sector-probe`）"的能力；
  2. **App 层零单测**：205 条单测全部覆盖 Core ✓，而近五轮报告的 **5 个 bug 全部出在 App 的状态机**里
     （停放的内容状态、入场起始状态、编辑态推导）。
- 代码卫生本身是好的：TODO/FIXME **0**、阻塞式等待 **0**、空 catch **1**（在探针里）、构建警告 **20**。

## 3. 架构

### 3.1 分层（清楚，且守住了）

- `Core` **不引用 WPF、不引用 App**：几何（`RadialLayout`/`Vec2`）、配置模型（`MenuSpec`/`AppConfig`）、
  悬停状态机（`SubmenuHoverMachine`，15 条边界单测）、运动曲线（`CubicBezier`）。
  **唯一的脏点**是 `Motion/CubicBezier.cs:6` 的文档注释用 `<see cref>` 指向 WPF 的 `KeySpline` ——
  Core 引用不到那个类型（未开文档生成所以不报错），属无害但会误导。
- `App` 内部按职责分区合理：`Hosting`（生命周期）、`Radial`（视图与窗口）、`Interop`（Win32）、
  `Config`（持久化）、`Design`（令牌资源）。四窗栈（遮罩/轮盘/操作条/设置面板）+ `ZOrderManager`
  的层序规则**有专门文档** ✓ —— 这是最容易失控的地方，反而被治理得最好。

### 3.2 结构性弱点

| # | 问题 | 证据 |
|---|---|---|
| A | **探针与产品同体** | `M0` 6486 行；`App.xaml.cs` 的命令分派里 15 个 `--*-probe` 与产品命令并列；`--shell-probe` 会装/卸 HKCU；`--add-sector-probe` 会移动真实鼠标 |
| B | **可测性污染产品接口** | `OverlayController` 有 40+ 个 `*ForProbe` 成员；窗口类里也散着接缝 |

| D | **文档漂移** | `docs/M7-entrance-motion.md:3` 仍写"产品行为尚未改动"（早已实现并定稿）；`docs/M1-status.md:171` 仍写"`design/tokens.json` 单一真源尚未建立"（早已建立并带范围校验） |

## 4. 性能

### 4.1 代价模型（项目自己的实测结论）

分层窗口的代价 ∝ **面积 × 变更帧率**，且**任何内容变化都会重新提交整块表面**。据此做的三件事都被实测证明有效：

| 措施 | 实测效果 |
|---|---|
| 窗口"停放"而非卸载（`Park()`） | 唤出时的长帧 10–16 → **5–8**，最大帧 59 → 24–47ms |
| z 序改**整组原子提交**（`DeferWindowPos`） | 重申导致的坏帧 6~7/15 → **0** |
| 入场只动 Transform/Opacity | 帧分布 p50 ≈ 16ms；几何动画的同长度对照多出一倍长帧（11–15 vs 7–8） |

### 4.2 余量与瓶颈

- **几何变化极便宜**：每帧重建 1/3/6/12 个扇区几何，**一帧不掉**（p95 17–18ms；12 格分配 4.1 MB/s）。
  真正的开销是"内容变化 → 整块重提交"这件事本身，以及窗口映射（已用 Park 消除）。
- **内存**：`~47MB 固定 + ~24 字节/DIP²`，窗口 740 DIP 上限由**单测锁着** —— 这是最容易被"顺手放大一点"
  破坏的约束，守得很好。
- **空闲唤醒**：800ms 置顶守卫（先 `NeedsReassert()` 再动手 ✓ 廉价）、5s 钩子健康 + **右键菜单巡检**
  （每次都读注册表并可能重写，是常驻态最重的一项，值得确认有无"内容没变就不写"的短路）、
  配置目录 `FileSystemWatcher`；25ms 指针轮询**仅在覆盖层可见时**运行 ✓。
- **未定位的残留**：入场期间偶发 20–55ms 长帧（与机器后台负载同级，未归因到单一代码路径）；
  175% 缩放下的文字/图标光栅化成本从未单独测过。

## 8. 执行记录

### P1 探针拆成独立进程（2026-09-17）

- 新增 `src/WinQuick.Probes`：`M0/`（17 个探针）与探针专用的 `Diagnostics/ScreenSampler`、`NativeMethods` 意义上的
  `NativeDisplay` 迁入；探针宿主 `ProbesHost.cs` 自带命令分派与帮助文本。
- 产品 exe 的命令分派**只剩 `--add-to` 与无参数（常驻）** ✓（实测：`case` 列表 = `['--add-to', '']`）。
- 探针命名空间保持 `WinQuick.App.M0` 不变（纯搬迁），可访问性靠 App 项目的 `InternalsVisibleTo`；
  这既是本次改动低风险的原因，也是**已知的整洁性代价**（命名空间与项目不再对应，已在类注释里写明）。
- 发布：`publish\WinQuick.exe`（125.6 MB）+ `publish\probes\WinQuick.Probes.exe` ✓ 都用同一条脚本发布。
- 冒烟：探针 exe 无参数/未知命令 → 打印用法并退出（不建窗口、不动鼠标）；产品 exe 未知命令 → 只列产品命令 + 指向探针 exe。
- 验收：产品 exe 分派无探针 ✓、两个 exe 编译通过 ✓、单测 205 全过 ✓、常驻重启正常 ✓。
- 过程中踩到的三个自身问题（都当场修掉）：移动文件时漏建目标目录；XML 注释里写了连续减号（非法）；
  替换帮助文本时漏掉结尾分号。**这三处都是"改文件"环节的操作错误，不是设计问题** —— 迁移类改动值得每次跑一次编译 + 冒烟。


### P2 顺序与状态下沉 Core（2026-09-17）

- 新增 `Core/Motion/OverlayLifecycle.cs`：`SummonSequence`（唤出顺序）、`DismissSequence`（退场顺序）、
  `EntrancePlan`（入场各通道的起点/终点/时长/曲线 + `PreShowOpacity` 常量）。
- 新增 13 条单测（`OverlayLifecycleTests`，单测 205 → **218**），逐条对应真实缺陷：
  "落定起始状态必须早于显示"（先闪终态的回归锁）、"焦点归还与遮罩消失必须早于等动画"
  （退场不得阻塞动作执行）、"每条通道终点精确落在终态"（动画残留的回归锁）、
  "关掉动画时计划为空但仍须落定终态"、"停放态与入场起点共享不透明度 0"
  （分层窗口安全性的根据："挪回屏上时不可能露出上一轮内容"）。
- App 侧改为消费它们：`OverlayController.Show()` 按 `SummonSequence` 的步骤表执行（不再自己排顺序）；
  `RadialWindow.PlayEntrance()` 从 `EntrancePlan` 取时长与曲线。`Hide()` **刻意不重排**
  控制流，只在注释里点明对应的 `DismissSequence` —— 为对齐清单去动已被验证的动画+计时器，风险大于收益。

### P3 探针接缝集中（**未执行**，判断改为不做）

理由（与 P2 里"不重排已验证的控制流"同一个判断）：P1 之后探针已在**独立进程**里，
"发布产物带着探针能力"这条风险已经消失；剩下的收益只是文件整洁，而代价是重排 1106 行的
`OverlayController` 与 1273 行的 `RadialWindow`（这两处正是最近所有缺陷的发生地，
而它们现在**是被验证过、工作正常的**）。留待"下次因为别的原因要动它们"时顺手做。

### P4 消除全部构建警告（2026-09-17）

**构建输出：0 错误、0 警告**（清理前 20 条普通警告 + 42 条生成器警告）。逐类做法：

| 类别 | 数量 | 做法 |
|---|---|---|
| CA1416（平台守卫） | 8 | 在调用点加**运行时守卫** `OperatingSystem.IsWindowsVersionAtLeast(...)`。先试过"程序集级 `SupportedOSPlatform`"——**那是错的**：它只影响程序集的*调用方*，不消内部告警；又试过把平台版本写进 TFM，被 SDK 拒绝（14393 不在可用目标包列表里），而写 17763 等于把支持范围收窄到 1809。守卫才是分析器真正要的"可证安全" |
| CS8602（可能空引用） | 6 | 三处**真实**风险，逐一改成可空安全写法：`_settingsPanelProbe` 给默认为"不可用"的委托（面板可能先于注入被创建）、探针里 `baselineConfig?.Behavior` 后直接取成员（经典漏网点）、`MonitorLayout.All().FirstOrDefault()` 后直接取属性（record 为 null） |
| CS8500（取托管类型地址） | 2 | `WNDCLASSEXW` 含委托字段故为托管类型；**局部抑制并写明为什么安全**（只喂给 `RegisterClassEx` 一次、委托由静态字段持有）。改成函数指针要动窗口过程 ABI，而遮罩是看得见的功能，为消警告去动它不划算 —— 记在下面 |
| CS0618（弃用 API） | 2 | 换成官方建议的等价调用 `IsPixelShaderVersionSupportedInSoftware(2, 0)` |
| CS4014（未 await） | 2 | 探针里刻意的 fire-and-forget，显式丢弃返回值并注明原因 |
| PInvoke004/PInvoke001（生成器清单） | 42 | `NativeMethods.txt` 里写的是**常量名**，CsWin32 要的是**声明它的枚举类型名**。按警告给出的映射逐条换成枚举类型（已在清单里的直接删行），代码本来就用枚举形式，所以零改动 |
