# 窗口层级与焦点架构

日期：2026-09-14
相关：[M4 状态](M4-status.md)

这份文档记录一次由用户反馈触发的层级问题排查与修复。之所以单独成文：这类问题的症状
（偶尔被盖住、某处点不动）很难稳定复现，靠人手判断也无法在改完后证明修好了，
所以排查过程、根因、以及验证手段都值得留下来。

---

## 1. 现象与最初判断

用户反馈：

1. 遮罩、轮盘、设置面板**一直在争抢顶层显示和焦点**
2. 设置面板弹出的**文件浏览器会被遮罩覆盖**

### 我最初的怀疑（后来被证实）

`ReassertTopmost()` 传了 `SWP_NOZORDER`。官方 `SetWindowPos` 文档原文：

> A window can be made a topmost window either by setting the `hWndInsertAfter` parameter to
> `HWND_TOPMOST` **and ensuring that the `SWP_NOZORDER` flag is not set**…

`SWP_NOZORDER` 的语义是「保持当前 z 序、忽略插入位置」，所以**四处 `ReassertTopmost`
（遮罩/轮盘/操作条/面板）全都是空操作**。我在 M1 文档里写的「事件驱动 + 800ms 定时重申置顶」
**一次都没有生效过**。

---

## 2. 先建验证，再改代码

这类问题不能用肉眼验证，所以先做了 `--zorder-probe`。它用两个系统 API 把现状变成数字：

| API | 回答的问题 |
|---|---|
| `GetWindow(GW_HWNDNEXT)` 沿顶层窗口链遍历 | **真实的 z 序是什么**（而不是相信我们设的 `Topmost=true`） |
| `WindowFromPoint` | **这个坐标上的点击会被哪个窗口拿走** |

第二个是关键：**视觉层级由 DWM 合成决定，命中层级由窗口链决定，两者可以不一致**。
不一致时用户看到的就是「看得见却点不动」——这正是本项目的症状。

### 探针的第一轮结果：没能复现

第一次跑，z 序和落点基本都对。**我没有复现用户描述的"争抢"。** 如实说明了这一点，
并顺着「什么时候窗口会被重新创建」继续查。

### 探针的第二轮结果：复现了

加了一个场景：模拟拖动遮罩深浅滑块（`ApplyDimOpacity` 会**销毁并重建遮罩窗口**）。

```
=== 改设置后（会重建遮罩窗口）===
  实际自上而下: 操作条 > 遮罩 #0
  圆盘扇区（正上方）  期望 轮盘     实际 遮罩 #0   × 点不到
  面板中心          期望 设置面板  实际 遮罩 #0   × 点不到
```

**根因确认**：新建的窗口会被插到 topmost 层**最前面**，于是重建出来的遮罩压在轮盘与面板之上。
它们仍然可见（遮罩只有 40% 不透明），但点击全被遮罩吃掉。而这个重建**每次改设置都会走**：
拖遮罩滑块 → 保存 → 热重载 → 重建遮罩 → 轮盘与面板被盖住。

---

## 3. 修了四处，它们是同一个根因的不同表现

### 3.1 层级栈集中定义（`Interop/ZOrderManager.cs`）

把层级定义成一个**显式的栈**，重申时**从下往上**依次插到 topmost 最前 ——
这样最终顺序确定等于这个栈，而不是取决于谁最后被创建。

```
从上到下（声明顺序）：
  系统对话框
  设置面板
  操作条
  轮盘
  遮罩（每屏一个）
```

集中定义还有一个好处：层级关系变成一处可读、可验证的声明，而不是散在四个文件里的隐式约定。

这与成熟做法一致：PowerToys MeasureTool 是「每屏一个 topmost 遮罩 + 一个 topmost 工具条」，
ColorPicker 把 z 序重申收敛到一个 helper。**ZoomIt 是反面教材** ——
它用 20~250ms 的定时器让多个 topmost 窗口互相重申，源码注释里全是
「免得被另一个 topmost 窗口挤下去」。

### 3.2 重建遮罩后立刻重申

`RebuildDimWindows()` 末尾调用 `ReassertTopmost()`。这是 bug 的发生点，修在这里最直接。

### 3.3 `ApplyDimOpacity` 不再走 Hide/Show 往返

原来它为了换透明度做 `Hide()` → 重建 → `Show()`，踩了两个坑：

- **`Hide()` 启动了退场动画计时器**，167ms 后它执行 `_radial.Hide()` ——
  而那时 `Show()` 早已把轮盘重新显示出来，于是**轮盘又被藏了回去**。
- **`Show()` 不恢复设置面板**，而 `Hide()` 把它藏掉了 —— 往返一次面板就没了。

改成只重建遮罩、并让新窗口跟随当前可见状态。同时补了两道保险：

- `Show()` 停掉退场计时器
- `FinishHide()` 若发现已重新可见就作废（防止过期计时器把刚显示的窗口藏回去）

### 3.4 显隐往返记住并恢复设置面板

`Hide()` 记住面板是否打开，`Show()` 恢复它。否则用户正在填的表单会因为
「改设置」「重建菜单」「显示器变化」这类内部操作毫无预兆地消失。

### 3.5 系统对话框成为层级栈的最顶层

**机制**：官方语义是「一个窗口**变成** topmost 时，它拥有的窗口才连带变 topmost」。
而我们的面板早就是 topmost 了，**这个转变从未发生**，所以它弹出的文件对话框一直是
非置顶的、被遮罩压住。

**修法**：让对话框作为层级栈的**最顶层**参与重申（按 **owner 关系**识别，而不是窗口类名 ——
`#32770` 是通用对话框类，全系统都在用，按类名判会误伤别人的对话框）。

为什么不能只「给对话框加个 topmost 就完事」：我们的重申会把自己的窗口逐个插到 topmost 最前，
**反而会把对话框挤到我们后面**。必须让它参与重申。

另外把对话框弹出期间的重申周期从 800ms 临时提到 100ms —— 对话框的 topmost 只能靠事后补样式，
800ms 的周期会让它先被遮罩盖住一闪。

## 4. 验证结果

```
=== 改设置后（会重建遮罩窗口）===
  实际自上而下: 设置面板 > 操作条 > 轮盘 > 遮罩 #0
  >>> z 序与期望一致。

  圆盘扇区（正上方）  轮盘      轮盘        √
  圆盘外的方形角落    遮罩      遮罩 #0     √
  操作条「设置」按钮  操作条    操作条      √
  面板中心          设置面板  设置面板    √
  遮罩空白（远离一切） 遮罩      遮罩 #0     √
  >>> 所有采样位置的落点都正确。

=== 系统文件对话框 ===
  对话框已置顶     是
  对话框中心落点    对话框自己（点得到）
  >>> 文件对话框已置顶，不会被遮罩盖住。
```

修复前「点不到」3 处，修复后 **0 处**。内存 66 MB（本方案不增加内存）。

## 5. 这次排查的方法论

1. **先建可重复的验证，再动架构。** 用户选了这条路，而它当场就有回报：
   探针第一轮没复现问题，逼着我继续找（而不是"改一改看看"）；
   第二轮用一个具体的触发路径复现了根因。
2. **不要相信自己的状态变量，要问系统。** `Topmost=true` 写着不代表窗口就在最上面；
   `IsVisible` 为真不代表点得到。真实答案只能从 `GetWindow` / `WindowFromPoint` 读。
3. **一个症状往往有多个独立成因。** z 序修完之后轮盘仍然点不到 ——
   根因是另一个：退场动画计时器与重新显示的竞争。如果只验证"z 序对不对"就收工，
   这个问题会留到用户手里。
4. **如实报告没复现出来的部分。** 探针第一轮一切正常，我没有硬说"修好了"，
   而是说明没复现并给出下一步。

## 6. 已知的遗留特性（不是缺陷，但要知道）

- **我们之上还有别的 topmost 窗口**（实测这台机器上有 40 多个，绝大多数不可见）。
  任务管理器、其他置顶工具会真的盖住我们。**没有文档化的、比普通 topmost 更高的层级**，
  未文档化的 `ZBID_*` band 需要签名且不建议使用。
- **独占全屏应用下覆盖层不可见** —— DWM 不参与合成，无解。
- **前台是提权窗口时热键不响应** —— UIPI 隔离，设计使然。
